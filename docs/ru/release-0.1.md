# Выпуск 0.1: что сейчас нужно проекту

Основная версия: [английская](../release-0.1.md).

Выпуск 0.1 «Ядро» **не опубликован и заблокирован**. Эта страница перечисляет, что стоит между текущим `main` и выпуском: проверки, которые должен пройти кандидат, работу, которая идёт, и задачи, которые могут выполнить только люди. Нормативные условия — в [plan.md](plan.md), раздел 12 (условия закрытия и выпуска), а факты по каждому требованию — в [status.md](status.md); эта страница — рабочая сводка обоих и меняется вместе с ними.

## Где мы сейчас

- Последняя полная проверка была у кандидата `a61b961` (2026-11-13). Его CI не зелёный: упали три задания (нативная компоновка на Windows, `std.path` на Windows, классификация предела CPU на Linux arm64), поэтому сборка выпуска, установка без checkout и независимая воспроизводимая сборка на этом коммите пропущены. Успех старых коммитов на кандидата не переносится.
- Условия закрытия 1–3 (резерв выпуска К-17, контрольный набор Н-10 и испытание модели, решение по К-13) выполнены. Испытание Н-10 исправило 161 из 200 программ после одной попытки и 192 из 200 за три ([отчёт](../../bench/results/control_trial-2026-11-12.md)).
- Условия выпуска 1–5 выполнялись на более ранних коммитах (установка, воспроизводимость на Linux x86-64, закреплённый инструментарий, лицензии, гонки доступа к файлам на Linux, macOS и Windows) и должны быть показаны заново на новом кандидате.

## Блокеры, которые исправляются

| Блокер | Что с ним делается |
|---|---|
| Windows: при компоновке нативных файлов нет `bcrypt.lib` | исправлено, ждёт CI: системные библиотеки — те, что сообщает rustc, это проверяет тест; нативный тест функций безопасной случайности |
| Windows: тесты `std.path` предполагают пути POSIX; `starts_with(path, ".")` неверно обрабатывает `\a` и `C:a` | исправлено, ждёт CI: платформенный контракт `std.path` записан в [stdlib.md](stdlib.md) и проверяется на каждой платформе |
| Linux arm64: остановка по пределу CPU классифицирована по времени на часах как сбой (101 вместо 102) | исправлено, ждёт CI: классификация по времени CPU, которое система записала для рабочего процесса |
| `limits.heap_bytes` считает оценку части значений | исправлено, ждёт CI: жёсткий предел по [RFC 0010](rfcs/0010-a-hard-heap-limit.md); распределитель считает каждый блок, который запрашивает программа, за ним стоит предел ОС на Linux и Windows |
| macOS: предел числа процессов — поиск каждые 5 мс, поэтому возможно кратковременное превышение | исправлено, ждёт CI: по [RFC 0011](rfcs/0011-no-process-creation-below-children-on-macos.md) потомки программы не могут запускать процессы, когда предел задан (`RLIMIT_NPROC`, равный 0, в каждом потомке, поэтому каждое создание завершается с `EAGAIN`), а `process.run` учитывает каждого потомка до запуска; программа от root с пределом не запускается (код 103), а потомку нельзя выполнить файл с set-user-ID или set-group-ID, поэтому поиск каждые 5 мс удалён |
| Тесты песочницы, которые завершаются раньше при отсутствии Python или компилятора C, считаются пройденными; два теста изоляции рабочих процессов не выполняются на Windows; тесты и CI на Windows ещё разрешают более слабую песочницу | исправлено, ждёт CI: CI задаёт `UNIO_REQUIRE_PREREQUISITES=1` в каждом задании, поэтому тест без python3, компилятора C, rustc или поддерживаемой цели сборки не проходит, а не считается пройденным, и задания с тестами устанавливают python3 и проверяют компилятор C; тесты рабочих процессов загрузки и распаковки выполняются на Windows в AppContainer и объекте задания (здесь собраны для Windows, выполняются только в CI); ни один тест на Windows и ни одно задание CI не разрешает более слабую песочницу, и это проверяет `release_checks_refuse_the_weaker_sandbox` |
| Фаззер мог сообщить «находок нет», если рабочий процесс умер до записи своего входа | исправлено, ждёт 24-часового запуска: такая смерть проваливает запуск; каждая цель обязана отработать всё время; итоговое задание проверяет все этапы |
| Артефакты выпуска и установка не охватывают Linux arm64; независимая сборка сравнивается только на Linux x86-64 | исправлено, ждёт CI: 0.1 поставляется на четырёх платформах Н-8; `release`, `install` и `reproducible` выполняются на всех четырёх ([plan.md](plan.md), раздел 12, условия 1 и 2); на Windows `unio.exe` компонуется с `/Brepro`, поэтому больше не содержит времени компоновки, а флаг проверяет тест |
| [status.md](status.md) ещё называет старый снимок и содержит строки, расходящиеся с кодом | каждая частичная строка подтверждается доказательством, исправляется или откладывается принятым RFC; никакая отсрочка не предполагается |

## Проверки, которые должен пройти кандидат

Все на одном зафиксированном коммите, после блокеров выше:

1. **Матрица CI зелёная на каждом задании** ([ci.yml](../../.github/workflows/ci.yml)): Linux x86-64, Linux arm64, macOS arm64 и Windows x86-64, включая наборы песочницы SB-8 и SB-15 (Н-7a), контрольный набор (проверка A Н-10), бенчмарки и пределы относительно Go (RFC 0003), паузу освобождения (RFC 0007), записи закреплённого инструментария, сборку выпуска, установленный `unio` без checkout и независимую воспроизводимую сборку.
2. **Санитайзеры** ([sanitizers.yml](../../.github/workflows/sanitizers.yml)): среда выполнения под ASan и MSan и каждый тест Unio через сборку с ASan.
3. **24 часа фаззинга** ([fuzz.yml](../../.github/workflows/fuzz.yml); человек не нужен, запуск на зафиксированном кандидате можно автоматизировать): пять этапов по 300 минут на одном коммите, каждая цель всё своё время, и отчёт `fuzz-evidence` с итогом «выполнено» (Н-1). Он копируется в `bench/results/` вместе с выпуском.
4. **Локальные проверки** из [AGENTS.md](../../AGENTS.md) и [compiler/README.md](../../compiler/README.md) для всех, кто готовит изменение: `cargo fmt --check`, `cargo clippy --all-targets -D warnings` для трёх целей хоста, `cargo test --workspace`, `unio fmt --check`, `unio check` и `unio test` по исходникам и четыре проверки на Python.

## Что могут сделать только люди

- **Проверить внешние функции (Н-5).** Два человека проверяют все 115 внешних функций стандартной библиотеки по [extern-review.md](extern-review.md) на полном SHA кандидата, записывают замечания и проверяют исправления заново. Автоматическая часть (санитайзеры) её не заменяет; выпуск не публикуется, пока колонка любого проверяющего в ожидании.
- **Подписать выпуск ключом выпуска.** Производственный ключ хранится offline и никогда не передаётся в CI (CI подписывает только ключом своего запуска). Ответственный за выпуск подписывает проверенные байты после того, как показаны установка и воспроизводимость, а распространяемый комплект проверяется по открытому ключу из независимого доверенного канала ([packages.md](packages.md), [cryptography.md](cryptography.md)).
- **Решать об отсрочках.** Требование, не выполненное к выпуску, либо исправляется, либо откладывается RFC, который принимает руководитель проекта; по умолчанию ничего не откладывается.
- **Опубликовать выпуск.** Опубликовать примечания к выпуску с результатами 7.1, Н-10 и доказательствами фаззинга. Выпуск подписывает владелец ключа выпуска, который его контролирует.

## Какая помощь нужна

- Запуск тестов на машинах, отличных от образов CI (другие дистрибутивы Linux, более старые macOS, Windows в режиме разработчика), и сообщения о различиях.
- Независимая проверка песочницы ([runtime.md](runtime.md), раздел 9) и криптографии ([cryptography.md](cryptography.md), раздел 7); сообщения — через [SECURITY.md](../../SECURITY.md).
- Программы на Unio и сообщения о неясных или неверных диагностиках; [как Unio работает с ИИ](ai.md) описывает цикл, который использует агент.

Принятые решения: TLS не входит в 0.1 (пакеты аутентифицируются подписями ML-DSA-65, загрузки не приватны); подсчёт ссылок заменяет трассирующий GC в 0.1 (RFC 0007); пределы рабочих процессов компиляции отделены от пределов программы (RFC 0006); предел кучи жёсткий (RFC 0010).

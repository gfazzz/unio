# Техническое задание: Unio, выпуск 0.1 «Ядро»

Версия ТЗ: 0.3 (черновик). Основание: `docs/ru/README.md`, `docs/ru/concept.md`. План работ: `docs/ru/plan.md`. Английская версия (основная): `docs/requirements.md`.

Изменения относительно 0.2: обязательная песочница, которую обеспечивают операционная система и внешняя политика (раздел 4.6); единое правило вызова функции с `fails with` (Я-14, Я-16); модель завершения с раздельными гарантиями для аварий, исчерпания памяти и внештатного завершения, атомарная запись файлов (раздел 4.5, Б-9, Н-2).

Ключевые слова «должен», «обязан» обозначают обязательные требования; «следует» — желательные; «может» — допустимые.

## 1. Общие сведения

### 1.1 Наименование

Unio — язык программирования и комплект инструментов. Предмет ТЗ — первый выпуск, версия 0.1, кодовое имя «Ядро».

### 1.2 Назначение выпуска

Выпуск 0.1 предназначен для написания утилит командной строки и скриптов автоматизации: обработка файлов и текста, вызов внешних программ, работа с JSON и переменными окружения. Выпуск служит основой для последующих серверных, вычислительных и квантовых расширений и не должен требовать их переделки.

### 1.3 Пользователи

- Разработчик, пишущий утилиты вручную.
- ИИ-агент, генерирующий и исправляющий код по заданию человека.
- Рецензент, проверяющий сгенерированный код перед запуском.

### 1.4 Критерии успеха выпуска

1. Утилита из `docs/examples/todo.unio` компилируется, проходит тесты и работает на четырёх платформах без изменений.
2. Десять эталонных утилит (см. раздел 9) написаны на Unio, и внешний читатель без знания языка правильно описывает их поведение по исходному коду в контрольном испытании.
3. ИИ-агент, получив только JSON-диагностику, исправляет не менее 80 % ошибок из контрольного набора без вмешательства человека.
4. Все требования раздела 7 подтверждены измерениями и опубликованы.

## 2. Границы выпуска

### 2.1 Входит

- Язык: конструкции из `docs/concept.md`, разделы 2–5.
- Компилятор с проверкой типов и ошибок, нативная сборка для Linux x86-64, Linux arm64, macOS arm64, Windows x86-64.
- Среда выполнения: GC, ресурсы, аварии, модель завершения, запуск `main`.
- Песочница: ограничение полномочий манифеста и внешней политики средствами операционной системы (раздел 4.6).
- Стандартная библиотека для CLI (раздел 5).
- Инструменты: `unio build`, `run`, `check`, `fmt`, `test`, `add`, `remove`, `update`, `doc`, `symbol`, `explain`.
- Менеджер пакетов с манифестом, lock-файлом и реестром.
- Языковой сервер (LSP) и расширение для VS Code.
- Документация: справочник языка, руководство, справочник стандартной библиотеки.

### 2.2 Не входит

- Параллельность и асинхронность.
- Сетевые клиенты и серверы, кроме загрузки пакетов.
- Вычислительное расширение: тензоры, автодифференцирование, GPU.
- Квантовый модуль.
- FFI для пользовательского кода (`external function` используется только внутри стандартной библиотеки).
- Самостоятельная реализация компилятора на Unio.
- Профилировщик (поставляется в 0.2; в 0.1 только формат событий).

## 3. Требования к языку

### 3.1 Лексика и структура

- Я-1. Файл — UTF-8, расширение `.unio`, блоки по отступам в 4 пробела; табуляция и смешанные отступы — ошибка.
- Я-2. Набор ключевых слов фиксирован и опубликован в справочнике; добавление ключевого слова после 0.1 требует RFC.
- Я-3. Комментарии `#`, документирующие `##`. Документирующий комментарий привязан к следующему объявлению и доступен `unio doc` и `unio symbol`.

### 3.2 Типы

- Я-4. Встроенные типы: `Int`, `Float`, `Bool`, `Text`, `Bytes`, `List[T]`, `Map[K, V]`, `Set[T]`, `Option[T]`, `Result[T, E]`, `Tuple`, `Path`, `Function`, `Never`. `Never` — тип результата функции, которая не возвращает управление; внутри интерфейса `Self` обозначает реализующий тип.
- Я-5. Неявных преобразований между типами нет. Преобразование — явный вызов (`to_text`, `to_int`, `to_float`).
- Я-6. Пользовательские типы: `struct`, `enum`, `interface`, `error`; реализация интерфейса через `extend ... with ...`.
- Я-6a. Вариант перечисления записывается как `Enum.Variant`. Краткая форма `Variant` допустима, если в модуле не видно типа, функции, константы или варианта другого перечисления с тем же именем; иначе краткая форма — ошибка компиляции с исправлением, добавляющим имя перечисления. `some`, `none`, `ok` и `error` видны всегда и не могут быть объявлены.
- Я-7. Обобщённые функции и типы с параметрами и ограничениями по интерфейсам.
- Я-8. Вывод типов только для локальных `let`/`var`. Параметры, результаты, поля и экспортируемые константы аннотируются обязательно.
- Я-9. Равенство структур и перечислений — по содержимому, реализация `Equal` выводится автоматически. `Float` сравнивается по IEEE 754 и не реализует `Hash`: не может быть ключом `Map`, элементом `Set` и образцом `match`. Ресурсы не реализуют `Equal`; `==` для них — ошибка компиляции с подсказкой `is_same`.
- Я-9a. Операторы привязаны к стандартным интерфейсам (`Add`, `Subtract`, `Multiply`, `Divide`, `Equal`, `Order`, `Hash`). Пользовательский тип реализует их только явно через `extend`; переопределение существующих реализаций запрещено. `item in collection` вызывает `collection.contains(item)`.
- Я-9b. Эффекты функций в сигнатуре не объявляются. Компилятор выводит их из графа вызовов и показывает в `unio symbol` и `unio doc` (К-11). Слово `uses` зарезервировано.

### 3.3 Изменяемость

- Я-10. `let` неизменяемо, `var` изменяемо. Повторное присваивание `let` — ошибка компиляции.
- Я-11. Значение меняется только через место, которое начинается с `var`-имени или `var`-параметра, а поле структуры меняется, только если объявлено `var`: `tasks[index].done = true`. Имена, введённые `let`, образцами (`case some(task)`) и `for`, неизменяемы. Изменяющие методы коллекций доступны только на таких местах. Функция изменяет аргумент только через параметр, объявленный `var`; вызывающий передаёт `var`-переменную, и одну переменную нельзя передать в два `var`-параметра одного вызова.
- Я-11a. Структуры, перечисления, коллекции и текст — значения: связывание, передача, возврат и сохранение никогда не делят изменяемое состояние, поэтому изменение через одно имя не видно через другое. Анонимные функции захватывают значения в момент создания и не могут присваивать захваченным переменным. Ресурсы — не значения: у них есть тождественность (Я-9), они никогда не копируются.
- Я-11b. Значения разделяются, пока не изменены. Изменение разделённого значения копирует только изменяемый уровень, вложенные значения остаются общими; изменение неразделённого значения выполняется на месте, добавление в неразделённый список занимает амортизированно постоянное время. Стоимость копий измеряется набором тестов производительности (раздел 7.1).

### 3.4 Ошибки и отсутствие значений

- Я-12. `Option[T]` с `some`/`none`, операторы `or` и `?.`.
- Я-13. `error` объявляет тип ошибки. `fails with` перечисляет ошибки функции и входит в её тип.
- Я-14. Вызов функции с `fails with` без `try` — ошибка компиляции в любой позиции: в инструкции, в инициализаторе, в аргументе, в субъекте `match`. `try` в форме префикса пробрасывает; `try:` с `on` обрабатывает; `try ... on E as e:` обрабатывает одну ошибку в строке. Такой вызов никогда не превращается в `Result` неявно.
- Я-14a. Блок строчного обработчика `try ... on E as e:` не может завершиться обычным образом: он заканчивается `return`, `fail`, `break`, `continue` или вызовом функции, которая не возвращает управление (`assert_fail`). Поэтому значение выражения — всегда успешный результат.
- Я-15. Компилятор проверяет полноту обработки: каждая ошибка либо обработана, либо указана в `fails with` текущей функции. `on Error` обрабатывает любую.
- Я-16. `Result[T, E]` — обычный `enum` с вариантами `ok(value)` и `error(value)`. Значение `Result` существует только там, где функция объявляет `returns Result[T, E]` или значение построено явно. `match` разбирает его; `try` пробрасывает или обрабатывает `E` так же, как для вызова с `fails with E`. Неявного преобразования нет ни в одну сторону.
- Я-17. Аварии: индекс вне диапазона, деление на ноль, переполнение `Int`, нарушение `assert`, `assert_fail`. Поведение — управляемое завершение (раздел 4.5): диагностика с трассой стека в stderr, освобождение ресурсов в `using`, код выхода 101. Аварию нельзя обработать через `on`.
- Я-17a. Исчерпание памяти (кучи или стека) — не авария: оно вызывает экстренное завершение с кодом 102 (раздел 4.5), при котором пользовательский код, включая `release`, не выполняется.
- Я-18. Для каждой аварийной операции в стандартной библиотеке есть безопасная форма с `Option` или ошибкой.

### 3.5 Память и ресурсы

- Я-19. Управляемые значения живут под GC. Программа не может получить адрес значения.
- Я-20. Интерфейс `Resource` с методом `release`. Значение-ресурс создаётся в `using` или как поле другого ресурса; сохранение ресурса в обычную структуру, переживающую блок, — ошибка компиляции.
- Я-21. Освобождение в `using` происходит при нормальном выходе, при ошибке и при аварии, в обратном порядке создания. При экстренном и внештатном завершении (раздел 4.5) освобождение не выполняется; гарантии для файлов в этих случаях дают только атомарные записи (Б-9).

### 3.6 Модули и видимость

- Я-22. Модуль — файл; пакет — каталог с `unio.toml`. Импорт: `import a.b`, `import a.b as c`, `from a.b import x, y`. Имя, начинающееся с `std.`, обозначает стандартную библиотеку; любое другое — модуль того же пакета, `a.b` — файл `a/b.unio` относительно корня пакета.
- Я-23. Всё приватно по умолчанию; `public` экспортирует.
- Я-24. Циклические импорты — ошибка компиляции с указанием цикла.

### 3.7 Тесты в языке

- Я-25. Блок `test "описание":` на верхнем уровне файла. Доступны `assert`, `assert_fail`, `expect_fault`. Тесты не попадают в сборку `build`.

## 4. Требования к компилятору и среде выполнения

### 4.1 Компилятор

- К-1. Этапы: лексер, парсер, разрешение имён, проверка типов и ошибок, проверка ресурсов, генерация кода. Каждый этап имеет отдельный набор тестов.
- К-2. Компилятор восстанавливается после ошибки и сообщает все ошибки файла за один проход, не только первую.
- К-3. `unio check` выполняет все проверки без генерации кода.
- К-4. Сборка детерминирована: одинаковые исходники и lock-файл дают побайтно одинаковый артефакт на одной платформе.
- К-5. Результат `unio build` — один исполняемый файл без внешних зависимостей, кроме системных библиотек.

### 4.2 Диагностика

- К-6. Каждая диагностика имеет уникальный код вида `E0001` (ошибка), `W0001` (предупреждение), `H0001` (подсказка стиля).
- К-7. Текстовый формат: код, путь, строка и столбец, фрагмент с подчёркиванием, сообщение, подсказка.
- К-8. Формат `--diagnostics=json`: массив объектов, каждый с полями `code`, `severity`, `message`, `explanation`, `spans` (файл, начало, конец, подпись), `fixes` (массив замен: файл, диапазон, новый текст, описание), `related` (символы и места). Схема публикуется как JSON Schema и версионируется.
- К-9. `unio explain E0001` печатает развёрнутое объяснение с примером ошибки и исправления.
- К-10. Сообщения на русском и английском языках; язык выбирается параметром и переменной окружения. Коды и схема JSON не зависят от языка.

### 4.3 Контекст символов

- К-11. `unio symbol <полное имя>` возвращает (текст и JSON): сигнатуру, документацию, место объявления, список использований, для функций — набор ошибок, выведенные эффекты (`files`, `network`, `process`, `env`) и список вызываемых функций.
- К-12. `unio outline <файл>` возвращает список объявлений файла с сигнатурами.

### 4.4 Среда выполнения

- К-13. GC точный, трассирующий, неперемещающий. Паузы и пропускная способность измеряются в наборе тестов производительности.
- К-14. Трасса стека при аварии содержит имена функций, файлы и строки без отладочных символов внешних форматов.
- К-15. Коды завершения: 0 успех; иначе значение `main` в диапазоне 0–100; 101 авария; 102 исчерпание памяти (кучи или стека); 103 не удалось применить песочницу или политику (раздел 4.6). Коды 104–127 зарезервированы за средой выполнения. Значение `main` вне 0–100 — авария.

### 4.5 Модель завершения

- К-16. Нормальное завершение: `main` возвращает значение. Буферизованный вывод записан, ресурсы уже освобождены своими блоками `using`.
- К-17. Управляемое завершение (авария, код 101): пользовательский код останавливается в точке аварии; среда выполнения печатает диагностику и трассу стека, раскручивает стек и вызывает `release` для всех открытых `using` в обратном порядке. `release` выполняется с резервом памяти, выделенным при запуске. Авария или ошибка внутри `release` при завершении сообщается, остальные ресурсы всё равно освобождаются; код выхода остаётся 101.
- К-18. Экстренное завершение (код 102): куча исчерпана сверх резерва, превышен лимит кучи из политики или переполнен стек. Среда выполнения пишет заранее подготовленную диагностику в stderr и завершается без выполнения пользовательского кода. Дескрипторы закрывает операционная система; данные в буферах программы теряются.
- К-19. Внештатное завершение: сигнал уничтожения, отключение питания, падение внешнего кода, сбой операционной системы. Среда выполнения гарантий не даёт; остаются только гарантии операционной системы и атомарных записей (Б-9).
- К-20. Документация перечисляет для каждого вида завершения, какие гарантии действуют для ресурсов, стандартного вывода и файлов. Запись через открытый дескриптор без `open_atomic` не считается безопасной: после экстренного или внештатного завершения её содержимое может оборваться в любом месте.

### 4.6 Песочница

- ПС-1. Каждая программа, запущенная через `unio run`, `unio test` или как собранный исполняемый файл, работает в песочнице. Среда выполнения применяет ограничения средствами операционной системы до `main`; программа не может снять их позже, дочерние процессы их наследуют.
- ПС-2. Действующие полномочия — пересечение полномочий манифеста (И-6) и внешней политики (ПС-3). Без объявленных полномочий программа может только читать свои аргументы и стандартный ввод и писать в стандартный вывод и поток ошибок.
- ПС-3. Внешняя политика — файл, который задаёт оператор через `--policy <файл>` или переменную окружения `UNIO_POLICY`. Она может только сузить полномочия манифеста и задаёт лимиты: размер кучи, время работы, процессорное время, число процессов, размер записываемых файлов. Лишние полномочия в политике не действуют и дают предупреждение. Если политику нельзя прочитать или разобрать, запуск прекращается с кодом 103.
- ПС-4. Механизмы: Linux — Landlock для файловой системы, seccomp-bpf для системных вызовов, `no_new_privs`, лимиты ресурсов; macOS — профиль Seatbelt и лимиты ресурсов; Windows — AppContainer и Job Object. Выбор подтверждается прототипами на этапе 4 плана; требование — результат, проверяемый по ПС-8.
- ПС-5. Песочница закрывается при отказе: если в операционной системе нет нужного механизма, программа не запускается (код 103). Разрешить более слабую песочницу может только оператор — флагом `--allow-weaker-sandbox` или `allow_weaker = true` в политике; тогда среда выполнения печатает, каких ограничений не хватает. Сама программа этого сделать не может.
- ПС-6. Операция, заблокированная песочницей, завершается ошибкой, которую функция стандартной библиотеки уже объявляет (например, `IoError` вида `PermissionDenied` с названием отклонённого полномочия), а не аварией. Безопасный код обращается к операционной системе только через стандартную библиотеку.
- ПС-7. Проверка при компиляции сохраняется: использование модуля стандартной библиотеки вне объявленных полномочий — ошибка компиляции, выведенные эффекты показываются в `unio symbol`. Песочница — вторая линия защиты, а не замена.
- ПС-8. Набор тестовых программ, которые пытаются выполнить запрещённые действия через каждый модуль стандартной библиотеки и через дочерние процессы, выполняется на всех четырёх платформах; каждая попытка должна быть отклонена.
- ПС-9. Документация называет пределы песочницы: она не защищает от уязвимостей ядра и побочных каналов, а также от злоупотребления выданными полномочиями. Для кода, созданного ИИ, рекомендуются минимальный манифест, внешняя политика с лимитами и отдельный пользователь, контейнер или виртуальная машина для недоверенного кода.

## 5. Требования к стандартной библиотеке

- Б-1. Модули: `std.text`, `std.collections`, `std.math`, `std.decimal`, `std.files`, `std.path`, `std.env`, `std.args`, `std.process`, `std.json`, `std.time`, `std.random`, `std.log`, `std.test`.
- Б-1a. `std.decimal.Decimal` — точная десятичная арифметика, реализует все операторные интерфейсы и `Hash`; создаётся из текста и `Int`, преобразование из `Float` только явное с указанием округления.
- Б-2. Каждая функция, способная завершиться ошибкой, объявляет конкретные типы ошибок; `fails with Error` в стандартной библиотеке запрещён.
- Б-3. Каждый модуль документирован; у каждой публичной функции есть пример.
- Б-4. `std.args`: позиционные аргументы, флаги, значения по умолчанию, автоматическая справка.
- Б-5. `std.json`: разбор в значение, кодирование и декодирование структур по их объявлению, без аннотаций.
- Б-6. `std.process`: запуск программы с аргументами, захват вывода, код выхода, таймаут.
- Б-7. Небезопасный код (`external function`) допускается только в стандартной библиотеке и проходит отдельную проверку надёжности (раздел 7.3).
- Б-8. Каждая операция стандартной библиотеки, заблокированная песочницей, сообщает об этом через объявленный тип ошибки (ПС-6). Функция, которая сообщает об отсутствии вместо ошибки (`files.exists`, `env.get`), сообщает о заблокированном объекте как об отсутствующем.
- Б-9. Атомарная запись в `std.files`: `write_text` и `write_bytes` заменяют целевой файл через временный файл в том же каталоге и последующее переименование, поэтому читатель видит либо старое, либо новое полное содержимое при любом виде завершения. Параметр `durable = true` дополнительно сбрасывает файл и каталог на носитель. `open_atomic(path)` возвращает ресурс, содержимое которого заменяет целевой файл только при вызове `commit()`. Освобождение без фиксации — при ошибке, при аварии или потому, что блок закончился без неё, — удаляет временный файл и оставляет целевой без изменений. Фиксация явная, потому что `release` не знает, как завершился её блок. После экстренного или внештатного завершения может остаться временный файл с именем `.<имя>.unio-tmp-<id>`; он никогда не заменяет целевой.
- Б-10. Стандартная библиотека пишется на Unio в `stdlib/std/`. Всё, что язык может выразить, реализуется на нём; только примитивы операционной системы и среды выполнения объявляются как `external function` в файлах `unsafe module`. Эти исходники — нормативный API; эталонные программы используют только его, что проверяет `spec/check_api.py`.

## 6. Требования к инструментам

### 6.1 Команды

| Команда | Назначение | Обязательные параметры |
|---|---|---|
| `unio new <имя>` | Создать пакет с манифестом и примером | `--lib`, `--bin` |
| `unio build` | Собрать исполняемый файл | `--release`, `--target` |
| `unio run` | Собрать и запустить | аргументы после `--`, `--policy` |
| `unio check` | Проверить без сборки | `--diagnostics=json` |
| `unio fmt` | Отформатировать | `--check` для CI |
| `unio test` | Запустить тесты | `--json`, фильтр по имени, `--policy` |
| `unio add/remove/update` | Управлять зависимостями | версия, `--unsafe-ok` |
| `unio doc` | Собрать документацию пакета | `--open` |
| `unio symbol`, `unio outline`, `unio explain` | Контекст для человека и ИИ | `--json` |

### 6.2 Форматтер

- И-1. Один стиль без настроек. Результат форматирования идемпотентен.
- И-2. Форматтер сохраняет комментарии и не меняет семантику; это проверяется тестом «AST до = AST после».
- И-3. Время форматирования файла в 1000 строк — не более 50 мс.

### 6.3 Тестирование

- И-4. Тесты из блоков `test` запускаются изолированно, результат в текстовом и JSON виде с именем, статусом, временем, выводом.
- И-5. Тесты могут проверять аварии через `expect_fault`.

### 6.4 Пакеты

- И-6. Манифест `unio.toml`: имя, версия (семантическая), зависимости, полномочия, список `unsafe module`. Полномочия имеют области: `files.read` и `files.write` — списки путей с подстановками `$HOME`, `$CWD`, `$TEMP` и суффиксом `/**` для поддерева; `env` — список имён переменных; `process` — список программ; `network` в 0.1 равно `false`. Пример:

```toml
[permissions]
files.read = ["$HOME/.todo.json"]
files.write = ["$HOME/.todo.json"]
env = ["TODO_FILE", "HOME"]
```
- И-7. `unio.lock` содержит версии и хеши содержимого всех зависимостей. Сборка с lock-файлом не обращается к сети.
- И-8. Реестр: публикация с подписью, проверка подписи при установке, запрет удаления опубликованных версий.
- И-9. Установка зависимости с `unsafe module` или полномочиями шире, чем у пакета, требует явного подтверждения.

### 6.5 Редактор

- И-10. Языковой сервер по протоколу LSP: диагностика, переход к объявлению, подсказки типов, автодополнение, форматирование, переименование.
- И-11. Расширение для VS Code с подсветкой и запуском тестов.

## 7. Нефункциональные требования

### 7.1 Производительность

Измеряется набором из эталонных утилит (раздел 9) на Linux x86-64; результаты публикуются с каждым выпуском.

| Показатель | Требование |
|---|---|
| `unio check` для пакета в 10 000 строк | не более 1 с |
| Полная сборка пакета в 10 000 строк (`--release`) | не более 30 с |
| Время запуска пустой программы | не более 5 мс |
| Обработка текста и JSON | не медленнее CPython 3.13 более чем в 0,5 раза, цель — быстрее в 3 раза |
| Пауза GC при куче 100 МБ | не более 10 мс (95-й перцентиль) |

Универсальная скорость C не обещается и не измеряется как требование.

### 7.2 Надёжность

- Н-1. Компилятор не аварийно завершается ни на каком входе: проверяется fuzzing-тестами не менее 24 часов перед выпуском.
- Н-2. При исчерпании памяти среда выполнения завершает программу с кодом 102 и заранее подготовленной диагностикой. Файлы, записанные атомарными операциями Б-9, сохраняют либо старое, либо новое полное содержимое; проверяется тестами, которые исчерпывают память и уничтожают процесс во время записи, на каждой платформе. Других гарантий для файлов нет.
- Н-3. Авария внутри `using` освобождает все ресурсы; проверяется тестами на каждой платформе.

### 7.3 Безопасность

- Н-4. Пользовательский код не может обойти проверки границ, типов и ресурсов.
- Н-5. Весь `external function` код стандартной библиотеки проходит ревью двух человек и тесты с санитайзерами памяти.
- Н-6. Сборка выпуска воспроизводима, артефакты подписаны, публикуется SBOM.
- Н-7. Компилятор и менеджер пакетов не выполняют код зависимостей во время сборки.
- Н-7a. Песочница (раздел 4.6) проходит набор ПС-8 на каждой платформе; выпуск с непройденным тестом ПС-8 не публикуется.

### 7.4 Совместимость и платформы

- Н-8. Платформы: Linux x86-64, Linux arm64, macOS arm64, Windows x86-64. Все тесты проходят на всех платформах в CI.
- Н-9. В пределах 0.x возможны несовместимые изменения языка; каждое сопровождается автоматической миграцией в `unio fmt --migrate` либо диагностикой с исправлением.

### 7.5 Удобство для ИИ

- Н-10. Контрольный набор из 200 программ с внесёнными ошибками (типы, ошибки, ресурсы, стиль). Критерий: агент, получающий только JSON-диагностику, исправляет не менее 80 % за не более чем три итерации.
- Н-11. Средняя длина сообщения диагностики — не более 200 символов; объяснение — отдельно.

## 8. Требования к документации

- Д-1. Справочник языка: грамматика в EBNF, семантика каждой конструкции, список кодов диагностики.
- Д-2. Руководство: от установки до публикации пакета, на примере `todo`.
- Д-3. Справочник стандартной библиотеки, генерируемый из документирующих комментариев.
- Д-4. Документ «Как Unio работает с ИИ»: форматы JSON, рекомендуемый цикл, примеры промптов.
- Д-5. Документация на русском и английском языках.

## 9. Приёмка

### 9.1 Эталонные утилиты

Десять программ, покрывающих ядро и стандартную библиотеку; хранятся в репозитории и служат тестами, бенчмарками и материалом для контрольного чтения:

1. `todo` — список задач (пример из концепции).
2. `wc` — подсчёт строк, слов, байтов.
3. `grep-lite` — поиск по шаблону в файлах.
4. `json-query` — выборка из JSON по пути.
5. `rename` — массовое переименование файлов.
6. `env-check` — проверка окружения и версий программ.
7. `csv-sum` — агрегация столбцов CSV.
8. `backup` — копирование каталога с фильтрами.
9. `log-tail` — чтение и фильтрация журналов.
10. `release-notes` — генерация заметок к выпуску из истории git через `std.process`.

### 9.2 Порядок приёмки

1. Все тесты компилятора, среды выполнения, библиотеки и инструментов проходят на четырёх платформах.
2. Эталонные утилиты собираются, тесты проходят, результаты производительности соответствуют 7.1.
3. Проведены испытания из 1.4 (читаемость, исправление ошибок ИИ) с опубликованной методикой.
4. Fuzzing по Н-1 выполнен, найденные дефекты устранены.
5. Документация по разделу 8 опубликована.

## 10. Ограничения и допущения

- Язык реализации компилятора 0.1 — Rust; генерация кода через Cranelift. Переход на LLVM или самостоятельную реализацию рассматривается после 0.1.
- Всё, что не обязано существовать до того, как язык заработает, пишется на Unio: стандартная библиотека (Б-10), эталонные утилиты и инструменты проекта в `tools/`. Проверяющие скрипты на Python в `spec/` и `.github/scripts/` — временная опора для CI; они удаляются, когда интерпретатор этапа 3 начнёт выполнять их версии на Unio.
- Решения по языку принимаются через RFC в `docs/rfcs/`; ТЗ обновляется при принятии RFC.
- Вопросы, открытые в первой версии концепции, закрыты в `docs/concept.md`, разделы 10–11. Их пересмотр возможен только через RFC.

# Файлы спецификации Unio

Версия 0.1-draft. Английская версия (основная): [spec/README.md](../../spec/README.md).

| Файл | Содержание |
|---|---|
| [grammar.ebnf](../../spec/grammar.ebnf) | Грамматика ядра: лексика, объявления, инструкции, выражения, образцы, типы |
| [check_grammar.py](../../spec/check_grammar.py) | Эталонный проверяющий скрипт: читает `grammar.ebnf` напрямую и разбирает по нему программы |
| [tests/valid/](../../spec/tests/valid) | Программы, которые должны разбираться; по одному файлу на область грамматики |
| [tests/invalid/](../../spec/tests/invalid) | Программы, которые должны давать ошибку на строке и с кодом, указанными в первой строке файла |

Эталонные программы — [docs/examples/todo.unio](../examples/todo.unio) и утилиты в [examples/](../../examples). Они, стандартная библиотека в [stdlib/](../../stdlib) и инструменты в [tools/](../../tools) проверяются той же грамматикой; [check_api.py](../../spec/check_api.py) проверяет, что они вызывают только объявленное в стандартной библиотеке.

CI выполняет версии этих скриптов на Unio из [tools/](../../tools) интерпретатором спринта S5. Скрипты на Python остаются в репозитории как эталон: задание CI «Unio tools agree with the Python checkers» (`compiler/unio/tests/tools.rs`) проверяет, что оба дают одинаковый вывод и код завершения, и они служат для сравнения производительности ([bench/README.md](../../bench/README.md)). Изменение поведения проверки меняет обе версии.

## Как пользоваться проверкой

Нужен только Python 3.9 или новее.

```sh
python3 spec/check_grammar.py --self-check                # согласованность грамматики
python3 spec/check_grammar.py --corpus                    # spec/tests
python3 spec/check_grammar.py docs/examples/todo.unio examples/*.unio
python3 spec/check_grammar.py --tree examples/wc.unio      # дерево разбора
```

`--self-check` проверяет, что каждое используемое правило определено и достижимо из `file`, а терминалы правил совпадают со списками ключевых слов и знаков в разделе L грамматики.

Грамматика читается как упорядоченный выбор: альтернативы пробуются в записанном порядке, берётся первая подошедшая. EBNF записана так, чтобы такое чтение давало задуманный разбор; изменение, которое это нарушает, обнаружит корпус.

## Что фиксирует грамматика, а что остаётся проверкам компилятора

Грамматика решает, корректен ли файл синтаксически. Правила, которые EBNF выразить не может, записаны в комментариях рядом с ограничиваемыми правилами и проверяются компилятором, а не `check_grammar.py`:

- обобщённые аргументы или индекс после выражения (правило `generic_call`; это правило скрипт реализует);
- не больше одного строчного обработчика в инструкции, и только в её конце (E0024);
- цель присваивания заканчивается именем, полем или индексом (E0030);
- позиционные аргументы идут раньше именованных (E0023);
- не больше одного остаточного элемента в образце списка, и только последним (E0034).

Разрешение имён, типы, наборы ошибок, полноту `match`, изменяемость и ресурсы проверяет `unio check` ([semantics.md](semantics.md)); их корпус — [tests/semantic/](../../spec/tests/semantic), который проверяет только компилятор.

## Коды диагностики уровня синтаксиса

Эти коды зафиксированы грамматикой. Каждый код компилятора с объяснением, примером ошибки и исправленным примером есть в каталоге диагностик (`compiler/unio/src/catalog.rs`, его показывает `unio explain CODE`); семантические коды перечислены в [semantics.md](semantics.md).

| Код | Значение |
|---|---|
| E0001 | Табуляция в отступе |
| E0002 | Отступ не кратен 4 пробелам |
| E0003 | Отступ вырос больше чем на уровень или после строки, которая не заканчивается `:` |
| E0005 | Незакрытый текстовый литерал |
| E0006 | Недопустимая escape-последовательность в тексте |
| E0007 | Недопустимый символ |
| E0008 | Недопустимый числовой литерал |
| E0009 | Незакрытая скобка |
| E0010 | Закрывающая скобка без парной открывающей |
| E0011 | Пустая или незакрытая интерполяция либо `}` в тексте без `\` |
| E0012 | Неожиданный токен; сообщение называет, что грамматика ожидает в этом месте (фронтенд компилятора) |
| E0013 | Слишком глубокая вложенность (больше 64 уровней выражений, образцов, типов, блоков или интерполяций) |
| E0020 | Цепочка сравнений вида `a < b < c` |
| E0023 | Позиционный аргумент после именованного |
| E0024 | Больше одного строчного обработчика в инструкции или обработчик не в её конце |
| E0030 | Недопустимая цель присваивания |
| E0032 | Слово, зарезервированное для следующих выпусков (`uses`) |
| E0034 | Остаточный элемент `name...` не последний или их больше одного |

E0004 не используется: раз отступ растёт по одному уровню, при выполненном E0002 уменьшение отступа всегда возвращает на открытый уровень.

## Соглашения корпуса

- Файл в `tests/valid/` должен разбираться полностью.
- Файл в `tests/invalid/` начинается с `# expect-error: СТРОКА` или `# expect-error: СТРОКА КОД`. Скрипт должен сообщить первую ошибку на этой строке и с этим кодом, если он указан. Коды скрипт выдаёт только для лексических ошибок; остальные синтаксические ошибки обозначаются как `syntax`.
- Один файл проверяет одно. Новое правило грамматики добавляется вместе хотя бы с одним корректным и одним некорректным файлом.

## RFC 0001

EBNF поддерживает контекстный `named` и имена в формах функций; `named_parameters.unio` и негативные примеры входят в корпус. Оба API-checker извлекают настоящее имя параметра. Порядок групп/умолчаний, обязательность имени при вызове и диагностики E0040–E0044 проверяет компилятор, а не эти скрипты; E0045–E0048 в каталоге компилятора пока нет ([status.md](status.md)). Нормативные правила: [контракты](language-contracts.md), [RFC](rfcs/0001-language-contracts.md).

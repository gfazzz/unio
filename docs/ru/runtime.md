# Динамическая семантика и среда выполнения Unio 0.1

Версия 0.1-draft. Английская версия (основная): [../runtime.md](../runtime.md). Основание: разделы 2–4 концепции, требования Я-10–Я-21, К-13–К-20, Б-9–Б-12, SB-1, И-4, И-5a; [semantics.md](semantics.md) — то, что проверяется до запуска программы. Этот документ — справочник для интерпретатора спринта S5 и нативной среды выполнения спринта S6.

Программа, дошедшая до среды выполнения, прошла `unio check`: имена разрешены, типы согласованы, ошибки обработаны, ресурсы остаются в своих блоках. Поэтому среда выполнения проверяет только то, что нельзя знать до выполнения: аварии, исчерпание ресурсов и внешний мир.

## 1. Вычисление

1. Вычисление строгое и идёт слева направо: операнды оператора, аргументы вызова, поля при построении структуры, элементы литерала списка или словаря и части текста с интерполяциями вычисляются в порядке записи.
2. `and` и `or` вычисляют правый операнд, только когда он определяет результат; `a or b` для `Option` вычисляет `b` только для `none`. `x if c else y` вычисляет `c`, затем одну ветку.
3. Значение параметра по умолчанию вычисляется при каждом вызове, который опускает аргумент, после предшествующих аргументов, и может использовать параметры перед ним.
4. Цикл `for` вычисляет коллекцию один раз до первой итерации; изменение исходной переменной внутри цикла не меняет итерацию, потому что цикл держит значение, с которого начал.
5. Генератор `[e for x in c if g]` вычисляет `c` один раз, затем `g` и `e` для каждого элемента по порядку.

## 2. Значения

1. `Int` — 64-битное целое в дополнительном коде; переполнение `+`, `-`, `*`, `**`, деление на ноль и `%` на ноль — аварии (Я-17). `/` округляет к нулю, а `%` имеет знак левого операнда.
2. `Float` — IEEE 754 binary64 с округлением к ближайшему чётному; ни одна операция над `Float` не вызывает аварию.
3. `Text` — неизменяемая последовательность скалярных значений Unicode, хранимая в UTF-8 с индексом позиций символов, поэтому `length`, `slice` и `char_at` выполняются за постоянное время.
4. Структуры, перечисления, кортежи, списки, словари, множества, `Bytes` и тексты — значения (Я-11a). Значение разделяется между именами, пока не изменено; изменение разделённого значения сначала копирует меняющийся уровень, а изменение неразделённого выполняется на месте (Я-11b). Словарь и множество перебираются в порядке первого добавления ключей, а хеширование не зависит от запуска, поэтому вывод программы одинаков при каждом запуске.
5. Значения-функции захватывают значения используемых имён в момент создания (Я-11a).
6. Ресурс — не значение: у него есть тождественность, он никогда не копируется, а его `release` выполняется ровно один раз (раздел 5).

## 3. Память

1. Поскольку значения никогда не делят изменяемое состояние, а замыкания захватывают копии, значение никогда не может ссылаться само на себя: циклов ссылок нет. Поэтому интерпретатор S5 и исполняемые файлы S6 управляют памятью подсчётом ссылок, который освобождает значение, когда исчезает его последнее имя, и заодно сообщает правилу копирования при изменении, разделено ли значение.
2. Требование К-13 — подсчёт ссылок (RFC 0007, принят 2026-11-12, вместо точного, трассирующего, неперемещающего сборщика). Подсчёт ссылок точен и не перемещает данные, никогда не просматривает память, которая остаётся живой, и не нуждается в трассировке, потому что циклы невозможны. Его пауза — освобождение того, что программа отпускает, пропорциональное ему: около 0,4–0,6 мс на МБ на Linux x86-64 (`bench/free/`, `bench/README.md`), с границей 1 мс на МБ в 7.1. Освобождение не уходит в рекурсию на глубину структуры: каждый объект, который держит значения, передаёт содержимое функции `release` (`compiler/unio-runtime/src/value.rs`), а она освобождает его рекурсией до 128 уровней вложенности, а глубже — через список, который опустошает цикл кадра на 128-м уровне, так что машинный стек ограничен при любой глубине (раньше цепочка вложенных списков аварийно завершала процесс переполнением стека на 120 000–160 000 уровней при стеке 8 МиБ). Освобождение остаётся немедленным: цикл заканчивается до возврата внешнего освобождения, и счёт кучи точен. Рекурсивными остаются два пути: цепочка функциональных значений, каждое из которых захватывает предыдущее, освобождается по уровню замыкания на шаг рекурсии, а ключ словаря или множества хешируется рекурсией при вставке, так что глубоко вложенный ключ исчерпывает стек при вставке, раньше чем его можно освободить.
3. Среда выполнения считает удерживаемую память, включая резерв для `release` (пункт 6). Когда она превышает лимит кучи из политики (`limits.heap_bytes`, SB-3a) или память, которую выделяет система, программа завершается с кодом 102 (К-18). Рекурсия глубже лимита стека тоже завершает программу с кодом 102.
4. **Бюджет до выделения.** Там, где размер выделения задаёт программа, среда выполнения проверяет лимит кучи до выделения и резервирует память выделением с возможностью отказа (`try_reserve`), чтобы отказ системы выделить память был тем же исчерпанием с кодом 102, а не аварийным прерыванием процесса: буфер `FileReader.read_bytes` (`max_bytes`), `read_text` и `read_bytes` (размер файла), вывод, который захватывает `process.run`, и `Text.repeat`. Так же до выделения проверяется временная память файловых операций `std.files`: копии, которые операция делает из длинного пути (системный путь, его разрешение, текст системного вызова, запрос процессу записи; копии пути обычной длины, всего до 32 КиБ, — постоянные расходы, как буфер порции чтения), имена, которые `list_directory` держит до построения списка, и для файла, размер которого система не сообщает (канал), буфер, растущий по мере чтения, вместе с копией, которую делает рост; `AtomicFile.write_bytes` записывает байты, которые держит программа, не копируя их. Остальные значения растут по шагам и проверяются после каждого шага. Сообщение кода 102 подготовлено заранее и пишется без выделения памяти.
5. **Что гарантировать нельзя.** Среда выполнения видит выделения, которые делает сама, и отказы распределителя памяти. Она не видит память, которую система пообещала, но не может предоставить: при overcommit (по умолчанию в Linux) выделение может пройти, а затем процесс завершит OOM killer системы — без кода 102 и его диагностики; вне пути аварии, который обслуживает резерв (пункт 6), небольшое выделение, которое не удалось внутри стандартной библиотеки Rust, по-прежнему прерывает процесс. Подсчитанные размеры — оценки ёмкости (`compiler/unio-runtime/src/heap.rs`), а не точные цифры распределителя. Поэтому надёжный путь к коду 102 — лимит кучи в политике; лимит операционной системы (`ulimit -v`, cgroup) останавливает процесс снаружи.
6. **Резерв для `release` (К-17).** До `main`, до каждого теста `unio test` и в исполняемом файле `unio build` среда выполнения откладывает резерв в 1 МиБ (1 048 576 байт): он выделен, каждая его страница записана, чтобы система её действительно предоставила, и он учтён в куче. Резерв входит в `limits.heap_bytes`, а не добавляется сверху: программе доступен лимит за вычетом резерва. Политика, у которой `limits.heap_bytes` меньше 2 МиБ (2 097 152 байт), отклоняется до `main` с кодом 103 и диагностикой, где названы лимит, минимум и резерв.
   - Резерв открывается только при аварии (код 101) — в момент создания аварии, до выделения её сообщения и трассы, чтобы полная куча не завершила программу кодом 102 раньше, чем начнётся путь освобождения. С этого момента каждое выделение потока программы берётся из отложенных страниц: глобальный распределитель среды выполнения (`compiler/unio-runtime/src/reserve.rs`) выдаёт блоки резерва, не обращаясь к системе. С этого момента путь ограничивает резерв, а не лимит кучи: путь продолжается, пока в резерве есть место, в том числе на полной куче, и завершается кодом 102, когда ему нужно больше, — независимо от того, задаёт ли политика лимит кучи и есть ли в куче место. Резерв обслуживает сообщение и трассу (16 байт на кадр), раскрутку и вызовы `release` открытых блоков `using` (раздел 5). Диагностика пишется в стандартный поток ошибок построчно, поэтому её текст не требует памяти при любой длине трассы.
   - Выделение на этом пути, которое не помещается в резерв, — исчерпание. Распределитель памяти не может раскручивать стек, поэтому блок берётся у системы, а резерв до своего закрытия считается переполненным; ближайшая проверка кучи — не позже конца переполнившего резерв `release` — завершает программу кодом 102 с заранее подготовленной диагностикой, а буфер, размер которого задаёт программа (пункт 4), отклоняется до выделения, если не помещается. От кучи это не зависит: с лимитом кучи и полной кучей, с лимитом и свободным местом в куче и без лимита кучи в политике, когда система выделила бы память, результат один и тот же. Отметка сохраняется, если блок освобождён до любой проверки, поэтому `release`, который строит большой текст и сразу его отбрасывает, или много мелких блоков, в сумме больших резерва, завершается кодом 102 так же, как `release`, который их сохраняет. Оставшиеся освобождения пропускаются: файл `open_atomic` сохраняет свой временный файл, а цель остаётся неизменной (Б-9). Поэтому программе, чьему `release` на пути аварии нужно больше резерва, следует освобождать там меньше: бюджет этого пути — резерв, а не куча.
   - Исчерпание (код 102) резерв никогда не открывает, и пользовательский код после него не выполняется (К-18). `expect_fault`, получив свою аварию, снова закрывает резерв, и тест продолжается с прежним бюджетом. Память, которая не принадлежит программе, берётся вне резерва, как она и не учитывается в куче: захваченный вывод теста в `unio test` и отчёт о его результате.
   - Тестовый хук заполняет кучу точно: при лимите кучи переменная окружения `UNIO_TEST_HEAP_FREE=N` до `main` считает кучу полной, кроме `N` байт (`fill_to` в `compiler/unio-runtime/src/heap.rs`, как `fail_point` из Б-9b). Он не держит память и может только уменьшить бюджет программы.
7. **Параметры резерва и их измерения.** Резерв в 1 МиБ и минимальный лимит кучи в 2 МиБ — начальные параметры 0.1, инженерный бюджет (раздел 12 плана, условие закрытия 1). Тест `the_reserve_peak_is_measured` (`compiler/unio/src/interp.rs`) выполняет измеряемые случаи на куче, заполненной тестовым хуком до лимита, чтобы весь путь шёл из резерва, и сообщает наивысшую точку, которой путь достиг в резерве, из 1 048 320 доступных байт (резерв без 256 байт его служебных данных). Измерено на Linux x86-64:

   | Случай | Пик, байт | Доля | Запас, байт |
   |---|---:|---:|---:|
   | Глубокая раскрутка: блок `using` в каждом из 9 000 вложенных вызовов, каждый `release` строит 20 текстов и обрабатывает ошибку | 156 336 | 14,9% | 891 984 |
   | Повторные аварии: тот же стек, десять самых внутренних вызовов `release` по очереди падают после обработки ошибки, каждый с трассой около 9 000 кадров | 300 448 | 28,7% | 747 872 |
   | Диагностика с длинной трассой: авария на глубине 9 990 вызовов, с длинным именем функции и путём файла (2 МБ текста диагностики) | 159 952 | 15,3% | 888 368 |

   Все пики помещаются; наибольший оставляет 730 КиБ. Основную долю дают трассы: лимит стека — 10 000 кадров, поэтому одна трасса занимает не больше 160 КБ, а случай повторных аварий держит две одновременно — аварию программы и аварию `release`. Текст диагностики не учитывается, потому что пишется построчно. Поэтому параметры остаются прежними; тест падает, если последующее изменение выведет какой-либо пик за пределы резерва.

## 4. Ошибки и аварии

1. Функция с `fails with` завершается либо результатом, либо одной из своих ошибок. `try` передаёт ошибку дальше без изменений; `on E as e` её принимает; `fail e` завершает функцию с `e`. Ошибка — значение и никогда не уходит за функцию, которая её не перечисляет, что гарантирует проверка.
2. Авария (Я-17) останавливает программу в своей точке. Среда выполнения открывает резерв для `release` (раздел 3.6), записывает трассу из имён функций, файлов и строк (К-14), раскручивает стек, вызывает `release` каждого открытого блока `using` в обратном порядке (К-17), пишет диагностику и трассу в поток ошибок и завершается с кодом 101. Авария внутри `release` при раскрутке сообщается, а остальные ресурсы всё равно освобождаются; `release`, исчерпавший резерв, вместо этого завершает программу кодом 102 — с лимитом кучи или без него, — и оставшиеся освобождения пропускаются (К-18).
3. Аварию нельзя принять через `on`. `expect_fault(action)` в блоке `test` выполняет `action` и считается успешным, только если тот завершился аварией; ресурсы, открытые внутри `action`, освобождаются до возврата из `expect_fault`.
4. `assert c` и `assert_fail(m)` — аварии с текстом условия или сообщением.

## 5. Ресурсы

1. `using r = e:` вычисляет `e`, связывает `r` и выполняет блок. Когда блок заканчивается — обычным образом, через `return`, `break`, `continue`, ошибку или аварию, — выполняется `release` для `r`; несколько блоков `using` освобождаются в обратном порядке открытия.
2. `release` не может завершиться ошибкой: в его сигнатуре нет `fails with`, а ошибка внутри него — дело самого ресурса (например, `AtomicFile` игнорирует ошибки удаления временного файла).
3. При экстренном (код 102) и внештатном завершении `release` не выполняется (К-18, К-19). При аварии `release` выполняется из резерва, отложенного до `main` (раздел 3.6).

## 6. Программы и тесты

1. Программа начинается с `public function main()` модуля, переданного `unio run`. Без результата код выхода — 0; с результатом `Int` — это значение, которое должно лежать в 0–100, иначе это авария (К-15).
2. `unio test` выполняет каждый блок `test` указанных модулей, каждый в свежем состоянии; порядок блоков не важен, потому что глобального изменяемого состояния нет. Результат каждого теста — пройден, не пройден из-за аварии, которой он закончился, или не пройден из-за диагностик, мешающих его компиляции (И-5a), в тексте или JSON с именем, статусом, временем и выводом (И-4). Анализ эффектов `unio test` учитывает тесты, которые она выполняет, и только их (RFC 0005, «Тесты в анализе»): блоки `test` переданных модулей, выбранные фильтром, входят в программу, так что функциональные значения, которые они передают или записывают, становятся возможными целями вызовов программы, а их эффекты проверяются по манифесту (E0085 делает файл непрошедшим, и ни один его тест не выполняется). Тесты импортированных модулей и стандартной библиотеки не включаются, если их модули сами не переданы (`unio test stdlib/alloc/builtin/list.unio` выполняет и анализирует тесты библиотеки). `unio check` и `unio run` не включают ни одного теста. Включение тестов никогда не расширяет манифест или внешнюю политику: тело теста выполняется в песочнице, которая по-прежнему запрещает то, что они не разрешают.
3. Константы верхнего уровня вычисляются один раз, в порядке зависимостей, до `main` или до первого теста, которому они нужны; константа, вычисление которой вызвало аварию, завершает программу этой аварией.

## 7. Внешние функции

1. Стандартная библиотека объявляет 83 внешние функции, все в файлах `unsafe module` (Б-7, Б-10). Каждая связывается по полному имени, например `std.files.system_rename` или метод `Text.slice`, с функцией среды выполнения. Документирующий комментарий объявления — её спецификация.
2. Тест среды выполнения проверяет, что у каждого внешнего объявления есть привязка, а у каждой привязки — объявление, чтобы библиотека и среда выполнения не расходились.
3. Группы и нужный им слой:

| Группа | Внешние функции | Слой |
|---|---|---|
| Аварии, тождественность, арифметика с проверкой, классификация `Float` и полный порядок | `assert_fail`, `expect_fault`, `is_same`, `Int.checked_*`, `Int.to_float`, `Float.is_nan`, `Float.is_finite`, `total_order_key` | core |
| Текст, байты, списки, словари, множества, числа как текст, кодовые точки | 40 методов и конструкторов в `alloc/builtin/*` и 3 функции `std.text`, среди них `from_code_point` | alloc |
| Преобразования JSON, порождаемые для каждого типа | `std.json.to_value`, `std.json.from_value` (реализует компилятор, а не вручную) | alloc |
| Стандартный вывод, аргументы, окружение, пути | `write_output`, `write_error`, `std.args.list`, `std.env.*`, `Path`, `Path.to_text`, `separator` | std |
| Файлы и протокол атомарной фиксации | 19 функций `std.files` | std |
| Процессы | `std.process.run` | std |

4. `unio run` и `unio test` запускают каждую программу в песочнице раздела 4.6 ТЗ: полномочия ближайшего `unio.toml`, суженные политикой, применяются до `main` или до первого теста. Раздел 9 говорит, как это устроено и где её пределы.
5. Поведение, закреплённое при реализации внешних функций там, где объявления молчали:
   - `Float.to_text` пишет десятичную запись для экспонент от −6 до 20 и научную иначе (`1e+300`), целые значения всегда с дробной частью (`2.0`), а не-конечные — как `nan`, `inf`, `-inf`; `Text.to_float` последние три обратно не читает.
   - `Text.index_of` со `start` вне `0..length()` — авария, как `slice`. `Int ** n` с отрицательным `n` — авария.
   - `std.files.rename` никогда не заменяет цель, и проверка — часть самого переименования: `renameat2` с `RENAME_NOREPLACE` в Linux, `renamex_np` с `RENAME_EXCL` в macOS, `MoveFileExW` без `MOVEFILE_REPLACE_EXISTING` в Windows. Где у системы или файловой системы этого нет, файл получает жёсткую ссылку под новым именем (это не удаётся, если имя существует), а затем старое имя удаляется; каталог же завершается ошибкой вида `Unsupported` вместо гонки с другим процессом.
   - `std.files.list_tree` не следует по символической ссылке на каталог: ссылка выводится как элемент, поэтому цикл ссылок конечен и ссылка не уводит обход за пределы дерева. Ссылка распознаётся по тому, что `resolve` от неё не даёт её собственного места в разрешённом дереве.
   - `std.env.home_dir` спрашивает у операционной системы каталог профиля пользователя; на Windows это каталог, который система сообщает через профиль пользователя, а не переменная, заданная программой.
   - `std.process.run` даёт дочернему процессу пустой стандартный ввод; процесс, завершённый сигналом, имеет статус 128 плюс номер сигнала; ограничение времени ноль или меньше — `ProcessError` вида `Other`. Дочерний процесс получает построенное для него окружение (9.5), работает в собственном дереве процессов, и каждый его вывод захватывается не больше чем на 16 МиБ; правила даёт раздел 9.5.

## 8. Интерпретатор спринта S5 и нативный код спринта S6

1. Интерпретатор S5 обходил проверенное синтаксическое дерево с таблицами проверки. Спринт S6 сначала понижает это дерево (`compiler/unio/src/lower.rs`): имена разрешаются в ячейки локальных значений и индексы констант, позиции полей и варианты перечислений находятся один раз в каждом месте, литеральные списки и кортежи строятся один раз, а вызовы делят один стек значений. Несколько функций прелюдии (`is_empty`, `first`, `last`, `enumerate`, `contains`, `keys`, `values`, `append_all`, `range`, `Text.to_int`) выполняются как встроенные функции среды с теми же результатами, что их определения на Unio. Та же пониженная форма — вход нативного кода (пункт 4). Замеры — в [bench/README.md](../../bench/README.md).
2. Интерпретатор — эталон смысла программ: нативный код должен давать тот же вывод, код выхода и диагностики для каждого теста репозитория (пункт 5).
3. Критерий выхода S5: каждый блок `test` в `stdlib/`, `examples/`, `docs/examples/` и `tools/` выполняется и проходит; инструменты из `tools/` работают в интерпретаторе и дают те же результаты, что проверяющие скрипты на Python, которые остаются в репозитории как эталон для сверки и для сравнения производительности.
4. **Нативный код (S6).** `unio build [--release] FILE [-o OUT]` делает один исполняемый файл (К-5) для машины, на которой работает компилятор: Linux на x86-64 или AArch64, macOS на AArch64 либо Windows на x86-64 (MSVC); на любой другой машине сборка останавливается с сообщением, которое называет эти четыре. Сборка проверяет программу, как `unio run`, понижает каждое тело, как интерпретатор, и переводит каждое пониженное тело (функции, лямбды, константы, значения по умолчанию полей и параметров внешних функций) через Cranelift в один объектный файл (ELF, Mach-O или COFF, с соглашением о вызовах системы: System V, AArch64 Apple или Windows x64), который системный компоновщик связывает со средой выполнения, собранной из крейта компилятора (`libunio.a`, в Windows `unio.lib`), и системными библиотеками, нужными среде выполнения: в Linux — компилятор C (`cc` или `CC`); в macOS — `clang` выбранных инструментов разработчика с их SDK, оба найдены через `xcrun` до шага компоновки (или `CC`), для macOS 11 и новее и без карты отладки; в Windows — `link.exe` новейших средств сборки C++ Visual Studio, найденный так же, как его находит rustc (или из командной строки разработчика), с `/Brepro`, чтобы исполняемый файл не нёс отметки времени. Без `-o` исполняемый файл называется по FILE, в Windows с `.exe`. Библиотека среды выполнения — это `UNIO_RUNTIME_LIB`, файл рядом с компилятором (как его оставляет `cargo build`) или `lib/unio/` рядом с каталогом `bin/` установленного компилятора: установленная раскладка — `PREFIX/bin/unio`, `PREFIX/lib/unio/libunio.a` (`unio.lib`) и `PREFIX/share/doc/unio/` с файлами лицензий, её делает `.github/scripts/release_build.sh` (план, раздел 12, условие выпуска 1). Стандартная библиотека встроена в компилятор, поэтому установленному компилятору не нужен ни один её файл (RFC 0004; `trusted_stdlib` в `compiler/unio/src/program.rs`). `--release` оптимизирует порождённый код (уровень Cranelift `speed`, каждая функция начинается на границе 64 байт, чтобы её скорость не зависела от кода, размещённого перед ней); без него Cranelift не оптимизирует. Устройство (`compiler/unio/src/native/`):
   - Значения имеют раскладку среды выполнения: `Value` — `repr(u8)`, первый байт — тег, полезная нагрузка `Int` и `Float` лежит по смещению 8, `Bool` — по смещению 1. Локальное имя, чей тип `Int`, `Float` или `Bool` виден из сигнатуры или из связывания, хранится неупакованным в регистре. Операторы над такими значениями — машинные инструкции с проверками раздела 2: сложение — одно сложение и переход при переполнении, деление проверяет ноль и `MINIMUM_INT / -1`. Значения этих типов никогда не трогают счётчик ссылок. `for i in range(a, b)` — цикл со счётчиком, который проверяет границу один раз перед первой итерацией и затем в конце каждой. Операция компилируется без проверки переполнения только там, где известные коду границы доказывают, что результат в диапазоне: у переменной цикла со счётчиком с литеральными границами и у параметра типа `Int` после проверки его с литералом, о которой известно, что она выполнилась или нет (`if n < 2: return n` даёт ниже `n >= 2`); ни то ни другое нельзя присвоить (Я-10). Сложение или вычитание операнда с известным знаком проверяется одним сравнением результата с другим операндом. `x % c` и `x / c` для литерала `c > 1` и `x`, о котором известно, что он не отрицателен, — умножение на обратную величину без поправок на знак; для прочих операндов деление Cranelift на константу соблюдает правило 2.1 (`/` усекает к нулю, `%` имеет знак левого операнда). Каждая операция, чей диапазон не доказан, сохраняет проверку, поэтому каждая авария интерпретатора происходит в нативном коде в том же месте. Где тип статически неизвестен, целые распознаются по тегам и всё равно вычисляются на месте; сравнения текстов, целых и логических значений выполняются там, где лежат значения, без копирования.
   - Вызов функции с телом и без аргументов типа — прямой вызов: скалярные параметры и результаты передаются в регистрах, прочие значения — по адресу, и вызываемая функция их забирает; параметры `var` возвращаются через свои адреса, а глубина стека вызовов среды вместе с кадром вызываемой функции — ещё один аргумент в регистре. Вызываемая функция кладёт свой кадр одним сравнением с пределом стека и одной записью своего места со строкой своего объявления; снятие кадра ничего не стоит. Глубина и строка текущей инструкции лежат в памяти только там, где среда может их прочитать: перед вызовом среды, получающим контекст (таким, что может закончиться аварией или выполнить код), код записывает обе, перед прямым вызовом — только строку, а инструкция без такого вызова не записывает ничего. Строка — переменная порождённого кода, которую задаёт каждая инструкция, поэтому после цикла, ветвления или обработчика записана строка инструкции, начавшейся последней, как в интерпретаторе; трассы и предел стека (К-14, К-18) — те же, что в интерпретаторе. Если тело функции начинается с предложений `if c: return v`, которые читают только скалярные параметры и не могут закончиться аварией, они решаются при каждом прямом вызове: когда в стеке есть место для кадра вызываемой функции и условие выполнено, результат — `v`, и вызова нет; на пределе стека вызов делается и заканчивается кодом 102, как и без этого.
   - Операции над значениями, владеющими памятью, вызывают среду выполнения: выбор метода по типу получателя с кешем в каждом месте вызова (внешняя или скомпилированная функция затем вызывается без кадра интерпретатора), поля (читаются на месте, когда значение держит кадр, и меняются на месте при присваивании), индексация, построение со значениями по умолчанию, интерполяция, образцы, перебор, места с индексами и внешние функции.
   - Ошибки, аварии и исчерпание раскручиваются по статусу: операция, которая не удалась, возвращает статус 1, а код освобождает свои временные значения и продолжает в ближайшем обработчике `try` или `on`, в освобождении открытого блока `using` (К-17) или возвращает статус 1 вызывающему. `break`, `continue` и `return` по пути освобождают открытые блоки `using`, как в интерпретаторе.
   - **Образ программы.** Исполняемый файл содержит образ программы, подготовленный сборкой, а не исходные тексты (`compiler/unio/src/native/image.rs`): объявления, нужные для выполнения (модули, типы с их полями и вариантами, функции с их параметрами, константы, реализации), каждое пониженное тело, на которое ссылается нативный код, и разрешения, которые объявляет манифест; отдельно от них, как диагностические метаданные, — файл каждого модуля и строка каждой функции для трасс. Объявления пронумерованы в порядке сборки и названы модулем и именем, из которых выполнение выводит идентичность каждого типа так же, как `unio run`; внешние функции связываются по имени при запуске. Образ версионирован: он начинается с метки, версии формата (2), идентичности компилятора (его версии и хеша исходных текстов компилятора и среды выполнения) и идентичности набора инструментов, который скомпоновал исполняемый файл (ниже). Исполняемый файл, чей образ другого формата, сделан другим компилятором, чем связанная с ним среда выполнения, или повреждён, останавливается до `main` с сообщением о причине и кодом 104 (одним из кодов, которые К-15 оставляет среде выполнения).
   - **Запуск.** До `main` исполняемый файл читает образ, строит таблицы интерпретатора из его объявлений, устанавливает пониженные тела и нативный код каждой единицы, заполняет таблицу ссылок каждого тела (кеши его мест вызова и литералы), применяет песочницу манифеста, суженную политикой из `UNIO_POLICY` (SB-1; аргументы принадлежат программе, поэтому `--policy` нет), и выполняет `main` в потоке со стеком `unio run`. Он ничего не разбирает, не проверяет и не понижает, и синтаксический анализатор, проверка и понижение в него не компонуются. Пустая программа запускается примерно за 2,6 мс (7.1: не более 5 мс; [bench/README.md](../../bench/README.md)).
   - **Пути.** Образ не содержит путей машины, на которой его собрали. Трасса называет файл модуля относительно корня его пакета (каталога его `unio.toml`, а без него — каталога файла), а модуль стандартной библиотеки — как `std:` с его путём внутри библиотеки (`std:core/prelude.unio`); `unio run` и `unio test` называют файлы так же, поэтому трассы одинаковы в нативном коде и в интерпретаторе, где бы программу ни собрали и ни запустили.
   - **Разрешения исполняемого файла.** Исполняемый файл хранит записи `[permissions]` так, как их пишет манифест, и раскрывает их при запуске: `$CWD` — рабочий каталог запуска, `$HOME` и `$TEMP` — каталоги запуска, абсолютные пути остаются как написаны; политика из `UNIO_POLICY` сужает их, как для `unio run`. Относительная запись `files.read` или `files.write` отсчитывается от каталога манифеста (И-6a), которого у установленного или перемещённого исполняемого файла нет, а привязка к рабочему каталогу или к каталогу исполняемого файла изменила бы то, что она разрешает; поэтому `unio build` отклоняет такой манифест, называет запись и предлагает `$CWD/...` или абсолютный путь. Исполняемый файл, перемещённый в другой каталог без своего проекта, запускается с теми же разрешениями.
   - Конструкция, которую генератор пока не умеет компилировать, останавливает `unio build` с сообщением «not yet compiled natively», файлом и строкой; ничего не откатывается к интерпретатору. Пока отклоняются (и не встречаются ни в одной программе репозитория): аргумент вызова метода, меняющий через `var` имя получателя; место с индексом как аргумент `var` метода, у имени которого есть параметр `var`; `var self` на месте с индексом, вычисление которого имеет эффекты.
   - Сборка детерминирована: одни и те же исходные тексты дают одинаковые байты, в том числе когда проект скопирован в другой каталог и собран там с другими домашним и временным каталогами (К-4).
   - **Набор инструментов.** Закрепление кода, который ищет компоновщик, не закрепляет найденный компоновщик, поэтому сборка записывает компоновщик и SDK, с которыми она компонует. До шага компиляции инструмент `unio` вычисляет идентичность своего набора инструментов (`compiler/unio/src/native/toolchain.rs`): тройку цели, затем в Linux — компилятор C и первую строку его `--version` (`x86_64-unknown-linux-gnu; cc: cc (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0`); в macOS — компилятор, первую строку его `--version` и версию SDK (`xcrun --show-sdk-version`, иначе из имени SDK); в Windows — версию набора MSVC, которому принадлежит `link.exe` (из его каталога `VC\Tools\MSVC\<версия>`, иначе из его баннера), и версию Windows SDK (из каталога `Windows Kits\10\lib\<версия>\um` в `LIB`): `x86_64-pc-windows-msvc; link.exe: MSVC 14.51.36231; sdk: Windows 10.0.26100.0`. Она содержит имена инструментов и версии и никогда — путь машины, поэтому одинакова везде, где установлен тот же набор инструментов. Эти запросы инструмент выполняет сам, как выполняет `xcrun` в macOS, а не в песочнице шага компоновки. Рабочий процесс записывает идентичность в образ после идентичности компилятора; выполнение её не проверяет. `unio build --print-toolchain` печатает идентичность, которую записала бы сборка, и ничего не собирает; `native::image::made_by_executable` читает её обратно из исполняемого файла (образ хранит её обычным текстом UTF-8). Две сборки дают одинаковые байты только на одном наборе инструментов, который называет эта запись. Когда компоновщика нет (`cc` или `CC` в Linux, инструментов разработчика в macOS, `link.exe` в Windows), `unio build` останавливается до компиляции с сообщением, которое называет его и говорит, что установить; сам он ничего не устанавливает.
   - **Цели.** Четыре цели различаются только набором команд, соглашением о вызовах, форматом объектного файла и компоновщиком. Значения имеют раскладку среды выполнения на каждой из них (64 бита, little-endian); глубина стека вызовов — счётчик среды выполнения, а не машинный стек, поэтому трассы и предел стека (К-14, К-18) одинаковы на всех целях; поток `main` получает стек `unio run`, а кадры пробуют машинный стек постранично (встроенные пробы Cranelift), так что ни один кадр не перескакивает сторожевую страницу. Деление на константу, описанное выше, порождается как `umulhi` Cranelift и точно на обоих наборах команд. Исполняемый файл применяет песочницу своей системы, как `unio run` на ней (Landlock и seccomp, Seatbelt, AppContainer из 9.4 в Windows), а аргументы в Windows читает из командной строки UTF-16, как `unio run`. Тест генератора кода собирает объектные файлы эталонных программ для всех четырёх целей на любой машине, проверенные Cranelift и одинаковые в двух сборках (`native::tests`); компоновка и запуск выполняются только на самой цели.
5. **Равнозначность.** `compiler/unio/tests/native.rs` собирает каждую эталонную программу, которую запускают тесты интерпретатора (утилиты с их входами, список задач, программы, завершающиеся каждым видом аварии и кодами выхода, бенчмарки и четыре инструмента `tools/` над репозиторием), запускает каждую нативно и через `unio run` и сравнивает стандартный вывод, стандартный поток ошибок и код выхода. Тест также проверяет, что две сборки одинаковы, в том числе одного проекта, скопированного в два каталога, что программа с ошибками не собирается, что исполняемый файл применяет манифест своего пакета, а перемещённый в другой каталог без проекта — те же разрешения, что трассы называют файлы относительно их пакета, что быстрые пути генератора (строки, записанные перед вызовами, границы, убирающие проверки переполнения, деление на константы, начальные предложения, решённые при вызове) сохраняют каждую аварию, трассу и код выхода что идентичность набора инструментов, которую печатает `unio build --print-toolchain`, совпадает с той, что несёт исполняемый файл, и не содержит путей машины, что отсутствующий компоновщик (несуществующий `CC` в Linux и macOS) останавливает сборку с сообщением и без исполняемого файла и что образ другого формата, другого компилятора или повреждённый отклоняется с кодом 104 (в macOS изменённый исполняемый файл заново подписывается подписью ad-hoc, потому что система запускает только подписанный код). CI запускает его в задании `compiler` на Linux x86-64, macOS на AArch64 и Windows x86-64 и в задании `native-linux-arm` на Linux AArch64; на любой другой машине он пропускается с пояснением.
6. **Ещё не сделано**, в порядке важности для скорости: типы проверки в пониженной форме — для статического выбора методов и мономорфизации обобщений (сейчас виды выводятся локально из сигнатур и связываний); устранение счётчиков ссылок и переиспользование на месте в духе Perceus (dup и drop по последнему использованию, заимствованные параметры, переиспользование освобождённой ячейки построением того же размера); неупакованные списки скаляров; оптимизирующая сборка выпуска.

## 9. Песочница на практике

Этот раздел — документация пределов песочницы, которую требует SB-9.

1. **Откуда берутся полномочия.** `unio run` и `unio test` читают `[permissions]` из ближайшего `unio.toml` над программой (И-6) и сужают их политикой (SB-3a). Без манифеста программа может читать свои аргументы и стандартный ввод и писать в стандартный вывод и поток ошибок — и ничего больше (SB-2). Тесты получают те же полномочия, что программа; тест, которому нужны файлы, объявляет их, например `files.write = ["$TEMP/**"]`.
2. **Пути и запись.** Относительные записи отсчитываются от каталога манифеста или политики. Ссылки и `..` разрешаются до сравнения пути в том порядке, в каком их берёт система, и затем операция использует проверенный путь, так что разрешённое и открываемое совпадают (`resolve` и `walk_path` в `compiler/unio-runtime/src/sandbox/mod.rs`). В Linux и macOS система проходит ссылку раньше идущего за ней `..`, поэтому `open/link/..` — это каталог над целью ссылки, а не `open`: путь разрешается по одному компоненту от корня, каждая ссылка заменяется своей целью до того, как берётся следующий компонент, а ниже первого отсутствующего компонента остаток берётся по тексту. В Windows система сначала убирает `..` из текста, и проверка делает так же. Операция чтения (`read_text`, `read_bytes`, открытие файла для чтения частями, `exists`, `is_directory`, `list_directory`, а значит и `list_tree`, и `resolve`) использует разрешённый путь. В песочнице в Linux и macOS, полной или ослабленной, она доходит до этого пути от каталога покрывающей его области, не проходя ссылку ни в одном компоненте (`compiler/unio-runtime/src/sandbox/beneath.rs` и `fdio.rs`): опора — корень области-поддерева или каталог, в котором лежит область из одного файла. В Linux опора открывается по одному компоненту от `/` (`O_PATH`, `O_NOFOLLOW`), а остаток — относительно неё через `openat2` с `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` или, если в ядре нет `openat2` (до 5.6), по одному компоненту через `openat` с `O_NOFOLLOW`; `exists` и `is_directory` открывают объект с `O_PATH` и спрашивают `fstat`, а `list_directory` читает имена из открытого дескриптора (`fdopendir`). В macOS 11 и новее проверенный путь, в котором нет `.`, `..` и ссылок, открывается с `O_NOFOLLOW_ANY` и исследуется через `fstatat` с `AT_SYMLINK_NOFOLLOW_ANY`, которые завершаются ошибкой на ссылке в любом компоненте; в более старой macOS чтение в песочнице завершается ошибкой. Поэтому ссылка, которую другой процесс ставит на путь после проверки, приводит к ошибке операции (`exists` и `is_directory` сообщают `false`), а не выводит её из области: ссылка отвергается, а не проходится с повторной проверкой. `resolve` сообщает проверенное разрешение, после того как так же подтверждено, что объект существует, и никогда не разрешает путь по имени второй раз. Операция записи называет запись каталога: её каталог разрешается, а последнее имя остаётся как дано, так что ссылка последним именем — это сама запись. Запись одного файла разрешает также временные файлы его атомарной фиксации рядом с ним и сброс его каталога. Имя программы без пути совпадает только с вызовом по этому имени, но не с путём, который им заканчивается.
   - **Процесс записи.** В Linux и macOS у программы нет права записывать файлы на уровне операционной системы, как и у запущенных ею дочерних процессов. Каждая операция записи `std.files` — запрос к процессу записи: шаги `AtomicFile` (а значит, `write_text`, `write_bytes` и `copy_file`), `create_directory` и `rename`. Процесс записи запускается из того же исполняемого файла до того, как применяется песочница программы, с пустым окружением, закрытыми стандартным вводом и выводом и одним концом пары сокетов. Он получает действующие области записи (манифест, суженный политикой, SB-3a) один раз, до того как выполняется какой-либо код программы, и другой настройки не принимает. Затем он применяет собственную песочницу: в Linux — `no_new_privs`, Landlock с правом записи только в области записи (область одного файла — на его каталог; это право есть только у процесса записи), без чтения других файлов и без TCP, и seccomp без exec, новых процессов и потоков и сокетов; в macOS — профиль Seatbelt с областями записи, временными файлами каждой области одного файла и чтением каталогов на пути к ним. Процесс записи завершается вместе с программой: сокет закрывается, а в Linux его убивает сигнал о смерти родителя.
   - **Что проверяет процесс записи.** Среда выполнения сначала проверяет каждую операцию, как и везде (пункт 3); процесс записи проверяет её ещё раз по своим областям и программе не доверяет. Он открывает каталог пути по одному компоненту от `/` с `O_NOFOLLOW` (в Linux ещё `O_PATH`), отказывает при ссылке на пути и выполняет все следующие шаги относительно этого дескриптора. Временный файл создаётся с `O_CREAT | O_EXCL | O_NOFOLLOW` под именем `.<имя>.unio-tmp-<pid процесса записи>-<номер операции>`; фиксация переименовывает его поверх цели в том же каталоге через `renameat`; `durable = true` сбрасывает этот каталог; `rename` использует `renameat2` с `RENAME_NOREPLACE` (`renameatx_np` с `RENAME_EXCL` в macOS); `create_directory` — `mkdirat`, а затем сбрасывает каталог, в котором создан новый (10.4). Поэтому каталог, заменённый ссылкой между двумя запросами, не может увести фиксацию в другое место, а новый запрос через ссылку отклоняется. Ссылка в последнем имени цели заменяется как запись каталога и никогда не разыменовывается. Номера операций — непредсказуемые 64-битные числа, которые выдаёт процесс записи: только операция, создавшая временный файл, может зафиксировать или удалить его, и фиксация должна назвать цель своей операции. Программа получает дескриптор своего временного файла (передаётся через SCM_RIGHTS и закрывается при exec) и сама записывает данные, поэтому данные не проходят через процесс записи и к ним применяется лимит размера файла программы. Процесс записи также отвечает, поддерживает ли цель `durable = true` (S-9a), по таблице монтирования, которую он прочитал до применения своей песочницы.
   - **Протокол** версионирован и использует префикс длины: кадр — это 32-битная длина в порядке little-endian, затем байт версии, байт операции (настройка, вопрос о надёжности, открытие, фиксация, отмена, сброс по операции, сброс каталога, создание каталога, переименование) и её поля: 64-битные числа и строки байтов с 32-битной длиной. Ответ несёт состояние: выполнено, отклонено, ошибка системы с её номером или некорректный запрос. Запрос, который нельзя разобрать, запрос другой версии и повторная настройка отклоняются как некорректные; кадр больше 1 МиБ завершает соединение. В одной программе одновременно открыто не больше 256 атомарных файлов.
   - **В Windows** процесса записи нет; процесс записи заменяет второй AppContainer программы (пункт 4). Поток программы берёт маркер этого контейнера только на время операции класса записи среды выполнения, после её проверок, на путях, которые эти проверки разрешили, и сразу после неё возвращается к маркеру программы (`Program::as_writer` в `compiler/unio-runtime/src/sandbox/windows.rs`). У контейнера записи есть права на запись: дерево области записи со всем содержимым, а для области одного файла — право создавать, заменять и удалять записи его каталога, не просматривая и не читая его, то есть право на уровне каталога, которое в Linux есть у процесса записи, с записью, которую наследует то, что он там создаёт, чтобы он мог писать свой временный файл; эта запись удаляется из каталога и из файлов в нём, когда программа завершается. Ни у маркера программы, ни у её дочерних процессов прав на запись нет. От Unix устройство отличается одним: запись выполняется в потоке программы, поэтому она не проверяет ничего сверх проверок среды выполнения; она добавляет то, что операционная система ограничивает каждую запись областями записи, так что ошибка проверок не может записать в другое место.
   - **Чего не исключают одни проверки.** Там, где операционная система не обеспечивает области (Linux и macOS с более слабой песочницей, Б-5, и режим одних проверок в тестах Windows), проверки среды выполнения — единственная преграда. На всех системах их достаточно против ссылки, которую другой процесс ставит на проверенный путь между проверкой и использованием: каждая операция чтения доходит до проверенного пути, не проходя ссылок (выше), а каждая запись идёт через процесс записи. Тест `a_link_swapped_in_after_the_check_reveals_nothing_outside_the_scope` (`compiler/unio-runtime/tests/files.rs`) в плотном цикле подменяет каталог и файл области ссылками за её пределы, при одних проверках среды выполнения, пока программа читает, перечисляет, спрашивает и разрешает пути через них, и не находит ничего извне. В Windows тот же обход открывает якорь по пути как его самого (`FILE_FLAG_OPEN_REPARSE_POINT`) и по его окончательному имени подтверждает, что это проверенный каталог (каталог над ним, подменённый junction, дал бы другое имя), затем каждое имя относительно дескриптора предыдущего (`NtCreateFile` с `RootDirectory` и `FILE_OPEN_REPARSE_POINT`) и отказывает в каждом дескрипторе, атрибуты которого называют точку повторного разбора (`ERROR_STOPPED_ON_SYMLINK`), для чтения, `exists`, `is_directory`, `list_directory` (перечисление по дескриптору) и `resolve` (`sandbox/windows.rs`, `Steps`). Поскольку в Windows нет процесса записи, запись открывается так же: каталог записи — от каталога её области записи, временный файл создаётся в нём, фиксация — переименование относительно этого дескриптора со сквозной записью (`FILE_WRITE_THROUGH`, как `MOVEFILE_WRITE_THROUGH`), `rename` — относительно каталога цели без замены, `create_directory` и удаление временного файла — так же. Контейнер чтения программы может входить, но не просматривать каталог над каждой областью чтения, потому что корень самой области и область одного файла открываются оттуда. Тест гонки выполняется в Windows с символическими ссылками (с junction, где учётная запись не может их создавать) и подвергает гонке и запись; с отключённым обходом он находит утечки (прогоны CI `43290120156` и отрицательная проверка `43290978690`). Программа на Unio сама ссылок создавать не может, но может дочерний процесс, который ей разрешено запускать. Синхронизация каталога при надёжной записи (`system_sync_directory`) по-прежнему открывает каталог по имени на всех платформах; она не читает содержимое и сообщает только, удалась ли синхронизация.
3. **Заблокированные операции** — это ошибки, которые объявляют функции, вида `PermissionDenied`, с названием недостающего полномочия; `exists` и `is_directory` сообщают `false`, а `env.get` — `none` (SB-6).
4. **Платформы.**
   - Linux: среда выполнения проверяет каждую операцию, а операционная система обеспечивает области чтения через `no_new_privs`, Landlock (файлы, TCP, сигналы) и seccomp (сокеты, `ptrace`, монтирование, пространства имён, `io_uring`, `bpf` и другие опасные вызовы); дампы памяти отключены. Программа и её дочерние процессы не могут записывать файлы; за программу пишет процесс записи (пункт 2). Дочерние процессы могут запускать через `execve` только перечисленные программы, интерпретаторы перечисленных сценариев и динамический загрузчик перечисленных программ ELF и читать только области чтения и то, что нужно этим программам для запуска; через загрузчик и перечисленный интерпретатор они могут выполнять больше, чем в списке (пункт 5). Без Landlock ABI 3 или seccomp запуск завершается с кодом 103, если оператор не разрешил более слабую песочницу.
   - macOS: профиль Seatbelt, запрещающий всё по умолчанию и построенный из областей чтения; программа и её дочерние процессы не могут записывать файлы, за программу пишет процесс записи (пункт 2); дочерние процессы могут запускать только перечисленные программы и интерпретаторы перечисленных сценариев, а перечисленный интерпретатор выполняет любой сценарий, который может прочитать (пункт 5). Seatbelt ограничивает весь процесс один раз, поэтому процессы записи всех программ одного `unio test` запускаются до применения первого профиля. Профили проверяются в CI на macOS.
   - Windows: каждый запуск программы получает два собственных AppContainer, созданных как профили со свежими именами (`unio.<процесс>.<случайное>`, так что SID никогда не повторяется) и без возможностей (capabilities), поэтому они не достигают сети, даже loopback; оба профиля удаляются, когда программа завершается (`compiler/unio-runtime/src/sandbox/windows.rs`). У контейнера чтения есть права ровно на области чтения, на файлы перечисленных программ (чтение и исполнение) и на рабочий каталог (вход без просмотра, потому что процесс, который не может войти в свой рабочий каталог, не запускает процессов); у контейнера записи — права на запись (пункт 2). Право — это запись для SID контейнера в DACL корня области; для дерева она пишется и во всё, что ниже корня, что бы ни наследовал DACL каждого элемента, а новые файлы получают её наследованием. Обход не проходит точки повторной обработки (reparse points), поэтому ссылка или junction в области не переносит право на свою цель. Записи удаляются, когда программа завершается; изменения DACL упорядочиваются между процессами пользователя именованным мьютексом, потому что запуски разделяют каталоги. В каталоги можно входить и просматривать их, файлы — читать; файл области чтения не исполняется. Поток программы заимствует маркер контейнера чтения (маркер lowbox, сделанный из маркера процесса) и проверяет, что заимствование на уровне, на котором открываются файлы, и внутри AppContainer, поэтому его собственные открытия проверяет система, а каждый дочерний процесс создаётся в контейнере чтения через `CreateProcessW` с возможностями безопасности контейнера, которые наследуют и дочерние процессы дочерних. Запись идёт через маркер контейнера записи (пункт 2). Операционная система тогда отказывает дочернему процессу и самому потоку во всех файлах вне прав, кроме того, что могут читать все пакеты приложений (системные каталоги, `Program Files`), в любой записи вне областей записи и в любом соединении. Внутри контейнера система не даёт букву диска пути, потому что не может обратиться к диспетчеру точек монтирования, а нормализация имени в таком виде потребовала бы каталогов над ним, которые открывать нельзя; поэтому среда выполнения и компилятор разрешают путь в нормализованное имя с NT-именем его тома и превращают том в букву диска по таблице, прочитанной до того, как контейнер начинает действовать (рабочий процесс получает таблицу от инструмента), что сохраняет разрешение ссылок из пункта 2 (`windows::canonicalize`).
5. **Лимиты.** Время работы и процессорное время ограничивает сторожевой поток, который завершает программу с кодом 102; лимит процессорного времени распространяется и на дочерние процессы. Лимит процессов `limits.processes = N` считает каждый процесс, который запускает программа: каждый вызов `process.run` и каждый процесс, который создаёт дочерний процесс или один из его потомков. Вызов сверх N завершается ошибкой `PermissionDenied` до запуска дочернего процесса. В деревьях дочерних процессов:
   - **Linux:** при лимите поток программы устанавливает ещё один фильтр seccomp со слушателем (`SECCOMP_FILTER_FLAG_NEW_LISTENER`), который заставляет `fork`, `vfork` и `clone` без `CLONE_THREAD` ждать среду выполнения (`clone3` и так завершается с `ENOSYS`, и библиотека C тогда использует `clone`). Отвечает поток `unio`, запущенный вместе с программой: создание потоком программы — это вызов `process.run`, уже учтённый; каждое другое считается ещё одним, и когда учтено N, оно завершается с `EAGAIN`, так что оболочка сообщает, что не может выполнить fork. Фильтр нельзя снять, и его наследует каждый потомок, поэтому счёт точен и ничего не создаётся сверх него. Нужен Linux 5.5 (уведомление пользователя с `SECCOMP_USER_NOTIF_FLAG_CONTINUE`); без него программа с лимитом не запускается (код 103), а совсем без seccomp (ослабленная песочница) лимит считает только вызовы. Не нужны ни root, ни делегированная cgroup; `RLIMIT_NPROC` не использован, потому что он считает все процессы пользователя (и ни одного процесса root), а пространство имён пользователя, которое отделило бы счёт, закрывает сама песочница (`unshare` и флаги пространств имён у `clone` запрещены).
   - **Windows:** Job Object дочернего процесса допускает одновременно не больше процессов, чем оставляет лимит (`JOB_OBJECT_LIMIT_ACTIVE_PROCESS`), поэтому система отказывает в создании сверх этого, а поток считает каждый новый процесс по сообщениям задания (`JOB_OBJECT_MSG_NEW_PROCESS`). Когда счёт доходит до N, задание больше не допускает процессов; дерево, которое за мгновение до этого создало больше (между двумя созданиями новый процесс может запуститься раньше, чем обработано сообщение о предыдущем), завершается, а вызов — ошибкой `PermissionDenied`. Так дерево никогда не выполняет одновременно больше процессов, чем оставляет лимит, а дерево, которое всего запустило больше, останавливается.
   - **macOS:** у системы нет надёжного механизма без root: `RLIMIT_NPROC` считает все процессы пользователя, Seatbelt может запретить `fork`, но не считать его, а `NOTE_TRACK` у kqueue больше нет. Пока вызов ждёт, каждые 5 мс среда выполнения обходит дерево так же, как при его остановке (группа, потомки через родителей и процессы с маркером профиля), и считает каждый процесс, которого ещё не видела; дерево, найденное сверх N, останавливается, а вызов завершается ошибкой `PermissionDenied`. Процесс, который запускается и завершается между двумя обходами, не учитывается, а всплеск созданий может выполняться до одного интервала, прежде чем дерево остановлено: в macOS лимит ограничивает дерево, которое держит свои процессы, а не каждое создание.

   Лимит размера файла проверяет среда выполнения, а в Linux и macOS — и операционная система. Дочерние процессы `process.run`:
   - **Что дочерний процесс может запускать и читать.** Дочерний процесс наследует правила программы, а полномочие `process` добавляет к ним только то, что нужно для запуска перечисленных программ. Каждое перечисленное имя разрешается так же, как его разрешает среда выполнения (голое имя — через каждый каталог `PATH`, путь — как написан, ссылки раскрываются). Через `execve` можно запускать ровно получившиеся файлы и то, что добавляют следующие предложения. Файл, начинающийся с `#!`, добавляет свой интерпретатор, а если интерпретатор — `env`, то и программу, которую `env` должен запустить, найденную через `PATH`; поэтому перечисленный сценарий запускает свой интерпретатор и ничего больше. В Linux файл ELF добавляет свой динамический загрузчик (`PT_INTERP`), который исполняет ядро, и разделяемые библиотеки своих записей `DT_NEEDED`, найденные через его `DT_RUNPATH` или `DT_RPATH` (с `$ORIGIN`), `/etc/ld.so.cache` и каталоги библиотек, и далее по цепочке; библиотеку вне каталогов библиотек можно читать как отдельный файл. Каталоги библиотек `/lib`, `/lib32`, `/lib64`, `/libx32`, `/usr/lib`, `/usr/lib32`, `/usr/lib64`, `/usr/libx32` и `/usr/local/lib` можно читать, но не исполнять, потому что программы загружают из них библиотеки и модули во время работы (модули NSS и `gconv` библиотеки C, библиотеку интерпретатора, например Python); так же можно читать файлы `/etc/ld.so.cache` и `/etc/localtime`, а в `/dev/null` ещё и писать. В macOS исполнять можно перечисленные файлы и интерпретаторы перечисленных сценариев, `/bin/sh` добавляет оболочку, которую называет `/private/var/select/sh`, а читать и отображать в память можно системные библиотеки: `/usr/lib`, `/System`, `/Library/Apple`, `/private/var/db/dyld` и `/private/preboot/Cryptexes` (общий кэш dyld), а также `/private/etc/localtime` и имена в `/`. Ничего другого нельзя ни запускать через `execve`, ни читать за пределами областей чтения: дочерний процесс, которому можно запускать `sh`, не может запустить `/bin/cat` или `/usr/bin/env` ни по пути, ни по имени и не может прочитать `/etc/passwd` или файл вне областей. Программе, которая читает свои данные вне этих мест (например, в `/usr/share` или `/opt`), нужна область чтения для них в манифесте, и тогда их может читать и сама программа.
   - **Что дочерний процесс может выполнить на деле.** Список называет то, что может запустить ядро, а не всё, что может выполнить дочерний процесс, поэтому возможность шире списка:
     - В Linux динамический загрузчик перечисленной программы ELF можно исполнять, а загрузчик сам является программой, которая загружает и выполняет любой файл ELF, который может прочитать (`ld-linux-x86-64.so.2 FILE`), без `execve` этого файла. Поэтому любую программу ELF, которую дочерний процесс может прочитать, — в каталогах библиотек, среди добавленных вне их библиотек и в областях чтения манифеста — можно выполнить, перечислена она или нет. Статически скомпонованная программа загрузчика не добавляет, но достаточно одной перечисленной динамически скомпонованной.
     - Разделяемые библиотеки отображаются в память как исполняемый код: в Linux библиотеки `DT_NEEDED` и каждый файл каталогов библиотек, в macOS перечисленные выше системные библиотеки, которым профиль даёт `file-map-executable` (области чтения там можно читать, но не отображать как код). Landlock и Seatbelt ограничивают запуск программы, а не отображение читаемой библиотеки, поэтому код этих файлов выполняется внутри загружающих их процессов.
     - Перечисленный интерпретатор и интерпретатор, который добавляет перечисленный сценарий (`sh`, `python3`, `perl`), выполняет любой сценарий, который может прочитать, и любой код из своих аргументов (`sh -c`, `python3 -c`); перечисленная программа, которая исполняет свои входные данные (оболочка, `awk`, `make`), делает то, что в них сказано.
     - Поэтому перечислить программу значит разрешить выполнять всё, что эту программу можно заставить выполнить с правами дочернего процесса: перечислить интерпретатор значит разрешить любой сценарий, который дочерний процесс может прочитать, а в Linux перечислить динамически скомпонованную программу значит разрешить любую программу ELF, которую он может прочитать. Закрытой остаётся программа, которую дочерний процесс не может ни запустить, ни прочитать: в Linux `/usr/bin`, `/bin`, `/sbin` и другие каталоги программ вне областей чтения; в macOS любая не перечисленная программа, потому что системный загрузчик там дочерний процесс запустить не может. Ни один дочерний процесс не может записать файл (пункт 2), поэтому не может и создать программу для запуска, а каждый запущенный им процесс сохраняет те же правила. Выполнение анонимного файла (`memfd_create` с `execveat`) тестом не покрыто. Манифесту следует перечислять интерпретатор или оболочку, только когда они нужны программе, и считать такую запись разрешением любого сценария, который дочерний процесс может прочитать.
   - **Окружение.** Дочерний процесс получает только переменные, которые действующие полномочия выдают в `env`, и `PATH` (в Windows ещё `SystemRoot`), со значениями работающей программы; ничего другого он не наследует. В Windows система добавляет в AppContainer `LOCALAPPDATA`, `TEMP` и `TMP`, которые называют папки его собственного профиля (процесс AppContainer не запускается без `LOCALAPPDATA`), поэтому они ничего не говорят дочернему процессу о пользователе. `PATH` передаётся, потому что среда выполнения находит по нему программу по голому имени, а дочерний процесс может так же запускать следующие программы; `SystemRoot` — потому что без неё в Windows не загружаются системные библиотеки. Переменные локали, часового пояса, домашнего и временного каталогов не передаются, если не выданы, и дочерний процесс без них использует умолчания своей системы (например, локаль C). Без песочницы, как в тестах среды выполнения, дочерний процесс наследует всё окружение — так же, как `env.get` тогда разрешает любую переменную.
   - **Дерево процессов.** В Unix дочерний процесс возглавляет новую группу процессов, и каждый процесс, который он запускает, входит в неё. В Linux ни один потомок не может покинуть группу: создав свою группу и до запуска программы, дочерний процесс устанавливает фильтр seccomp, на котором `setsid` и `setpgid` завершаются ошибкой `EPERM` для него и каждого процесса, который он запускает (и без песочницы — тогда в дочернем процессе устанавливается `no_new_privs`). В macOS потомок может покинуть группу, и остановка дерева замораживает группу сигналом SIGSTOP, находит потомков дочернего процесса через их родителей (`proc_listpids`) и, под профилем Seatbelt программы, по метке этого профиля, и замораживает каждого, пока два прохода подряд не найдут ничего нового, затем посылает SIGKILL им и группе. Метка — это пара правил в конце профиля, названных по случайному токену процесса: чтение одного домена настроек разрешено (`user-preference-read`), чтение другого запрещено. Метка называет домены настроек, а не пути, потому что `sandbox_check` сообщает о несуществующем пути как о запрещённом для любого процесса, с профилем или без; разрешённый домен ничего не даёт, так как чтение настроек требует `cfprefsd`, к которому профиль не допускает процесс. `sandbox_check` сообщает ровно эту пару только для процессов под этим профилем, который ни один процесс не может покинуть или изменить и который наследует каждый запущенный им процесс, поэтому находится и потомок, родитель которого уже завершился. В Windows дочерний процесс создаётся приостановленным (`CREATE_SUSPENDED`) собственным `CreateProcessW` среды выполнения (в AppContainer программы, с наследованием ровно трёх его стандартных дескрипторов), помещается в Job Object с kill-on-close и без выхода из задания (не установлены ни `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, ни `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`) и только затем возобновляется, поэтому его первая инструкция уже выполняется в задании, а процесс в задании не может запустить дочерний процесс вне его. Если задание нельзя создать, настроить или назначить, приостановленный дочерний процесс завершается, так и не начав работу, а вызов завершается ошибкой `ProcessError` вида `Other`. Когда дочерний процесс завершается, процессы, ещё работающие в его дереве, останавливаются (SIGKILL группе, до того как дочерний процесс будет утилизирован, поэтому номер группы не может быть занят другим процессом в промежутке; в Windows задание завершается). При истечении времени, при выводе сверх лимита и при исчерпании останавливается всё дерево. Когда сторожевой поток завершает программу с кодом 102, он останавливает деревья ещё работающих дочерних процессов. Деревья реализованы в `compiler/unio-runtime/src/sandbox/tree.rs`.
   - **Срок и вывод.** `timeout_seconds` покрывает весь вызов, включая чтение выводов. Если дочерний процесс завершился, а канал остаётся открытым, вызов ждёт его только до срока и затем завершается ошибкой `TimedOut`; ожидание каналов всегда ограничено. Стандартный вывод и поток ошибок захватываются каждый не больше чем на 16 МиБ (16 777 216 байт); больше — ошибка вида `OutputTooLarge`. Захваченные байты учитываются в лимите кучи по мере поступления, и его превышение завершает программу с кодом 102. Между каналами и вызовом вывод проходит через ограниченную очередь: поток чтения перестаёт читать, пока его фрагменты не забраны, поэтому в пути находится не больше 384 КиБ (`IN_FLIGHT`: два фрагмента по 64 КиБ в очереди и для каждого потока фрагмент, ждущий очереди, и буфер, в который идёт чтение). Эта граница учитывается в лимите кучи на всё время вызова, до запуска дочернего процесса. Вывод сверх лимита сразу завершает вызов и останавливает дерево, поэтому дочерний процесс, который пишет намного больше 16 МиБ, стоит вызову не больше памяти, чем лимит и эта граница.
   - **Пределы дерева.** В Linux программа, которой нужны `setsid` или `setpgid` в дочернем процессе или потомке, там не работает: отсоединяющийся демон, утилита `setsid`, управление заданиями интерактивной оболочки, `start_new_session` и `process_group` в `subprocess` Python; запрет этих вызовов — цена дерева, которое нельзя покинуть без cgroup, а на делегированную ей cgroup среда выполнения рассчитывать не может. Без seccomp (ослабленная песочница, SB-5) фильтра нет, и процесс, покинувший группу, переживает вызов. В macOS потомок, покинувший группу, родитель которого уже завершился (двойной fork в новую сессию), принадлежит launchd и находится только по метке профиля. Программа выполняется под своим профилем всегда, когда применяется её песочница; без песочницы (тесты среды выполнения, которые вызывают её напрямую) такой потомок не находится и может пережить вызов. Метка опирается на `sandbox_check` из libsystem_sandbox, у которой нет публичного заголовка; тест проверяет её ответы в macOS (`tree.rs`), а не сработавшая проверка ничего не находит, и остановка тогда опирается на группу и родителей; номер процесса, который завершился и был утилизирован между поиском и сигналом, в принципе может быть занят другим. Процесс, переживший вызов, держит поток чтения заблокированным на своём канале, пока его не закроет, но сам вызов возвращается к сроку. В Unix прерывание с терминала (Ctrl-C) доходит только до `unio`, а не до дочернего процесса программы в своей группе: тот работает, пока не завершится сам (рабочие процессы инструментов останавливаются, 9.7). Seccomp, Landlock и Seatbelt по-прежнему ограничивают процесс, покинувший дерево.
6. **Чего песочница не делает** (SB-9).
   - Она не защищает от уязвимостей ядра, от побочных каналов и от злоупотребления выданным: программа с правом записи `$HOME/**` может уничтожить эти файлы.
   - Запись на уровне операционной системы точна: ни программа, ни её дочерние процессы не могут там записать ни одного файла, а процесс записи, у которого есть право на уровне каталога, нужное области одного файла, разрешает только этот файл и временные файлы своих операций. Дочерний процесс не может записать даже файлы, которые разрешено записывать программе; он возвращает данные программе, и она их записывает. Область записи, каталога которой нет при запуске программы, записать нельзя совсем, потому что правилу песочницы процесса записи нужен этот каталог. В Windows процесс AppContainer всегда может писать в папку своего профиля (`%LOCALAPPDATA%\Packages\<имя>\AC`, куда указывает его временный каталог), поэтому дочерний процесс может создавать там файлы; папка принадлежит только этому запуску и удаляется вместе с профилем, когда программа завершается. Чтение в Windows шире областей на то, что могут читать все пакеты приложений: системные каталоги и `Program Files`, и дочерний процесс может запустить любую программу оттуда.
   - В Windows права — это записи в DACL файлов пользователя, пока программа работает. Запуск, завершённый извне (убитый или завершённый лимитом, код 102), оставляет свои записи и свой профиль; они называют SID, которого больше нет ни у одного маркера, поэтому ничего не разрешают, но остаются в DACL, пока их не удалят. Файлу, DACL которого пользователь не может менять (файл другого пользователя), право дать нельзя: программа запускается, предупреждает, и ей отказано в этом файле. Право на большое дерево записывает DACL каждого его элемента, дважды за запуск, что занимает время, пропорциональное его размеру.
   - В Windows поток программы может вернуться к маркеру процесса через `RevertToSelf`, который ни одна программа на Unio вызвать не может: смогла бы только ошибка, выполняющая чужой машинный код в этом потоке, так же как такая ошибка в Linux могла бы воспользоваться неограниченным главным потоком `unio run` (ниже). Дочерние процессы и рабочие процессы — процессы своих AppContainer, из которых ничто в них выйти не может.
   - Запуск программ на уровне операционной системы точен: дочерний процесс может запускать через `execve` только перечисленные программы, интерпретаторы перечисленных сценариев и в Linux динамический загрузчик (пункт 5). Выполнять он может больше, как говорит пункт 5: в Linux через загрузчик — любую программу ELF, которую может прочитать, а везде через перечисленный интерпретатор — любой сценарий, который может прочитать. Чтение по-прежнему грубее проверок среды выполнения в следующем. Область чтения, корня которой нет при запуске, там ничего не даёт. Метаданные (`stat`) не ограничены. При любом полномочии `process` каталоги библиотек доступны для чтения, и программе тоже; кроме библиотек, в них есть некоторые программы и сценарии (например, в `/usr/lib`), и в Linux дочерний процесс может запустить такую программу или перечисленную через динамический загрузчик (`ld-linux.so /usr/lib/.../program`), который загружает её без `execve`; программу, которую он не может прочитать, он так не запустит, поэтому `/usr/bin` и другие каталоги программ остаются закрытыми. Перечисленный интерпретатор (`sh`, `python3`) выполняет любой сценарий, который может прочитать, как перечисленная программа обрабатывает свои входные данные. Сценарию, строка `env` которого находит интерпретатор иначе (параметр `env` со значением, например `-u NAME` или `-C DIR`, перед именем или присваивание `PATH`), и в macOS программе, которая сама запускает другую (как `/usr/bin/python3` запускает инструменты разработчика), нужна и эта другая программа в списке.
   - Процесс записи доверяет областям, которые получает от среды выполнения того же исполняемого файла до запуска программы; манифест и политику он заново не читает. Он не останавливает другой процесс того же пользователя, который может записывать в каталоги областей: такой процесс может подменить временный файл или цель между двумя запросами, что никогда не уводит запись за пределы областей, но может изменить содержимое цели.
   - В Linux правила действуют на потоки, которые выполняют программу, и на её дочерние процессы; бездействующий главный поток `unio run` не ограничен.
   - Для кода, написанного ИИ, используйте минимальный манифест, политику с лимитами и отдельного пользователя, контейнер или виртуальную машину для недоверенного кода.
7. **Рабочие процессы инструментов** (SB-10, SB-11, SB-12, SB-14, SB-15). Инструменты читают проекты, которые могут быть враждебными, поэтому их работа выполняется в рабочем процессе, а сам инструмент только разбирает аргументы, запускает рабочий процесс и показывает, что тот вернул.
   - **Какие команды.** `unio check`, `fmt`, `build`, `outline`, `symbol`, `parse --ast`, шаги компиляции `unio test` и `unio run`, каждый анализ языкового сервера `unio lsp` (ниже) и шаги загрузки и распаковки пакетных команд `unio add`, `remove`, `update` и `install` (ниже). `unio explain` не читает исходных текстов и работает в самом инструменте.
   - **Запуск.** Рабочий процесс — тот же исполняемый файл, запущенный со скрытым первым аргументом, с пустым окружением, кроме переменных, выбирающих язык сообщений (`UNIO_LANG`, `LANG`, `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`; в Windows ещё `SystemRoot`, без которой не загружаются системные библиотеки, и `LOCALAPPDATA`, `TEMP` и `TMP`, которые система устанавливает на папки собственного профиля AppContainer рабочего процесса), и с конфигурацией на стандартном вводе: областями, пределами, каталогом стандартной библиотеки, который нашёл инструмент (поэтому `UNIO_STDLIB` ему не нужна), и временным каталогом. Его стандартный вывод и поток ошибок — каналы, которые инструмент передаёт дальше. В Linux он завершается вместе с инструментом (сигнал о смерти родителя).
   - **Области.** Он может читать пакет каждого данного файла и стандартную библиотеку. Пакет — ближайший каталог над файлом по написанному пути, в котором есть `unio.toml`; ссылка в конце пути не разворачивается, поэтому исходный текст-ссылка на файл в другом месте остаётся в пакете, где он перечислен, и его чтение отклоняет система. Без манифеста пакетом служит каталог файла, как в компиляторе; `unio symbol` читает пакет вокруг рабочего каталога. Ещё он может читать записи кэша зависимостей, которые фиксирует `unio.lock` каждого такого пакета (И-14, [packages.md](packages.md)), каждую как дерево, и никакую другую часть кэша; каталог кэша ему передаёт инструмент, потому что у рабочего процесса нет окружения, чтобы его найти. Читать и писать он может только свой временный каталог (режим 0700 в системном временном каталоге, удаляется после работы). В `target/` пока не пишет ни один инструмент: будущий кэш сборки там станет областью записи только после того, как инструмент проверит, что это каталог, а не ссылка.
   - **Правила.** Linux: `no_new_privs`; Landlock с чтением областей, чтением и записью временного каталога, без исполнения, без TCP и с сигналами только внутри песочницы (ABI 6); seccomp без сокетов, `execve`, `fork` и `vfork`, с `clone` только для потоков (`CLONE_THREAD`) и без вызовов пункта 4; без файлов дампа памяти. Правила применяются в главном потоке до чтения чего-либо из проекта и поэтому действуют для всех потоков. macOS: профиль Seatbelt с запретом по умолчанию, чтением областей, чтением и записью временного каталога, просмотром рабочего каталога (он нужен `getcwd`), без процессов и сети. Windows: инструмент создаёт рабочий процесс в собственном AppContainer (пункт 4) с правами ровно на его области: чтение пакетов и стандартной библиотеки, чтение и запись временного каталога, а у рабочего процесса распаковки — и промежуточного каталога его записи кэша, запись на месте файлов, переданных `unio fmt`, исполнение самого `unio` и вход в рабочий каталог; возможностей у него нет, поэтому сети нет. Рабочий процесс проверяет, что работает в AppContainer, и при отказе завершается (код 103), а затем входит в Job Object с пределами памяти и процессорного времени и одним активным процессом, так что не может запустить другой. Права удаляются, когда рабочий процесс завершается.
   - **Пределы.** Память и время берутся из таблицы `[compile]` политики (`--policy` или `UNIO_POLICY`, SB-3a, RFC 0006): `compile.memory_bytes`, `compile.wall_seconds` и `compile.cpu_seconds`, а без них равны 2 ГиБ, 10 минутам и отсутствию собственного предела процессорного времени. Это не пределы программы: `[limits]` никогда не доходит до рабочего процесса, а `[compile]` никогда не доходит до программы. Они одинаково действуют для каждого рабочего процесса: `unio check`, `fmt`, `outline`, `symbol`, `parse --ast`, шагов компиляции `unio run` и `unio test` и обоих шагов `unio build`, шага компиляции и шага компоновки, для каждого рабочего процесса отдельно (каждый из двух рабочих процессов `build` получает весь `compile.wall_seconds`). Предел памяти — это адресное пространство в Linux (`RLIMIT_AS`, он же предел размера файлов рабочего процесса), расход памяти, который инструмент читает каждые несколько миллисекунд, в macOS, и предел памяти Job Object в Windows; время по часам отслеживает инструмент. Рабочий процесс, превысивший предел, останавливается, инструмент печатает `unio: error: the worker of the tool was stopped: ...` и завершается с кодом 102; он никогда не зависает. Рабочий процесс выполняется в собственном дереве процессов, как дочерний процесс программы (9.5): в Linux это группа процессов, которую не может покинуть ни один потомок; в macOS — группа, потомки, найденные через родителей, и для шага компоновки каждый процесс, профиль Seatbelt которого несёт метку, выданную инструментом; в Windows — Job Object, в который рабочий процесс вступает, ещё будучи приостановленным. Когда рабочий процесс завершается, по пределу или нет, оставшееся от его дерева останавливается, поэтому компоновщик и запущенные им процессы не переживают `unio build`; если дерево нельзя подготовить, инструмент завершается с кодом 103. SIGINT, SIGTERM, SIGHUP и SIGQUIT инструмента, пока у них действие по умолчанию, сначала посылают SIGKILL группам процессов его рабочих процессов. Предел процессорного времени — это `RLIMIT_CPU` в Linux и macOS, исчерпание которого инструмент тоже сообщает как предел, и процессорное время Job Object в Windows, где завершение по этому пределу пока не отличается от другого выхода рабочего процесса и не сообщается кодом 102. `unio.toml` никогда не задаёт эти пределы.
   - **Наименьшая память.** Инструмент никогда не повышает предел оператора. `compile.memory_bytes` меньше 192 МиБ (201 326 592 байта, `MINIMUM_COMPILE_MEMORY` в `compiler/unio/src/worker.rs`) соблюсти нельзя, потому что примерно столько рабочему процессу нужно, чтобы запуститься и скомпилировать пустую программу, поэтому инструмент отказывает с кодом 103 и сообщением `unio: error: compile.memory_bytes = N of the policy is below the minimum of 201326592 bytes (192 MiB) ...` до того, как запустит рабочий процесс или что-либо скомпилирует. Минимум получен из измерений в Linux x86-64 (ядро 6.18, GNU ld 2.42, GCC 13.3): наименьшее адресное пространство, с которым рабочий процесс каждой команды завершился, найденное делением пополам с точностью до 1 МиБ и меняющееся на несколько МиБ от запуска к запуску; в него входит стек потока фронтенда в 64 МиБ. Для пустой программы release-сборке инструмента понадобилось 109 МиБ для `check`, `run`, `test` и `symbol`, 78 МиБ для `fmt`, `outline` и `parse --ast` и 127 МиБ для `build` вместе с шагом компоновки; debug-сборке — 121 МиБ, 90 МиБ и 139 МиБ для шага компиляции `build`. Для самого большого исходного файла репозитория, `tools/grammar.unio` (38 КБ), release-сборке понадобилось 153 МиБ для `check`, 154 МиБ для `test`, 123 МиБ для `fmt`, 115 МиБ для `outline` и `parse --ast`, около 165 МиБ для `build` и 175 МиБ для `build --release`; debug-сборке — 164 МиБ для `check` и `test` и 173 МиБ для шага компиляции `build`. 192 МиБ оставляют запас примерно в половину сверх release-чисел для пустой программы; рекомендуемое значение — 256 МиБ, которых с запасом хватает и самому большому файлу. Числа для macOS (расход памяти, который не учитывает зарезервированный стек) и Windows (память Job Object) ещё не получены: `a_compile_memory_below_the_minimum_is_refused_before_compiling` в `compiler/unio/tests/workers.rs` компилирует и запускает пустую программу на минимуме в CI на каждой системе. Шаг компоновки запускает системный компоновщик, потребность которого зависит от набора инструментов и размера `libunio.a`: около 130 МиБ с библиотекой release-сборки и около 530 МиБ с библиотекой debug-сборки в 290 МБ, несущей отладочную информацию; компоновщик сверх предела завершает сборку с кодом 102 или с кодом 1 и сообщением компоновщика, когда это сообщение не показывает исчерпания.
   - **Отказ при нехватке механизмов.** Без Landlock ABI 3 или seccomp, или если правила не применяются, рабочий процесс завершается с кодом 103, если оператор не передал `--allow-weaker-sandbox` (его принимает каждая команда, читающая исходные тексты) или не задал `allow_weaker = true` (SB-5). В Windows механизмов хватает; рабочий процесс вне AppContainer завершается с кодом 103, что бы ни разрешил оператор, а AppContainer, который нельзя создать, завершает инструмент с кодом 103. SB-14 не даёт инструментам выполнять код пакета, но они всё равно обрабатывают недоверенные данные (исходные тексты, импорты, пути, глубоко вложенные конструкции), и ошибка компилятора может вывести за пределы проекта, привести к зависанию или исчерпанию памяти; эту границу и защищает SB-10. Разрешить ослабленную песочницу может только оператор, флагом или внешней политикой (политика для доверенных рабочих каталогов избавляет от флага при каждом запуске); проект через `unio.toml` этого сделать не может. В ослабленном режиме действуют те ограничения, что есть. CI запускает каждую систему с её полной песочницей.
   - **`unio fmt`** пишет через процесс записи из пункта 2, который рабочий процесс запускает до применения своих правил и которому можно писать ровно данные файлы, каждый как элемент своего каталога: данный файл-ссылка заменяется отформатированным файлом и никогда не разворачивается, а её цель вне пакета нельзя даже прочитать. Сам рабочий процесс не вправе писать ни один исходный текст.
   - **`unio build`** выполняется в три шага. Рабочий процесс проверяет программу и пишет объектный файл в свой временный каталог. Шаг компоновки — второй рабочий процесс, который применяет свои правила и запускает компилятор C (`cc` или `CC` инструмента): ему можно запускать ровно компилятор и программы, которые тот называет для `collect2` и `ld`, найденные так же, как для дочерних процессов программы (пункт 5, с интерпретаторами и динамическим загрузчиком), читать каталоги библиотек, `/etc/ld.so.cache`, `/etc/localtime`, каталог собственных программ компилятора (для подключаемых модулей вроде `liblto_plugin.so`, только чтение), `libunio.a` и временный каталог, писать только в этот каталог и не открывать сокетов; его окружение — `PATH` и `TMPDIR`. В macOS инструмент запускает `clang` и его компоновщик напрямую, а не прослойки `xcrun` из `/usr/bin`, и профиль Seatbelt шага компоновки разрешает ему запускать процессы, исполняющие ровно эти программы, читать и отображать дерево инструментов разработчика (`Xcode.app/Contents/Developer` или инструменты командной строки) и системные библиотеки и читать SDK; в Windows он запускает `link.exe` в своём AppContainer, который `link.exe` наследует, с переменными, которые указывают библиотеки Visual Studio и Windows SDK (`LIB`, `LIBPATH`, `PATH`); `link.exe` и эти библиотеки лежат в `Program Files`, который могут читать все пакеты приложений, а сам он может читать объектный файл и `unio.lib` и писать только во временный каталог (набору инструментов, установленному в другом месте, нужно было бы право, которого шаг компоновки не даёт). Затем инструмент копирует исполняемый файл в OUT через временный файл и переименование: OUT выбирает оператор, а не проект, поэтому область записи ему не нужна. Рабочий процесс, читающий проект, не запускает процессов, как требует SB-11; компоновщик — программа системы, которая читает только объектный файл, созданный компилятором, и среду выполнения, и ограничена так же. Остаётся: ошибка компоновщика, которую мог бы задеть подготовленный объектный файл, выполняется с этими правилами.
   - **`unio test` и `unio run`.** Рабочий процесс загружает и проверяет программу и возвращает её диагностики и все файлы, из которых она загружена (её модули, модули стандартной библиотеки и манифесты её пакетов). Инструмент держит их в памяти; поток каждой программы сначала применяет песочницу SB-1, затем заново загружает программу из памяти и выполняет её. Поэтому проект никогда не разбирается вне песочницы. Манифесты и политику инструмент, как и прежде, читает сам, чтобы настроить песочницы программ.
   - **Языковой сервер (SB-13).** `unio lsp` говорит по LSP через свои стандартные потоки и хранит открытые документы; сам он исходных текстов не читает. Каждый анализ (диагностика документа при открытии, изменении и сохранении; подсказка при наведении, переход к определению, дополнение, подсказки типов, форматирование и переименование) выполняется в отдельном рабочем процессе с областями и пределами `[compile]`, описанными выше, для пакета документа: рабочий процесс может читать этот пакет и стандартную библиотеку, пишет только в свой временный каталог, не имеет сети и процессов. Запрос и несохранённые тексты открытых документов этого пакета приходят рабочему процессу на стандартный ввод после его конфигурации (строка `input N` объявляет N байт); внутри эти тексты заменяют для загрузчика свои файлы (`unio::vfs::overlay`), поэтому несохранённому буферу не нужен ни файл, ни более широкая область чтения, а буферы других пакетов не передаются. Рабочий процесс пишет результат LSP в виде JSON в стандартный вывод, и сервер разбирает его, прежде чем передать дальше. Рабочий процесс сверх предела останавливается, как у любого инструмента; тогда сервер публикует диагностику в начале документа вместо анализа или отвечает на запрос ошибкой. Каждый анализ ждёт своего рабочего процесса в отдельном потоке, поэтому сервер тем временем отвечает на другие сообщения; диагностика одного документа выполняется по одной за раз и, когда прогон кончается, ещё раз для последнего изменения. Политика и `--allow-weaker-sandbox` — те, что даны `unio lsp`; политика, которую нельзя соблюсти, останавливает сервер при запуске с кодом 103. `unio/explain`, текст за ссылкой кода диагностики, сервер отвечает сам, как `unio explain`, так как он не читает исходных текстов. Проверяется `compiler/unio/tests/lsp.rs`: в рабочем процессе анализа пробы в обход компилятора отклоняются (файл вне пакета, исходник-ссылка за его пределы, домашний каталог, запись, процессы, сеть), ничего из секрета не доходит до редактора, а анализ сверх предела времени или памяти даёт диагностику, пока сервер продолжает отвечать.
   - **Операции с пакетами (SB-12).** Пакетные команды делят работу между двумя видами рабочих процессов, которые запускаются как остальные, с пределами `[compile]` политики, и так же отказывают при нехватке механизмов; инструмент читает только манифест и блокировку корневого пакета и конфигурацию пакетов оператора и пишет `unio.toml`, `unio.lock` и готовые записи кэша ([packages.md](packages.md)).
     - *Рабочий процесс загрузки* получает один файл настроенного реестра. Инструмент проверяет, что хост URL — хост реестра из конфигурации, разрешает его имя и сам открывает TCP-соединение; рабочий процесс наследует это соединение и не может открыть ни одного: в Linux его фильтр seccomp запрещает `socket` и `connect`, а Landlock — TCP-соединения, в macOS его профиль Seatbelt запрещает сеть, в Windows у его AppContainer нет возможностей, а сокет он получает как унаследованный дескриптор, поэтому он не может достичь никакого другого хоста или порта, даже на той же машине. Он ничего не читает, пишет только во временный каталог (область загрузки), говорит по HTTP/1.1 с `Connection: close`, не следует перенаправлениям и ограничивает ответ (предел архива, 8 МиБ для индекса, 1 МиБ для подписи, 4 МиБ для поручительств и 1 МиБ для списка отзыва реестра). Загруженные файлы доверия и конверты подписей передаются дальше как байты. Для индекса реестра он получает на стандартный ввод набор доверия реестра (якорь оператора и файлы доверия реестра в загруженном виде с нижней границей списка отзыва), конверт индекса и нижнюю границу его порядкового номера; он проверяет файлы доверия, подпись ML-DSA-65 индекса и его порядковый номер *до* разбора индекса (И-8a; [packages.md](packages.md) 7.3) и отдаёт инструменту нормализованные строки, подписавший ключ и порядковые номера, поэтому инструмент никогда не разбирает данные из сети.
     - *Рабочий процесс распаковки* не имеет сети и не запускает процессов. Для архива он может читать только этот файл (подпись и файлы доверия приходят на стандартный ввод) и писать только в каталог подготовки одной создаваемой записи кэша (`<кэш>/staging/...`, который инструмент переименовывает в `packages/<хеш содержимого>`, когда всё проверено и подтверждено). Он сверяет SHA-384 архива с манифестом, индексом или блокировкой до чтения архива; для пакета реестра он затем проверяет набором доверия и конвертом, полученными на стандартный ввод, файлы доверия и подпись ML-DSA-65 архива именно для этого пакета и версии и отклоняет пакет при любом отказе, без исключений (И-8, И-8a; [packages.md](packages.md) 7.3); только потом он читает записи, отклоняя абсолютные пути, `..`, ссылки, устройства, FIFO, расширенные заголовки, повторяющиеся и совпадающие без учёта регистра имена, непереносимые имена и всякое превышение пределов размера, числа и глубины до того, как что-либо записано. Для зависимости-каталога он может читать только этот каталог и копирует его по тем же правилам; для `unio install` он читает существующую запись кэша, ничего не пишет и сверяет её хеш содержимого. Модули пакета он разбирает, чтобы найти пометку `unsafe module`, и ни один из них не выполняет (SB-14), а манифест, помеченные модули и хеш содержимого возвращает как данные.
     - SB-14: при установке и сборке ничего из пакета не выполняется: сценариев сборки нет, а единственные процессы — рабочие, которые не запускают других.
     - Проверяется `compiler/unio/tests/packages.rs`: каждый враждебный архив SB-15 отклоняет рабочий процесс распаковки, и в кэш ничего не записано; в рабочем процессе распаковки пробы записи в кэш вне его каталога подготовки и в проект, чтения вне пакета и exec отклонены; несовпадение хеша отклоняется до распаковки; проба другого порта на 127.0.0.1 в рабочем процессе загрузки отклонена, пока загрузка из настроенного реестра проходит, а URL архива на ненастроенном хосте отклоняется до какого-либо соединения; при `add`, `install`, `check` и `test` ничего из пакета не выполняется; подделанные, недоверенные, отозванные, откаченные или неподписанные файлы реестра отклоняются до того, как распаковано что-либо из архива (`tampered_and_untrusted_registry_files_are_refused_before_unpacking` и другие тесты подписанных реестров).
   - **Пробы.** С `UNIO_WORKER_PROBE` рабочий процесс после применения правил пробует операции простыми системными вызовами в обход компилятора и сообщает о каждой в поток ошибок как `unio worker probe: OPERATION: allowed` или `denied (ERROR)`: `read=`, `list=`, `write=`, `mkdir=`, `remove=`, `write-temp`, `exec=`, `fork`, `connect=HOST:PORT`, `udp`, `env`, `pid`, `sleep=`, `spin`, `alloc=BYTES`. Набор SB-15 (`compiler/unio/tests/workers.rs`) использует их, чтобы показать, что каждую попытку отклоняет система, а не компилятор. Переменную читает инструмент, а не проект.
   - **Ограничения рабочих процессов.** Метаданные в Linux и macOS не ограничены, поэтому рабочий процесс может узнать, существует ли путь где угодно и каков его размер; в macOS он может просмотреть рабочий каталог. В Windows рабочий процесс может читать то, что могут читать все пакеты приложений, и писать в папку своего профиля, которая удаляется вместе с ним. `unio doc` пока нет. В macOS использование унаследованного соединения под профилем Seatbelt проверяется только в CI.

## 10. Испытания гарантий файлов

Этот раздел говорит, как гарантии Б-9 испытываются против сбоев (Б-9b) и что не испытывается. Испытания находятся в `compiler/unio/tests/power_loss.rs` и входят в `cargo test` в Linux, macOS и Windows.

1. **Трасса.** С переменной окружения `UNIO_TEST_FILE_TRACE=1` среда выполнения пишет в стандартный поток ошибок одну строку на каждую операцию, от которой зависит, что накопитель может сохранить после отключения питания, после того как операция удалась: создание временного файла, каждую запись в него, каждый сброс файла или каталога с вызовом, который его сделал (`fsync`, `fullfsync` для `fcntl(F_FULLFSYNC)`, `flush` для `FlushFileBuffers`), каждое переименование, удаление и новый каталог (`compiler/unio-runtime/src/file_trace.rs`). Программа записывает то, что делает сама; процесс записи (9.2) записывает то, что делает для программы, в унаследованный им стандартный поток ошибок, до ответа, поэтому строки обоих процессов идут в порядке операций. Программа передаёт переменную процессу записи, только если она задана. Как и `UNIO_TEST_HEAP_FREE`, хук только наблюдает: он ничего не открывает, ничего не разрешает и не меняет ни одной операции. Второй хук, `UNIO_TEST_FAIL_PARENT_SYNC`, делает неудачным сброс родителя после `create_directory`: со значением `once` только этот сброс, с `always` — и каждую следующую попытку (`parent_sync_fails` в `compiler/unio-runtime/src/externs/durability.rs`); он передаётся процессу записи так же и может только сделать операцию неудачной.
2. **Имитация отключения питания.** Тестовая программа несколько раз заменяет файл с `durable` и без него, пишет его по частям через `open_atomic`, освобождает один атомарный файл без фиксации, создаёт новый файл и пишет в только что созданный каталог. Её трасса воспроизводится на модели файловой системы в каждой точке сбоя, после каждого префикса операций, и проверяется каждое состояние, которое модель позволяет сохранить накопителю, по образцу ALICE и CrashMonkey.
   - Модель сохраняет данные файла только до его последнего сброса вызовом, который доходит до накопителя на этой платформе: `fsync` в Linux, `fcntl(F_FULLFSYNC)` в macOS (простой `fsync` там не считается), `FlushFileBuffers` в Windows. Данные, записанные позже, могут потеряться начиная с любой записи; слабая модель может также сохранить новую длину с нулями.
   - Запись каталога (новый файл, переименование, удаление, новый каталог) сохраняется наверняка, когда её каталог сброшен после неё таким вызовом, а в Windows — когда вернулось переименование с `MOVEFILE_WRITE_THROUGH` в ней или после неё. Записи, сохранность которых не наверняка, сохраняются по двум моделям: *упорядоченной* — префикс в порядке операций, как журналы ext4, XFS, Btrfs, APFS и NTFS хранят метаданные, — и *слабой* — любое подмножество, это всё, что обещает POSIX. Переименование атомарно в обеих.
   - В каждом состоянии проверяется: цель содержит старое содержимое или полное содержимое одной фиксации, дошедшей до переименования (гарантии 1 и 2); после возврата фиксации с `durable = true` цель содержит это содержимое или более позднее (гарантия 3); в каталоге нет имён, кроме целей, бывших там файлов, новых каталогов и временных файлов `.<name>.unio-tmp-*`, которые Б-9 допускает после сбоя; бывшие там файлы сохраняют содержимое.
   - Трасса, воспроизведённая без сбоя, должна дать ту файловую систему, которую оставил запуск, чтобы изменяющая её операция не могла остаться незаписанной, а каждая фиксация в трассе должна нести данные, которые записала программа.
   - Сначала показано, что испытание ловит сломанные протоколы в той же трассе: без сброса данных, с переименованием до сброса данных, без сброса каталога у долговечной фиксации, с простым `fsync` в macOS, без сброса родителя нового каталога (ловит слабая модель), а на пути кода Windows — без `FlushFileBuffers` или без `MOVEFILE_WRITE_THROUGH`; запись на месте, заданная вручную, тоже ловится.
   - Трасса берётся из реального запуска в Linux или macOS. В Windows процесса записи пока нет, и её путь кода в `externs/files.rs` проверяется на трассе, переведённой в вызовы этого пути, при двух явных допущениях: `FlushFileBuffers` доходит до накопителя, а NTFS ведёт журнал по порядку, так что переименование со сквозной записью возвращается, когда оно и все записи до него на накопителе.
3. **Уничтожаемые процессы.** Программа в цикле заменяет файл содержимым размером до 300 КБ, которое можно различить и проверить на полноту, с `durable` и без него. Её уничтожают сигналом SIGKILL (в Windows — `TerminateProcess`) в случайные моменты после первой фиксации; в Linux уничтожается и один процесс записи, после чего следующая запись завершается ошибкой. Каждый раз цель содержит одно полное содержимое, и рядом с ней нет ничего, кроме её временных файлов. Начальное значение генератора печатается, а `UNIO_TRIAL_SEED` повторяет запуск.
4. **Что нашли испытания и что изменилось.**
   - Новый каталог не сбрасывался в родителя: долговечная запись в каталог, только что созданный `create_directory`, могла после отключения питания пропасть вместе с этим каталогом на файловой системе, которая не хранит метаданные по порядку (слабая модель), хотя `write_text` вернулась. Теперь `create_directory` сбрасывает каталог, в котором создан новый, и в процессе записи, и без него; в Windows сброса каталога нет, а NTFS журналирует запись.
   - Если этот сброс не удавался, это игнорировалось, и последующая долговечная запись в новый каталог возвращалась, хотя сам каталог мог не пережить отключения питания (найдено аудитом; испытание с `UNIO_TEST_FAIL_PARENT_SYNC=once` не проходило в слабой модели). `create_directory` по-прежнему удаётся, раз каталог существует, но процесс записи, а также среда выполнения там, где она создаёт каталоги сама, запоминает каждый новый каталог, родитель которого не сброшен. Долговечный сброс каталога, последний шаг долговечной фиксации, сначала заново сбрасывает родителя каждого такого каталога на своём пути, вплоть до каталогов, существовавших до запуска, начиная с самого глубокого; если один из них снова не удаётся, сброс не удаётся, и `commit` сообщает вид `DurabilityUnconfirmed` (Б-9c), а цель уже заменена. Так долговечная фиксация подтверждает всю цепочку новых каталогов, от которой зависит. Сверх 1024 таких каталогов за запуск ни одна долговечная фиксация не подтверждается. Испытание выполняется с хуком: с `once` каждое состояние после сбоя в обеих моделях сохраняет гарантии, а с `always` фиксация сообщает `DurabilityUnconfirmed`. Каталог, переименованный через `rename`, не сбрасывается, поскольку `rename` не обещает долговечности.
   - В macOS, когда `fcntl(F_FULLFSYNC)` каталога не удавался, каталог сбрасывался простым `fsync`, и фиксация считалась долговечной, хотя простой `fsync` там не доходит до накопителя. Простой `fsync` по-прежнему выполняется, поскольку он упорядочивает переименование, но ошибка теперь сообщается, и `commit` завершается ошибкой вида `DurabilityUnconfirmed` (Б-9c).
   - Сброс данных проверен в стандартной библиотеке закреплённого набора инструментов: на платформах Apple `File::sync_all` — это `fcntl(F_FULLFSYNC)` без отступления к `fsync`; в Windows — `FlushFileBuffers`.
5. **Что не испытывается.** Модель описывает гарантии файловых систем так, как их дают их документации; это не отключение питания. Настоящее отключение питания, запись блоков (dm-log-writes, dm-flakey, loop-устройство) и выключение виртуальных машин требуют прав root или виртуальных машин и не выполняются; трасса записывает системные вызовы, а не блоки, которые пишет файловая система, поэтому файловая система, нарушающая собственные обещания, не обнаруживается. Правила для macOS и Windows — допущения, а реальные трассы берутся только из Linux и macOS. Временный файл, оставленный сбоем, потом не удаляется; Б-9 это допускает. Накопитель, подтверждающий записи, которые он не сохранил, вне пределов любой программной проверки (Б-9a).

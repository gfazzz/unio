# RFC 0003: Скорость и память нативного кода относительно Go

- Статус: accepted (ТЗ 7.1, `bench/run.py --check-go`; в CI блокирует для wc и loop, лучший из 9 запусков, с тех пор как шаг о запуске из раздела «Решение», пункт 4, и порождение кода из `docs/ru/runtime.md` 8.4 довели loop примерно до 1,4x Go; json и text — в отчёте)
- Автор: проект Unio при участии Claude
- Дата: 2026-11-07
- Затрагивает: ТЗ / инструменты
- Английская версия (основная): [0003-native-speed-against-go.md](../../rfcs/0003-native-speed-against-go.md)

## Кратко

Требование 7.1 сравнивает Unio только с CPython: не медленнее 0,5x, цель — 3x. Нативные программы `unio build --release` уже в 26 раз быстрее Python на целочисленном коде, поэтому планка относительно Python больше не говорит, хорош ли нативный код. Этот RFC добавляет для нативных программ вторую меру: на наборе бенчмарков из `bench/` каждый бенчмарк занимает не больше двукратного времени того же алгоритма на Go, а цель — паритет с Go; пиковая память — не больше двукратной пиковой памяти Go плюс 8 МБ на среду выполнения. Порог вводится в два шага, чтобы 0.1 не ждал оптимизаций, запланированных после него.

## Мотивация

Замеры на Linux x86-64 с 4 процессорами, лучший из 3 запусков, полное время с запуском (`python3 bench/run.py --native`, коммит третьей части спринта S6). Последний столбец — время нативного Unio, делённое на время Go: 1 — паритет, 2 — предлагаемый предел.

| Бенчмарк | Unio нативно | Python | Go | Rust | Нативно ÷ Go |
|---|---|---|---|---|---|
| wc | 0,273 с | 0,429 с | 0,523 с | 0,103 с | 0,52 |
| json | 6,858 с | 4,307 с | 0,596 с | 0,323 с | 11,5 |
| text | 0,243 с | 0,123 с | 0,065 с | 0,057 с | 3,7 |
| loop | 0,036 с | 0,969 с | 0,015 с | 0,014 с | 2,4 |

Все четыре проходят планку относительно Python, и это скрывает настоящую картину: JSON в одиннадцать раз медленнее Go, а текст — почти в четыре. Пользователи компилируемого языка сравнивают его с другими компилируемыми языками; у Go есть сборщик мусора, проверки границ и простой компилятор, как у Unio, поэтому он честный ориентир. Rust и Mojo — нет: они убирают большую часть проверок, которые Unio сохраняет намеренно (переполнение `Int` всегда авария, Я-17).

Пиковая память тех же запусков, МБ: wc 168 (Go 184), json 731 (Go 173), text 24 (Go 14), loop 6,6 (Go 1,9).

## Почему существующих требований недостаточно

В 7.1 нет меры нативного кода относительно компилируемых языков, а планка относительно Python уже выполнена с большим запасом на двух бенчмарках из четырёх. Без второй меры регрессия, которая вдвое замедлит нативный JSON, всё равно пройдёт CI. Меры памяти в 7.1 нет вовсе, хотя память решает, где программа может работать: на рабочей машине, на сервере с множеством процессов или на машинах, для которых делается UniOS.

## Решение

1. Новая строка в таблице раздела 7.1 ТЗ:

   | Метрика | Требование |
   |---|---|
   | Нативные программы (`unio build --release`) на бенчмарках из `bench/` | каждый не больше двукратного времени того же алгоритма на Go; цель — паритет |

   | Пиковая резидентная память тех же нативных программ | не больше двукратного пика Go плюс 8 МБ; цель — паритет |

   Время — полное, с запуском, лучшее из N запусков, на Linux x86-64, по правилам `bench/README.md`. Пиковая память — пиковый резидентный размер процесса, наименьший из запусков; его измеряет `bench/peak_rss.c`, чтобы не учитывать память запускающего процесса. Запас в 8 МБ покрывает постоянную часть среды выполнения, чтобы программу в несколько мегабайт не судили по отношению. Версия Go записывается вместе с результатами.
2. Порог вводится в два шага:
   - Выпуск 0.1: wc и loop укладываются в оба предела; json и text измеряются и публикуются.
   - Выпуск 0.2: каждый бенчмарк набора укладывается в оба предела.
3. `bench/run.py --check-go` завершается с кодом 1, когда бенчмарк под порогом выходит за любой из пределов, и печатает оба отношения для каждого бенчмарка. CI запускает его на Ubuntu. Пока не сделан шаг о запуске ниже, loop от прогона к прогону колеблется между 1,6x и 2,4x Go, поэтому CI печатает результат проверки, не проваливая прогон; с этим шагом проверка становится блокирующей.

   Примечание о статусе: шаг о запуске вошёл, когда loop всё ещё был в 2,2–2,3 раза медленнее Go, а его вычисление (fib(30) и цикл) — примерно вдвое. Затем порождение кода убрало большую часть цены вызова и инструкции (глубина стека в регистре, строка записывается только перед вызовом, который может её прочитать, проверки переполнения опускаются там, где границы доказывают, что они не нужны, начальные предложения `if c: return v` решаются при вызове; `docs/ru/runtime.md` 8.4), что довело loop примерно до 1,4x Go на машине из `bench/README.md`. С тех пор проверка в CI блокирует для wc и loop, по лучшему из 9 запусков; json и text печатаются и её не проваливают.
4. Порядок работ, которые закрывают разрыв, по замерам:
   1. Запуск: программа заново строит таблицы объявлений из встроенных исходников, около 14 мс. Сериализованные таблицы убирают это; заодно выполняется строка 7.1 о запуске за 5 мс, которую нативный код сейчас не выполняет. Ожидаемый эффект: loop в пределах 2x Go.
   2. Статическая диспетчеризация и мономорфизация обобщённых функций по типам проверки вместо диспетчеризации по типу получателя во время выполнения. Ожидаемый эффект: большая часть разрыва в text и часть в json.
   3. Устранение подсчёта ссылок и повторное использование на месте (Perceus): копирование и освобождение в точке последнего использования, заимствованные параметры, повторное использование освобождённой ячейки того же размера. Ожидаемый эффект: json, который тратит большую часть времени на счётчики и выделение значений `Option` и односимвольных текстов.

   Память следует тем же шагам: сериализованные таблицы убирают фронтенд, который сейчас несёт каждая программа (loop: 6,6 МБ против 1,9 МБ у Go), а представление символов без кучи убирает большую часть пика json (731 МБ против 173 МБ у Go), который держит документ как список односимвольных текстов.
   4. Представление символов без значения в куче.
   5. Второй бэкенд через LLVM для `--release`, если после шагов 1–4 какой-то бенчмарк остаётся за пределом (раздел 10 ТЗ уже называет LLVM).

## Миграция

Не нужна: ни конструкции языка, ни программы не меняются.

## Альтернативы

- Паритет с Go как жёсткий предел: недостижим для 0.1 без шагов 2 и 3; предел, который никогда не выполняется, перестаёт что-либо значить.
- Rust как ориентир: Rust убирает проверки переполнения и многие проверки границ, которые Unio сохраняет по замыслу, поэтому сравнение измеряло бы безопасность Unio, а не качество его компилятора.
- Фиксированное время на бенчмарк: зависит от машины; отношение к Go на той же машине — нет.
- Без порога, только публикация цифр: регрессии оставались бы незамеченными, а именно эту проблему решает RFC.

## Проверка

- `bench/run.py --check-go` на наборе, в CI на Ubuntu, с отношениями времени и памяти в журнале задачи.
- Таблица в `bench/README.md` обновляется после каждого шага из пункта 4 решения, чтобы эффект каждого шага был записан.
- Заметки к выпускам 0.1 и 0.2 публикуют результаты, как уже требует раздел 7.1.

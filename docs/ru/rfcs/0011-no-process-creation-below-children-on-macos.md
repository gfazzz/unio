# RFC 0011: В macOS при пределе числа процессов потомки программы не запускают процессов

- Статус: accepted (решение руководителя проекта от 2026-11-13; реализовано в `compiler/unio-runtime/src/sandbox/mod.rs`, `macos.rs` и `tree.rs`, см. «Проверка»; тесты macOS выполняются только в CI)
- Автор: проект Unio при участии Claude
- Дата: 2026-11-13
- Затрагивает: требования (SB-3) / документацию среды выполнения (docs/ru/runtime.md, 9.5)
- Английская версия (основная): [0011-no-process-creation-below-children-on-macos.md](../../rfcs/0011-no-process-creation-below-children-on-macos.md)

## Кратко

В macOS, когда политика задаёт `limits.processes`, потомок `process.run` и всё, что он запускает, не может создать ни одного процесса. Сама программа по-прежнему запускает своих потомков через `process.run`, и каждый учитывается средой выполнения до запуска, поэтому число процессов, которые вызывает программа, в точности равно числу её вызовов, пропущенных средой выполнения, и никогда не больше предела. Потомок, который пытается выполнить `fork`, `vfork` или `posix_spawn`, получает `EAGAIN`. В Linux и Windows ничего не меняется: там система считает всё дерево. Поскольку ядро освобождает root от этого правила, программа с таким пределом не запускается в macOS, если её реальный или эффективный пользователь — root (код 103), а потомок не может выполнить файл с set-user-ID или set-group-ID. Поиск по дереву, который среда выполнения делала каждые 5 мс, удалён.

## Мотивация

`limits.processes = N` учитывает каждый процесс, который запускает программа, и каждый процесс, который создаёт потомок или его потомки (docs/ru/runtime.md, 9.5). Linux заставляет каждое создание ждать среду выполнения (фильтр seccomp со слушателем), Windows позволяет Job Object потомка держать не больше оставшихся процессов. В macOS такого механизма без root нет, поэтому среда выполнения каждые 5 мс обыскивала дерево потомка (`over_limit` в `compiler/unio-runtime/src/sandbox/tree.rs`, вызывается из цикла `run` в `externs/process.rs`) и останавливала дерево, найденное сверх предела. Процесс, который запускался и завершался между двумя поисками, не учитывался, а всплеск созданий шёл до одного интервала, прежде чем дерево останавливалось:

```unio
import std.process

## Под limits.processes = 3, с process = ["sh"] в манифесте.
public function main():
    let script = "for n in 1 2 3 4 5 6 7 8; do true & done; wait"
    let output = try process.run("sh", ["-c", script], timeout_seconds = 10) on ProcessError as e:
        print(e.reason)
        return
    print("status {output.status}")
```

При пределе три все восемь коротких подоболочек в macOS могли отработать, поскольку каждая может завершиться до следующего поиска. Обзор выпуска 0.1 числит это блокером ([release-0.1.md](../release-0.1.md)). Руководитель проекта решил 2026-11-13, что в macOS потомкам программы запрещено запускать процессы, когда предел задан, чтобы предел был точным.

## Почему существующих конструкций недостаточно

Языковые конструкции не затронуты. SB-3 называл число процессов, не говоря, что и как считается; чтобы предел можно было проверить, смысл нужно записать для каждой системы, а в macOS теперь отличается то, что может делать потомок.

## Устройство

### Что может запускать программа

Программа запускает процессы только через `process.run`. Перед тем как вызов запустит потомка, среда выполнения учитывает его (`may_run` в `compiler/unio-runtime/src/sandbox/mod.rs`); когда N вызовов уже запустили потомка, следующий вызов завершается `ProcessError` вида `PermissionDenied` с причиной `denied by the sandbox: the policy limits the program to N processes`, и процесс не создаётся. Это уже было точным и не меняется.

### Что может запускать потомок

В потомке, после того как среда выполнения его породила и до того, как он запустит свою программу, среда выполнения ставит мягкий и жёсткий `RLIMIT_NPROC` потомка в 0 (`deny_process_creation`, вызывается из `limit_child`). `fork1` в ядре XNU одинаково обслуживает `fork`, `vfork` и `posix_spawn` и завершается с `EAGAIN`, когда число процессов реального пользователя вызывающего процесса вместе с новым превышает мягкий предел вызывающего; при пределе 0 это верно для каждого создания. Процесс не от root не может поднять свой жёсткий предел, а предел наследуется через `fork` и `exec`, включая программы с set-user-ID. Поэтому потомок не может запустить внука, и нет внука, который запустил бы больше. Потомок по-прежнему может заменить себя через `exec` (профиль разрешает только перечисленные программы, docs/ru/runtime.md, 9.5), что не создаёт процесса. Если предел поставить нельзя, запуск завершается ошибкой, и потомок не запускает свою программу.

### Что видит потомок, которому отказано

`fork` и `vfork` возвращают -1 с `errno`, равным `EAGAIN` («Resource temporarily unavailable»), а `posix_spawn` возвращает `EAGAIN`; это та же ошибка, что Linux даёт сверх предела. Оболочка сообщает, что не может выполнить fork: `sh` в macOS — это `bash`, который повторяет fork, завершившийся с `EAGAIN`, с растущими паузами около 15 секунд, прежде чем сообщить `fork: Resource temporarily unavailable`, поэтому вызову, который запускает оболочку, стоит учесть это в `timeout_seconds`. Сам вызов `process.run` возвращается обычным образом со статусом и выводом потомка.

### Почему не Seatbelt

Решение называло профиль Seatbelt, и его правила проверены первыми. Они не могут этого выразить:

- `sandbox_init` применяет профиль ко всему процессу, и каждый процесс, который тот запускает, наследует этот профиль; процесс, уже работающий под профилем, не может применить другой. Поддержка разработчиков Apple пишет, что потомку процесса в песочнице нельзя дать другую песочницу (Apple Developer Forums, тема 747880), и среда выполнения уже опирается на то, что профиль применяется один раз (`macos.rs`, docs/ru/runtime.md, 9.4).
- Программа порождает потомков сама, поэтому её профиль должен разрешать `process-fork`, и потомки работают именно под этим профилем. В языке профилей нет документированного фильтра для `process-fork`, который отличал бы программу от её потомков; `process-exec` управляет тем, какой файл процесс может выполнить, а не тем, может ли он создать процесс, и потомки должны выполнять свои перечисленные программы.

Чтобы запретить потомкам `process-fork`, нужен был бы процесс вне профиля программы, который порождал бы их и применял второй профиль до их запуска (см. «Альтернативы»). Этот RFC не меняет профиль Seatbelt программы: он по-прежнему разрешает `process-fork` для `process.run` и по-прежнему ограничивает то, что потомок может выполнить.

### Root и файлы с set-ID

`fork1` не проверяет `RLIMIT_NPROC` для реального пользователя 0. К нему ведут два пути, и оба закрыты:

- **Программа, запущенная от root.** В macOS, когда политика задаёт `limits.processes`, а реальный или эффективный пользователь процесса равен 0, песочница не применяется и программа не запускается: код 103 до `main` с причиной `the sandbox cannot hold limits.processes for this program: on macOS the limit is exact only because a child may create no process, which the system does not enforce for root, and the program runs with real user R and effective user E (RFC 0011). Run it as a user other than root, or without limits.processes`. Эффективный пользователь 0 тоже учитывается, поскольку он может сделать реальным пользователем 0. Проверка выполняется при каждом входе в песочницу программы, то есть в `unio test` для каждого файла, а в собранном исполняемом файле — как в `unio run` (`root_refusal` в `sandbox/mod.rs`). Тестовый крючок `UNIO_TEST_AS_ROOT=1` заставляет среду выполнения считать обоих пользователей равными 0; он может только отказать в запуске.
- **Файл с set-user-ID или set-group-ID.** Потомок программы не от root становится root, только выполнив файл с set-user-ID, принадлежащий root, и сделав реального пользователя равным эффективному. Поэтому при пределе, прежде чем каждый вызов `process.run` запустит потомка, среда выполнения проверяет каждый файл, который потомок может выполнить: файлы, которые профиль Seatbelt разрешает через `process-exec` и которые песочница один раз разрешила с раскрытыми ссылками (перечисленные программы и интерпретаторы перечисленных сценариев, docs/ru/runtime.md, 9.5; в `unio test` — всех программ запуска, поскольку профиль — их объединение). Каждый открывается без следования ссылке в последнем имени и проверяется через дескриптор с `fstat` (через `lstat`, если его нельзя открыть для чтения); файл, в режиме которого стоит бит set-user-ID или set-group-ID, завершает вызов с `PermissionDenied` и причиной `denied by the sandbox: under a limit of processes on macOS a child may not execute the set-user-ID or set-group-ID file F (RFC 0011)`, как и путь, который теперь является ссылкой или не обычным файлом. Несуществующий файл пропускается. Проверяются все файлы, а не только тот, который называет вызов, потому что потомок может выполнить любой из них (перечисленный `sh` может запустить перечисленную программу с set-user-ID). Бит set-group-ID не даёт пользователя, но тоже отклоняется, чтобы ни один файл не менял полномочия потомка. Затем программа выполняется по пути, который песочница разрешила и проверила, а не ищется снова через `PATH`, а её имя в том виде, как оно записано, становится `argv[0]` (`child_command`). В потомке, после установки предела и непосредственно перед выполнением, те же файлы открываются и проверяются снова, и каждый должен остаться тем же файлом (устройство и inode) без обоих битов; иначе запуск завершается с `EPERM`, и потомок не запускает свою программу (`recheck_executables`).

Остаётся файл, который меняется после последней проверки: перечисленный файл заменён или ему поставлены биты, пока потомок работает. В macOS нет `fexecve`, поэтому ядро при выполнении ещё раз разрешает путь. Поставить бит set-user-ID на файл, принадлежащий root, или положить такой файл по перечисленному пути можно только от root или с правом записи в этот путь; программа и её потомки не пишут файлов на уровне системы (docs/ru/runtime.md, 9.2, в профиле нет `file-write`, кроме `/dev/null`), а процесс записи не может поставить ни один из битов. Поэтому предел точен против всего, что могут сделать программа и её потомки; процесс root вне песочницы, меняющий перечисленные файлы, вне модели угроз SB-9.

Ядро закрывает и этот случай. Seatbelt запрещает выполнять файл с set-user-ID или set-group-ID при любом профиле, независимо от его правил: на образе macos-26 вызов отклоняется с `EPERM`, а журнал записывает `deny(1) forbidden-exec-sugid` (запуск CI 43397303584, тест `a_set_id_file_is_not_executed_under_a_process_limit_on_macos`, который теперь проверяет, что перечисленный файл с set-ID отклоняется и без предела). Поэтому файл, подменённый после последней проверки, всё равно не выполнится как set-ID; проверка среды выполнения остаётся, потому что она отклоняет вызов до запуска потомка с причиной, которая называет файл и правило.

### Поиск по дереву удалён

При запрете, отказе root и проверке файлов с set-ID в дереве не может появиться ни одного процесса, кроме потомка, поэтому поиск каждые 5 мс (`over_limit` в `tree.rs`) в macOS удалён: там `over_limit` возвращает `false`, как в Linux. Поиск потомков для остановки дерева (группа, родители, метка профиля) остаётся, поскольку потомок по-прежнему может покинуть группу процессов, не запуская процесса (`setsid`).

### Нормативный текст

SB-3 говорит, что число процессов учитывает каждый процесс, который запускает программа, и каждый процесс, который создают деревья её потомков, и что в macOS при этом пределе потомки программы не могут создать ни одного процесса и выполнить файл с set-user-ID или set-group-ID, а программа, реальный или эффективный пользователь которой — root, не запускается (код 103). docs/ru/runtime.md, 9.5, описывает механизм, ошибки и то, что остаётся.

## Миграция

Для исходных текстов не нужна. В macOS программа с `limits.processes`, чьи потомки запускают процессы (оболочка, выполняющая конвейер или другую программу, инструмент сборки, запускающий компилятор), теперь получает ошибку в этом потомке; она должна запускать каждую программу своим вызовом `process.run` или работать без предела процессов. Программа с пределом, которая работает от root или чьи потомки могут выполнить файл с set-ID, должна работать от другого пользователя, отказаться от предела или не перечислять этот файл. В Linux и Windows ничего не меняется.

## Альтернативы

- **Оставить поиск для root.** Первый вариант этого RFC оставлял поиск каждые 5 мс для root и для потомка, ставшего root, с его неточностью; руководитель проекта 2026-11-13 потребовал точного предела без исключений.
- **Запускающий процесс вне профиля.** Процесс, запущенный до применения песочницы, как процесс записи (docs/ru/runtime.md, 9.2), порождал бы каждого потомка по запросу программы, применял к нему профиль программы без `process-fork` и передавал обратно его каналы. Тогда правило выражал бы Seatbelt, в том числе для root, а самой программе не нужен был бы `process-fork`. Но запускающий процесс работает без профиля и действует по запросам программы, поэтому он должен был бы проверять каждый запрос, как это делает процесс записи, и взять на себя ожидание потомков и остановку их деревьев, что сейчас программа делает через свою группу процессов, свою метку и `waitid`. Это изменение больше, и отказ для файлов с set-ID всё равно был бы нужен, поскольку второй профиль не меняет полномочий.
- **Искать чаще.** Более короткий интервал сужает окно, но не закрывает его.
- **Считать через `RLIMIT_NPROC`.** Он считает все процессы пользователя, а не дерева, поэтому его нельзя поставить в число оставшихся процессов; равный 0, он запрещает, и этот RFC использует именно это.
- **Отказывать в `limits.processes` в macOS** с кодом 103: точно, но тогда программа в macOS вообще не могла бы ограничить свои процессы.
- **Endpoint Security или `NOTE_TRACK` у kqueue**: Endpoint Security требует entitlement и root, а `NOTE_TRACK` больше не существует.

## Проверка

- `compiler/unio-runtime/src/sandbox/mod.rs`: `a_child_without_process_creation_cannot_fork` (macOS): потомок, поставивший предел, пытается выполнить `fork` до запуска своей программы и получает `EAGAIN`; без предела тот же потомок выполняет fork. Под root тест завершается ошибкой, а не проходит, ничего не проверив.
- `compiler/unio/tests/sandbox.rs`: `a_child_under_a_process_limit_cannot_start_a_grandchild_on_macos` (macOS): потомок на C пять раз пытается выполнить `fork` и один раз `posix_spawn`; без предела всё удаётся; при `processes = 2` два вызова `process.run` запускают его, каждое создание завершается с `EAGAIN`, а третий вызов отклоняется до запуска, так что программа всего запустила два процесса. Отсутствие компилятора C или запуск от root проваливают тест. `a_child_that_starts_more_processes_than_the_limit_is_stopped_or_its_starts_fail` теперь ожидает в macOS, что оболочка не может выполнить fork ни при одном из пределов.
- `compiler/unio-runtime/src/sandbox/mod.rs`: `root_is_refused_a_limit_of_processes` (на каждой системе: причина для реального и эффективного пользователей 0) и `set_id_files_links_and_directories_are_refused_to_children` (на каждой Unix: файл с set-user-ID, файл с set-group-ID, ссылка и каталог отклоняются через открытый дескриптор, несуществующий файл пропускается, обычный проходит со своими устройством и inode). Эти два теста выполнены в Linux x86-64.
- `compiler/unio/tests/sandbox.rs`: `a_program_with_a_process_limit_is_refused_under_root_on_macos` (macOS: под крючком `UNIO_TEST_AS_ROOT=1` программа с `processes = 1` завершается с кодом 103 до `main`, без предела она работает под крючком, а с пределом — без крючка) и `a_set_id_file_is_not_executed_under_a_process_limit_on_macos` (macOS: копии `/usr/bin/true` с set-user-ID и с set-group-ID перечислены вместе с `sh`; при пределе оба вызова отклоняются с `PermissionDenied` с именем файла, без предела оба работают). Файловая система, сбрасывающая бит, проваливает тест.
- Тесты macOS выполняются только в macOS, то есть только в CI; в Linux код собран для `aarch64-apple-darwin` командой `cargo clippy --release --all-targets -- -D warnings`.

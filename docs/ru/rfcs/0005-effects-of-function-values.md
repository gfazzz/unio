# RFC 0005: Эффекты функциональных значений переносятся вызовами

- Статус: proposed (реализовано в `unio check` и `unio symbol` для рассмотрения)
- Автор: проект Unio при участии Claude
- Дата: 2026-11-08
- Затрагивает: ТЗ / семантику / компилятор
- Английская версия (основная): [0005-effects-of-function-values.md](../../rfcs/0005-effects-of-function-values.md)

## Кратко

Эффекты функционального значения относятся к вызовам значения, а не к месту, где оно создано. Создание значения имеет только эффекты создания: вычисление захваченного и, для лямбды с захватом, `allocates`. Вызов через параметр функционального типа — скрытый эффект его функции; в каждом вызове этой функции скрытый эффект заменяется эффектами значения, которое передаёт вызывающий. Значение, множество возможных значений которого точно не известно, потому что оно прочитано из поля, коллекции, образца или параметра, который функция сохраняет, получает консервативное множество: все значения, которые программа туда записывает, или все функциональные значения программы, тип которых может совпасть с его типом. При `--profile=core` и в модуле слоя `core` вызов через такое значение — E0087, если хоть одно значение множества требует большего, чем core. Эффекты по-прежнему выводятся (Я-9b); нового синтаксиса нет.

## Мотивация

До этого RFC в docs/ru/semantics.md 8.4 функциональное значение учитывалось там, где оно создано: упоминание функции как значения считалось её вызовом, а тело лямбды принадлежало объемлющей функции. Для одного запуска это правило надёжно, потому что значение создаётся раньше вызова, но оно ложно для того, кто читает эффекты:

```unio
import std.files as files

function remember() returns Int:
    let reader = files.read_text
    let kept = [reader]
    return kept.length()
```

`remember` не читает файлов, но имела `files.read`, а пакет без полномочия получал E0085 за ссылку, которую никогда не вызывает. То же правило давало `List.map` пустые эффекты, а вызывающему `map` — эффекты каждой написанной им лямбды, где бы она ни вызывалась; функция, которая только возвращает лямбду, получала эффекты её тела; библиотечная функция, хранящая обратный вызов в поле, учитывалась там, где поле заполнено, часто в другом модуле. Руководитель проекта принял это правило лишь как временное ограничение, если описаны его ложные отказы и доказано, что оно покрывает каждый путь значения. Этот RFC его заменяет.

Принцип: сохранение ссылки на `files.read_text` не читает файл; это делает последующий вызов, и он должен перенести `files.read` в вызывающую функцию. То же для обратных вызовов и диспетчеризации через интерфейс.

## Почему существующих конструкций недостаточно

Конструкций не добавляется. RFC меняет то, как компилятор выводит эффекты; текст программ не меняется.

## Дизайн

### Создание значения

- Упоминание функции как значения не имеет эффектов её тела. Оно записывается как использование имени (для `unio symbol` и хешей содержимого) и добавляет функцию в множество функциональных значений программы.
- Лямбда — отдельный носитель: то, что вызывает, выделяет или использует её тело, относится к лямбде. Её создание имеет эффекты вычисления захваченного, то есть чтения локальных имён, и `allocates` со слоем `alloc`, если она захватывает локальное имя или `self` (семантика 8.4, «Выделение памяти»).

### Вызов значения

Вызов через функциональное значение имеет эффекты всех значений, которыми может быть вызываемое выражение. Компилятор отслеживает функциональные значения анализом потока по формам, которые их переносят:

| Форма | Возможные значения |
|---|---|
| Именованная функция `f`, `alias.f` | `f` |
| Лямбда | эта лямбда |
| Локальное имя | всё, что ему присвоено (`let`, `var`, присваивания) |
| Параметр текущей функции или лямбды | скрытый эффект: то, что передаёт каждый вызов |
| Константа | значения её инициализатора |
| `x.field` структуры или ошибки | всё, что записано в это поле где угодно в программе: аргументы построения, значения полей по умолчанию, присваивания |
| `f(...)` именованной `f`, возвращающей функцию | всё, что дают её инструкции `return` |
| `a if c else b` | значения обеих ветвей |
| всё остальное: элемент коллекции, имя из образца, результат вызова через значение, содержимое `Option` | любое функциональное значение программы, тип которого может быть ожидаемым типом |

Последняя строка — консервативный запасной случай. «Тип, который может совпасть» сравнивает число и типы параметров, причём обобщённые параметры, неизвестные типы и интерфейсы совпадают с любым типом; результаты и ошибки не сравниваются.

### Скрытые эффекты параметров

Внутри функции вызов через параметр `f` даёт скрытый эффект «эффекты `f`» вместо собственного эффекта. Лямбда, вызывающая параметр объемлющей функции, даёт тот же скрытый эффект этой функции, когда лямбда вызывается внутри неё. В каждом вызове функции скрытый эффект заменяется эффектами значений, которыми может быть аргумент, вычисленными у вызывающего; при отсутствии аргумента берётся значение параметра по умолчанию. Скрытый эффект, который доходит до вызывающего неразрешённым (вызывающий передаёт дальше свой параметр), остаётся скрытым у вызывающего и так поднимается до вызова, где значение названо.

```unio
function apply(f as Function[(Path) -> Text fails with IoError], p as Path) returns Text fails with IoError:
    return try f(p)

function plain() returns Text fails with IoError:
    return try apply(constant_text, Path("a"))     # эффектов нет

function reading() returns Text fails with IoError:
    return try apply(files.read_text, Path("a"))   # files.read
```

У самой `apply` эффектов нет; `unio symbol apply` показывает `argument effects: f`, а отчёт JSON — `"argument_effects":["f"]`. Функции высшего порядка библиотеки устроены так же: `List.map`, `List.filter`, `List.sorted_by`, `List.try_map` и другие имеют скрытый эффект своего обратного вызова, а вызывающий получает его эффекты. Внешняя функция библиотеки имеет скрытые эффекты всех своих параметров функционального типа, потому что их вызывает среда выполнения.

Параметр, который функция сохраняет (записывает в поле, возвращает, захватывает в лямбду, вызываемую в другом месте), ускользает: там, где его вызывают вне получившей его функции, его значения — все аргументы этого параметра во всех вызовах функции, его значение по умолчанию и, если функция сама используется как значение, любое значение типа параметра. Параметр лямбды получает любое значение своего типа.

### Интерфейсы

Вызов метода интерфейса имеет эффекты реализаций, которые могут до него дойти: только метода типа значения, когда тип известен, иначе всех реализаций метода в программе (это множество замкнуто, семантика 8.4). Скрытые эффекты реализаций становятся скрытыми эффектами метода интерфейса на том же параметре, так что обратный вызов, переданный через метод интерфейса, разрешается у вызывающего так же, как для функции.

### Консервативные случаи и профиль core

Вызов через значение, множество которого лишь оценено (поле, запасной случай таблицы, ускользнувший параметр или локальное имя, константа или результат, содержащие такое значение), надёжен, но может быть шире любого запуска. В прикладном профиле он просто получает объединение; E0085 тогда называет место: «значения, записанные в поле `app.Handler.run`», «любое значение-функция типа ...», «значения, переданные в `app.store` как `f`». При `--profile=core` и в модуле слоя `core` библиотеки такой вызов — **E0087**, если одно из его возможных значений требует слоя выше `core`: нельзя показать, что вызов остаётся в core. Функция, чья цепочка к `alloc` или `std` проходит через такой вызов, получает E0087 у вызова вместо E0084. Вызов через именованную функцию, лямбду, параметр или константу с известными значениями — не оценка и даёт E0084, как любой вызов.

### Ложные отказы консервативных случаев

Оценка может отвергнуть программу, которая никогда не делает опасного вызова:

1. **Поля объединяются по всей программе.** Если `Handler.run` в одном месте заполнено чистой `double`, а в другом — `label` (которая выделяет память), то каждый вызов `h.run(1)` требует `alloc`, даже в функции, которая получает только чистый обработчик. В профиле core этот вызов — E0087.
2. **Коллекции и образцы сводятся к типу.** `for step in steps: step(x)` при `steps as List[Function[(Int) -> Int]]` имеет все функциональные значения программы с одним параметром `Int`, включая никогда не попадавшие в список.
3. **Ускользнувшие параметры объединяют вызывающих.** Вспомогательный конструктор `make(f) returns Box`, сохраняющий `f`, даёт каждому `box.f()` значения, переданные в `make` где угодно.
4. **Значения, переданные функции, которая сама используется как значение.** Когда функция с параметром функционального типа передаётся как значение, её параметр может получить любое значение этого типа.
5. **Обобщённый код.** Значение, прочитанное там, где тип — обобщённый параметр `T`, совпадает с каждым функциональным значением программы.

Ни один из них не скрыт: цепочка E0085 или E0087 называет поле, параметр или тип, по которому сделана оценка, а исправление — вызвать именованную функцию или параметр либо хранить в этом месте только функции core.

### Почему пути покрыты

Функциональное значение существует, только если функция названа как значение или вычислена лямбда, и оба случая записываются. Значение перемещается только формами таблицы: связыванием, присваиванием, аргументом, `return`, записью в поле или операцией над коллекцией или образцом. Каждая из них либо отслеживается точно, либо сводится к типу, чьё множество содержит каждое значение программы, тип которого может быть типом в этом месте, так что значение, которое вызывает запуск, входит в множество, используемое проверкой. Скрытый эффект заменяется в каждом вызове своей функции; если вызов идёт через значение, аргументы не известны и используется множество ускользнувших значений. Анализ — неподвижная точка над конечными множествами, поэтому он завершается.

## Миграция

Не нужна. Программы, получавшие E0085 или E0084 лишь за создание значения, которое они не вызывают, принимаются. Отвергнутой программа может стать только через консервативный случай выше; в репозитории ни одна программа не изменилась (см. «Проверка»).

## Альтернативы

- **Аннотации эффектов в типах функций** (`Function[(Path) -> Text uses files.read]`). Объявленные эффекты сделали бы каждый случай точным, но Я-9b не допускает эффекты в сигнатурах, а слово `uses` зарезервировано для будущего решения; аннотация потребовала бы также работы с грамматикой и корпусом. Вывод выше покрывает случаи библиотеки и эталонных программ, а оценка видна там, где сделана.
- **Оставить учёт в месте создания.** Надёжно для одного запуска, но описывает не ту функцию и отвергает ссылки, которые никогда не вызываются; руководитель проекта не принимает это как окончательное правило.
- **Запасной случай по типу и для полей.** Первый вариант давал каждому чтению поля объединение всех функциональных значений типа поля. Отслеживание записей каждого поля так же надёжно (каждая запись в поле — построение, значение по умолчанию или присваивание) и гораздо точнее: `std.files` хранит системные вызовы в полях, и объединение по типу смешивало шаги чтения и записи библиотеки.
- **Контекстно-чувствительный анализ замыканий.** Лямбда, возвращённая из функции, могла бы помнить аргументы этого вызова. Это убрало бы ложный отказ 3 для замыканий ценой гораздо большего анализа; его можно добавить позже, не меняя правила.

## Проверка

- `compiler/unio/tests/symbol.rs`: сохранённое функциональное значение не имеет эффектов; `apply` переносит эффекты своего аргумента вызывающему, с цепочкой E0085 `app.reading -> app.apply (argument f) -> std.files.read_text`; `List.map`, `List.sorted_by` и `List.try_map` переносят эффекты обратного вызова вызывающему и показывают `argument effects`; вызов через поле структуры имеет записанные значения, а в профиле core — E0087, если одно из них выделяет память; тело возвращённой лямбды учитывается там, где она вызывается, а лямбда с захватом по-прежнему выделяет память там, где создана; константа с лямбдой и значение параметра по умолчанию учитываются там, где вызываются.
- В каталоге есть E0087 с примером и исправлением (`compiler/unio/tests/catalog.rs`).
- `unio check` для стандартной библиотеки, примеров, инструментов и `spec/tests/semantic/valid` даёт тот же результат, что и раньше: ни одна программа не стала отвергнутой.
- docs/ru/semantics.md 8.4 формулирует правило; compiler/README.md перечисляет оставшиеся ограничения.

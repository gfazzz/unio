# Unio: доработанная концепция

Версия: 0.6. Изменения относительно 0.5: слои библиотеки и профили сборки, план системного программирования (раздел 8.1).

Изменения относительно 0.4: запись файлов сохраняет гарантии после отключения питания на названных файловых системах, а компилятор и инструменты пакетов работают изолированно (разделы 3.3, 6).

Изменения относительно 0.3: язык создаётся на самом языке (раздел 1.1); песочница обязательна (раздел 6), правило вызова функции с `fails with` одинаково в любой позиции (раздел 3.2), гарантии при завершении разделены по видам (разделы 3.3, 4.1), значения никогда не разделяются между именами (раздел 2.7), варианты с совпадающим именем пишутся полностью (раздел 2.6). Этот документ уточняет исходную концепцию из README и фиксирует решения, без которых нельзя начинать реализацию. Открытых вопросов нет; обоснование последних решений — в разделе 11.

## 1. Назначение и принцип

Unio — язык общего назначения, который:

- легко читает человек, в том числе не автор кода;
- удобно генерирует ИИ, потому что словарь конструкций мал, стиль один, а ошибки компилятора точны и машиночитаемы;
- можно строго проверить до выполнения: типы, ошибки, ресурсы и побочные эффекты видны в сигнатурах.

Главный принцип: **понятный код, явное поведение, контролируемые ресурсы**.

Следствия принципа, которыми проверяется каждое решение по языку:

1. Одна задача — один способ записи. Если есть два способа, один объявляется стандартным, форматтер приводит к нему.
2. Ничего не происходит неявно: нет неявных преобразований типов, нет состояния, тайно общего у разных имён, нет скрытых исключений.
3. Сигнатура функции — полный контракт: вход, результат, ошибки, а позднее и эффекты.
4. Всё, что может пойти не так, либо выражено типом (`Option`, `fails with`), либо является аварией (fault) с определённым поведением.

### 1.1 Язык создаётся на самом языке

Unio разрабатывается на Unio везде, где это возможно: стандартная библиотека, инструменты проекта, эталонные утилиты, а к 1.0 и компилятор. Каждый пробел, найденный по ходу, закрывается в языке или в библиотеке, и улучшенный язык используется для следующей части. Так язык рекурсивно улучшает сам себя, и каждое решение проверяется на настоящем коде до того, как будет зафиксировано.

Где Unio пока применить нельзя, работу делает временная реализация на другом языке, и она удаляется, как только Unio может её заменить: компилятор и среда выполнения написаны на Rust до самостоятельной реализации, проверяющие скрипты в `spec/` — на Python, пока интерпретатор этапа 3 не начнёт выполнять их версии на Unio из `tools/`. Для части на другом языке нужны названная причина и названный срок.

Это уже окупилось: при написании стандартной библиотеки и проверяющих инструментов на Unio обнаружились явная фиксация атомарных файлов, контекстные ключевые слова, `pass`, модули пакета и недостающие функции библиотеки; всё это решено в версии 0.4.

## 2. Синтаксис

### 2.1 Общие правила

- Блоки задаются отступами в 4 пробела. Табуляция запрещена.
- Заголовок блока заканчивается двоеточием.
- Ключевые слова — английские слова целиком, без сокращений: `function`, `returns`, `fails with`, `struct`, `interface`, `enum`, `match`, `case`. Слова `error`, `external`, `module`, `test` и `unsafe` — ключевые только там, где начинается объявление; в остальных местах это обычные имена, поэтому поле может называться `error`.
- Идентификаторы: `snake_case` для функций, переменных, полей и модулей; `PascalCase` для типов. Форматтер и компилятор предупреждают об отклонениях.
- Комментарии начинаются с `#`. Документирующие комментарии начинаются с `##` и стоят перед объявлением.
- Исходные файлы в UTF-8, расширение `.unio`.

### 2.2 Объявления значений

```unio
let limit = 10            # неизменяемое значение, тип Int выведен
var count = 0             # изменяемая переменная
count = count + 1

let name as Text = read_line()   # явная аннотация допускается
```

Правило: `let` по умолчанию. `var` обязателен для всего, что переприсваивается. Поля структур неизменяемы, если не помечены `var`.

### 2.3 Функции

```unio
## Возвращает приветствие для имени.
function greet(name as Text) returns Text:
    return "Привет, {name}!"

function active_names(users as List[User]) returns List[Text]:
    return [user.name for user in users if user.active]

function log(message as Text):        # без returns — ничего не возвращает
    print(message)
```

- Параметры всегда аннотированы типом. Тип результата всегда указан, если функция что-то возвращает. Выводятся только типы локальных значений.
- Аргументы передаются позиционно или по имени: `connect(host, port = 8080)`. Значения по умолчанию допускаются только для параметров в конце списка.
- Функции — значения первого класса. Тип функции: `Function[(Int, Text) -> Bool]`. Анонимная функция: `function (x as Int) returns Int: x * 2`, однострочная форма.

### 2.4 Текст и операторы

- Интерполяция `"{expression}"` — стандартный способ собрать текст. Внутри фигурных скобок — любое выражение, значение которого реализует `Display`.
- Оператор `+` определён для чисел и для `Text + Text`. Смешивание типов (`Text + Int`) — ошибка компиляции с подсказкой использовать интерполяцию. Так привычная запись сохраняется, а неявных преобразований нет.
- Арифметика: `+ - * / %` и `**`. `/` для `Int` даёт `Int` с усечением, для `Float` — `Float`. Переполнение `Int` — авария (см. 4.3), не тихое зацикливание.
- Сравнения `== != < <= > >=`, логика `and or not`. Логические операторы — слова, чтобы код читался как текст.
- Проверка членства: `item in collection`, что вызывает `collection.contains(item)`.
- Операторы привязаны к стандартным интерфейсам: `+` к `Add`, `-` к `Subtract`, `*` к `Multiply`, `/` к `Divide`, `==` к `Equal`, `<` и остальные сравнения к `Order`. Встроенные числа и `Text` реализуют их. Пользовательский тип получает оператор только явным объявлением `extend Money with Add`; скрытых реализаций и неявных преобразований нет. Операторы нельзя переопределять для типов, которые уже их реализуют.

### 2.5 Управление потоком

```unio
if count > limit:
    stop()
else if count == limit:
    warn()
else:
    continue_work()

for user in users:
    print(user.name)

for index, user in users.enumerate():
    print("{index}: {user.name}")

while not queue.is_empty():
    process(queue.pop())

match command:
    case Add(item):
        items.append(item)
    case Remove(id) if id > 0:
        items.remove(id)
    case Quit:
        return
```

`match` обязан быть полным: компилятор проверяет, что перечислены все варианты, либо есть `case _`. Ветка, которая намеренно ничего не делает, говорит об этом через `pass`; пустой блок — ошибка.

### 2.6 Типы данных

```unio
struct User:
    id as Int
    name as Text
    var active as Bool = true

enum Command:
    Add(item as Text)
    Remove(id as Int)
    Quit

interface Display:
    function to_text(self) returns Text

extend User with Display:
    function to_text(self) returns Text:
        return "{self.name} (#{self.id})"
```

- `struct` — запись с именованными полями, создаётся как `User(id = 1, name = "Анна")`. Значения-структуры сравниваются по содержимому.
- `enum` — тип-сумма с вариантами, у вариантов могут быть поля. Используется для команд, состояний, результатов разбора.
- `interface` — набор методов. Реализация объявляется явно через `extend ... with ...`. Наследования реализаций нет; переиспользование — через композицию и обобщённые функции.
- Обобщения: `function first[T](items as List[T]) returns Option[T]`. Ограничения: `[T with Display]`.

Встроенные типы ядра: `Int` (64 бит со знаком), `Float` (64 бит), `Bool`, `Text`, `Bytes`, `List[T]`, `Map[K, V]`, `Set[T]`, `Option[T]`, `Tuple`, `Path`, `Function` и `Never` — тип результата функции, которая не возвращает управление (`assert_fail`).

Варианты перечислений записываются как `Command.Add(...)`. Краткая форма `Add(...)` допустима, если в модуле больше не видно ничего с таким именем. Поэтому вариант с именем типа пишется полностью: `Value.Text("Anna")`, а вариант `List` перечисления `Command` нельзя записать одним словом.

Равенство:

- `struct` и `enum` сравниваются по содержимому, если все поля реализуют `Equal`; реализация выводится автоматически и может быть заменена явной.
- `Float` реализует `Equal` и `Order` по IEEE 754: `nan == nan` даёт `false`, сравнения с `nan` дают `false`. `Float` не реализует `Hash`, поэтому не может быть ключом `Map`, элементом `Set` и образцом в `match`. Для сортировки и ключей есть `float.total_order()`, для проверки `float.is_nan()`.
- Ресурсы (раздел 4) не реализуют `Equal`: `==` для них — ошибка компиляции. Тождественность проверяется функцией `is_same(a, b)`. Так читатель не спутает сравнение содержимого файлов со сравнением дескрипторов.
- `Decimal` (точная десятичная арифметика для денег) — не встроенный тип, а структура в `std.decimal`, реализующая `Add`, `Subtract`, `Multiply`, `Divide`, `Equal`, `Order`, `Hash`. Создаётся явно: `Decimal("19.99")`; литералов для него в ядре нет. Это сохраняет малый словарь ядра и привычную запись `price * quantity`.

### 2.7 Изменяемость и значения

- Структуры, перечисления, коллекции и текст — значения. Связывание, передача, возврат и сохранение никогда не делят изменяемое состояние: изменение через одно имя не видно через другое.
- Значение меняется только через место, которое начинается с `var`-имени или `var`-параметра, а поле меняется, только если объявлено `var`. Имена, введённые `let`, образцами и `for`, неизменяемы:

```unio
var tasks = load()
match tasks.find_index(function (task as Task) returns Bool: task.id == id):
    case some(index):
        tasks[index].done = true        # меняет список
    case none:
        fail NotFound(id = id)
```

  Запись `task.done = true` для задачи из `case some(task)` — ошибка компиляции с подсказкой менять элемент через коллекцию.
- Изменяющие методы (`append`, `remove`, `sort`) доступны только на `var`-местах и помечены в документации.
- Функция изменяет аргумент только через параметр, объявленный `var name as List[Int]`; вызывающий передаёт `var`-переменную, и одну переменную нельзя передать в два `var`-параметра одного вызова.
- Анонимные функции захватывают значения в момент создания и не могут присваивать захваченным переменным.
- Ресурсы — не значения: у них есть тождественность, они никогда не копируются (раздел 4).

Значения разделяются, пока не изменены; изменение разделённого значения копирует только меняющийся уровень, изменение неразделённого выполняется на месте. Никакая копия не меняет поведение программы, а стоимость копий измеряется. Читатель, видя `var` в сигнатуре, знает, что функция меняет переданное состояние, а видя `let` — что значение не изменится вовсе.

Состояние, которое вместе меняют несколько функций, оформляется структурой с методами `var self`: `reader.advance()` меняет читателя, и каждое место изменения видно в вызове. Передача того же состояния через `var`-параметры тоже работает, но длиннее.

## 3. Отсутствующие значения и ошибки

### 3.1 Option

```unio
function find_user(id as Int) returns Option[User]:
    for user in users:
        if user.id == id:
            return some(user)
    return none

let user = find_user(7) or default_user
let name = find_user(7)?.name            # Option[Text]

match find_user(7):
    case some(user):
        print(user.name)
    case none:
        print("не найден")
```

`Option[T]` — обычный `enum` с вариантами `some(value)` и `none`. Нет `null`. Оператор `or` на `Option` даёт значение по умолчанию; `?.` пробрасывает `none` по цепочке.

### 3.2 Ошибки в сигнатуре

```unio
error IoError:
    path as Path
    reason as Text

error ParseError:
    line as Int
    message as Text

function read_config(path as Path) returns Config fails with IoError, ParseError:
    let text = try read_text(path)                 # IoError пробрасывается
    let parsed = try parse_toml(text)              # ParseError пробрасывается
    return Config.from(parsed)
```

Правила:

1. `error` объявляет тип ошибки, это структура с полями. Ошибки — значения, не исключения.
2. Функция, которая может завершиться ошибкой, перечисляет их после `fails with`. Множество ошибок — часть типа функции.
3. `fail IoError(path = path, reason = "нет доступа")` завершает функцию ошибкой.
4. Вызов функции с `fails with` без обработки — ошибка компиляции. Есть два способа обработать:
   - префикс `try` перед вызовом: ошибка пробрасывается вызывающему, который должен перечислить её в своём `fails with`;
   - блок `try:` с обработчиками `on`.

   Правило одинаково в любой позиции: в инструкции, в инициализаторе, в аргументе, в субъекте `match`. Вызов функции с `fails with` сам по себе никогда не превращается в `Result`.

```unio
try:
    let config = read_config(path)
    run(config)
on IoError as e:
    print("Не удалось прочитать {e.path}: {e.reason}")
on ParseError as e:
    print("Строка {e.line}: {e.message}")
```

5. Компилятор проверяет, что каждая ошибка из `fails with` вызываемой функции либо обработана в `on`, либо есть в `fails with` текущей функции. Обработчик `on Error as e` ловит любую ошибку; `Error` — общий интерфейс всех ошибок с методом `to_text`.
6. Для скриптов и прототипов допустима сигнатура `fails with Error`: конкретный набор не фиксируется, но факт возможной ошибки всё равно виден.
7. Для функций, где ошибка нужна как значение, есть тип `Result[T, E]` с вариантами `ok(value)` и `error(value)`; `try` работает и с ним. `Result` существует только там, где функция объявляет его результатом или значение построено явно. В стандартной библиотеке `Result` используется только там, где ошибки надо хранить или передавать дальше. Переход от `fails with` к `Result` записывается явно:

```unio
function parse_safely(arguments as List[Text]) returns Result[Command, UsageError]:
    try:
        return ok(parse_command(arguments))
    on UsageError as e:
        return error(e)
```

8. Блок строчного обработчика `try ... on E as e:` не завершается обычным образом: он заканчивается `return`, `fail`, `break`, `continue` или вызовом, который не возвращает управление (`assert_fail`). Поэтому значение выражения — всегда успешный результат.

### 3.3 Аварии (faults)

Авария — нарушение контракта, которое нельзя обработать внутри программы: индекс вне диапазона при `items[i]`, деление на ноль, переполнение `Int`, нарушение `assert`.

- Поведение определено: программа печатает диагностику с трассой стека в stderr, среда выполнения раскручивает стек и вызывает `release` для открытых блоков `using` в обратном порядке, программа завершается с кодом 101.
- Исчерпание памяти (кучи или стека) — не авария. Среда выполнения не может обещать выполнение пользовательского кода, когда памяти нет, поэтому пишет заранее подготовленную диагностику и завершается с кодом 102 без вызова `release`. То же относится ко всему, что вне её контроля: сигналу уничтожения, отключению питания, падению внешнего кода.
- Что переживает любое завершение, сказано отдельно. Файл, записанный через `files.write_text` или через `files.open_atomic` с фиксацией, заменяется атомарно: читатель видит либо старое, либо новое полное содержимое, потому что запись идёт во временный файл, который заменяет целевой переименованием. Данные попадают на носитель до переименования, поэтому это верно и после отключения питания; `durable = true` добавляет, что новое содержимое переживёт отключение питания, как только вызов вернул управление. Гарантии обещаются для названных файловых систем (ext4, XFS, Btrfs, APFS, NTFS); на остальных запрос `durable` завершается ошибкой, а не делает вид.
- Аварию нельзя поймать через `on`. Её можно наблюдать только в тестах (`expect_fault`) и на границе процесса.
- Для каждой аварийной операции есть безопасная форма с `Option` или ошибкой: `items.get(i)`, `a.checked_divide(b)`, `a.checked_add(b)`.

Так ошибки предметной области и дефекты программы различаются синтаксически, и читатель видит, что именно может произойти.

## 4. Память и ресурсы

### 4.1 Две модели

- **Управляемые значения.** Структуры, коллекции, текст, замыкания живут в куче под управлением GC. Программист не думает об их освобождении.
- **Ресурсы.** Файлы, сокеты, процессы, дескрипторы устройств, а в вычислительном расширении — тензоры и буферы GPU. У них есть явная область жизни.

Граница между моделями: тип реализует интерфейс `Resource` (метод `release`) — значит это ресурс. Такое значение:

- создаётся в блоке `using` или в поле другого ресурса;
- освобождается при выходе из блока, в обратном порядке создания, в том числе при ошибке и аварии (но не при исчерпании памяти и внештатном завершении, см. 3.3);
- не может быть сохранено в обычную структуру или коллекцию, пережившую блок, — это ошибка компиляции. Если ресурс нужно хранить, владелец сам объявляется `Resource` и освобождает его в `release`.

```unio
function count_lines(path as Path) returns Int fails with IoError:
    using file = try open_file(path):
        var count = 0
        for line in file.lines():
            count = count + 1
        return count
```

### 4.2 Что входит в первый выпуск

Первый выпуск содержит GC и ресурсы с `using`. GC относится к слоям `alloc` и `std`; `core` от него не зависит, чтобы код без GC оставался возможным (раздел 8.1). Бюджеты памяти, области жизни для тензоров и учёт завершения вычислений GPU относятся к вычислительному расширению и проектируются поверх того же интерфейса `Resource`: тензор — ресурс, область жизни — ресурс-владелец с бюджетом.

### 4.3 Сборщик мусора

- Точный (precise), трассирующий, неперемещающий в первой версии. Простота отладки важнее пиковой пропускной способности.
- Паузы ограничены для CLI-нагрузок; измеряется и публикуется.
- `Resource` не зависит от GC: освобождение детерминировано и не ждёт сборки.

## 5. Модули и пакеты

```unio
import std.files
import std.json as json
from std.text import split, join

let data = json.parse(text)
```

- Модуль — файл. Пакет — каталог с манифестом `unio.toml`. Имя модуля совпадает с путём файла.
- Видимость: всё приватно по умолчанию; экспорт через `public` перед объявлением.
- Зависимости фиксируются в `unio.lock` с хешами содержимого. Сборка без сети воспроизводима.
- Один стандартный способ импорта и один порядок (форматтер сортирует).

## 6. Безопасность

- Весь код первого выпуска написан в безопасном подмножестве: нет указателей, нет ручного управления памятью, проверки границ, инициализированные значения.
- Небезопасные операции появляются только во внешних функциях (`external function`, FFI) и только в модулях, помеченных `unsafe module`. Такие модули перечисляются в манифесте и отображаются при установке зависимости.
- Минимальные полномочия: манифест объявляет, что пакету нужно (`files` с путями для чтения и записи, `env` с именами переменных, `process` с именами программ, `network`). Компилятор запрещает использовать модули стандартной библиотеки вне объявленных полномочий. Это даёт читателю ответ на вопрос «что эта программа может сделать» до запуска.
- Обязательная песочница: те же полномочия при выполнении ограничивает операционная система (Landlock и seccomp в Linux, Seatbelt в macOS, AppContainer в Windows). Оператор может дополнительно сузить их внешней политикой (`--policy` или `UNIO_POLICY`) и задать лимиты памяти, времени и процессов; программа расширить их не может. Если нужного механизма нет, программа не запускается, пока оператор явно не разрешит более слабую песочницу. Проверка компилятора сообщает читателю, что программа намерена делать; песочница ограничивает, что она может сделать, даже если ошиблись проверка, компилятор или стандартная библиотека. Это важнее всего для запуска кода, созданного ИИ.
- Инструменты тоже изолированы: `check`, `build`, языковой сервер и операции с пакетами выполняются в рабочих процессах, которые могут читать только проект и его зафиксированные зависимости, писать только в каталог сборки и не имеют сети (кроме процесса загрузки, ограниченного настроенными реестрами). Компилятор никогда не выполняет код проекта, поэтому открыть или собрать недоверенный проект не опаснее, чем прочитать его.
- Эффекты отдельных функций в сигнатуре (`uses files`) в первом выпуске не объявляются. Компилятор выводит эффекты из графа вызовов и показывает их в `unio symbol` и в документации: читатель и ИИ видят, что функция обращается к файлам или процессам, без роста словаря языка. Слово `uses` зарезервировано для вычислительного расширения (`uses gpu`), где эффект влияет на планирование ресурсов, а не только на полномочия.
- Зависимости: подпись реестра, проверка хешей, предупреждение о `unsafe module`, запрет сетевых действий во время сборки.
- Выпуск: воспроизводимая сборка, подписанные артефакты, SBOM.
- Отдельные тесты надёжности: поведение при нехватке памяти, при аварии внутри `using`, при ошибке во внешнем коде.

## 7. Работа с ИИ

Что получает ИИ-агент от инструментов:

1. **Диагностика в JSON**: код ошибки, диапазон в файле, сообщение, объяснение, предлагаемые исправления в виде патчей, связанные символы. Та же информация, что видит человек, без разбора текста.
2. **Контекст символа**: `unio symbol app.users.find_user` возвращает сигнатуру, документацию, места использования, тип результата и набор ошибок.
3. **Проверка без сборки**: `unio check` за время, достаточно малое для цикла «сгенерировал — проверил — исправил».
4. **Один стиль**: `unio fmt` делает сгенерированный код неотличимым от написанного человеком, поэтому ревью смотрит на смысл, а не на оформление.
5. **Тесты рядом с кодом**: `test "описание":` блоки в том же файле, запуск `unio test --json`.

Что требуется от ИИ: описывать намерение в документирующих комментариях и тестах; код остаётся однозначным.

## 8. Вычисления для ИИ и квантовое расширение

Не входят в первый выпуск. Ограничения на ядро, чтобы расширения были возможны:

- тип `Resource` и `using` достаточны для тензоров и областей жизни;
- обобщения и интерфейсы достаточны для операций над тензорами разных типов и устройств;
- в сигнатуры можно будет добавить эффекты (`uses gpu`) без изменения существующего синтаксиса;
- профилировщик проектируется с общим форматом событий, куда позднее добавятся RAM/VRAM.

Квантовый модуль: схемы как значения, симулятор как backend, оборудование через тот же интерфейс backend с описанием возможностей. Ускорение не обещается; гарантируется проверяемость схемы до запуска.

### 8.1 Системное программирование: слои библиотеки и профили сборки

Веб-сервер, а также службы и приложения операционной системы — обычные программы: им нужны сеть и конкурентность (выпуск 0.2), а не другой язык. Ядро — другое дело: обычная программа получает память, файлы, потоки и изоляцию от операционной системы, а ядро должно создавать их само. Unio поддерживает обе работы как один язык.

**Слои библиотеки.** Стандартная библиотека и среда выполнения разделены на три слоя, и модуль может пользоваться только своим слоем и предшествующими:

- `core` — базовые типы и операции, которым не нужны ни аллокатор, ни GC, ни операционная система;
- `alloc` — то, чему нужен аллокатор (текст, создаваемый при выполнении, списки, словари, JSON); в 0.1 аллокатор — куча GC;
- `std` — то, чему нужна операционная система (файлы, окружение, процессы, стандартный вывод, песочница).

Имена модулей не содержат слоя (`std.json` находится в `alloc`), поэтому приложения это не затрагивает; слой — свойство места, где лежит модуль, и он проверяется.

**Профили сборки.** Профиль выбирает доступные слои. Профиль `application` содержит все три слоя, GC и песочницу операционной системы. Профиль `system` всегда содержит `core`, содержит `alloc` только с аллокатором, который предоставляет программа, и не содержит ни GC, ни `std`. Синтаксис, типы и обработка ошибок во всех профилях одинаковы; профиль только убирает возможности и никогда не меняет смысл конструкции. Если функции нужен слой, которого в профиле нет, компилятор сообщает цепочку вызовов, которая к нему ведёт. Выпуск 0.1 реализует профиль `application` и проверку `unio check --profile=core`, подтверждающую, что пакет зависит только от `core`.

**Что добавляет системное расширение.** Эти возможности проектируются через RFC для одного из следующих выпусков и доступны только в профиле `system`, а где указано — только в файлах `unsafe module`:

1. Предсказуемая память: явно принадлежащие буферы, размещение данных в заданных областях, работа без GC и участки, где копирование при изменении запрещено: компилятор сообщает о каждом месте, где может возникнуть копия, потому что неожиданная копия большого массива там недопустима.
2. Контроль представления: размеры и выравнивание структур, аппаратные регистры, таблицы страниц, соглашения вызова и размещение секций исполняемого файла.
3. Контролируемый низкоуровневый доступ: указатели, устройства, отображённые в память, специальные инструкции процессора и небольшой объём ассемблера — только в файлах `unsafe module`.
4. Прерывания и синхронизация: обработчики прерываний, атомарные операции и определённая модель памяти, согласованная с конкурентностью выпуска 0.2. Доступ `volatile` и синхронизация между потоками — разные операции.
5. Проверяемые ограничения: функция может потребовать, чтобы она не выделяла память, не блокировалась и не обращалась к GC, и компилятор проверяет всю цепочку вызываемых функций, а не только тело. Это опирается на выведенные эффекты раздела 6 (`allocates` выводится начиная с 0.1) и проектируется вместе с `uses`.

**Гарантии.** Песочница приложения опирается на операционную систему. Ядро на реальном оборудовании само управляет привилегиями и изоляцией, поэтому его низкоуровневая часть входит в доверенную основу. Первые эксперименты выполняются в виртуальных машинах.

**Первая операционная система на Unio** — небольшое ядро со службами в отдельных процессах, чтобы большинство компонентов оставались на безопасном Unio, а аппаратная сложность сосредоточилась в небольшой части. Первый проверяемый прототип — цепочка: готовый загрузчик, вход в код Unio, вывод в последовательный порт, управление страницами памяти, таймер, простейший планировщик, пользовательский процесс и системный вызов. Небольшой стартовый слой на Rust или ассемблере допустим по правилу раздела 1.1, с названными причиной и сроком. Поддерживает ли Cranelift нужные соглашения вызова и формат бинарного файла, проверяется ранним прототипом. Операционная система с драйверами и совместимостью уровня Linux — многолетний проект, в котором язык — небольшая часть, и в планы развития языка она не входит.

GC не делает операционную систему невозможной: он может обслуживать службы и некоторые подсистемы. Ранней загрузке, обработчикам прерываний и критическим участкам нужна независимая модель памяти профиля `system`; полностью управляемое ядро сделало бы свою среду выполнения отдельным сложным проектом.

## 10. Решённые вопросы

| Вопрос | Решение |
|---|---|
| `+` для текста | Разрешён только `Text + Text`, стандарт — интерполяция |
| Как связаны `Option`, `fails with`, `Result` | `Option` — отсутствие значения; `fails with` — ошибка функции; `Result` — ошибка как хранимое значение; `try` работает с двумя последними |
| Что происходит при `items[i]` вне диапазона | Авария с кодом 101, непоймаемая; безопасная форма `get` |
| Вызов функции с `fails with` без `try` | Ошибка компиляции в любой позиции, включая субъект `match`; неявного `Result` нет |
| Нехватка памяти | Не авария: код 102, пользовательский код не выполняется; файлы защищены только атомарной записью |
| Ограничение полномочий | Обязательная песочница ОС, сужаемая внешней политикой; закрывается при отказе |
| На чём написаны язык и его инструменты | На Unio везде, где возможно (раздел 1.1); на другом языке только временно, с причиной и сроком |
| Ядра и код без операционной системы | Один язык: слои библиотеки `core`, `alloc`, `std` и профили сборки, которые только убирают возможности; системные возможности — в одном из следующих выпусков (раздел 8.1) |
| Граница GC и ресурсов | Тип реализует `Resource` — значит ресурс, живёт в `using` |
| Формат ошибок компилятора | JSON с кодом, диапазоном, объяснением и патчем; фиксируется в ТЗ до первого выпуска |
| Параллельность в ядре | Нет. Ядро не содержит общего изменяемого состояния между потоками, чтобы модель параллельности добавлялась позднее без ломки |
| `Decimal` в ядре | Нет. `std.decimal` как структура со стандартными операторными интерфейсами; создание явное `Decimal("19.99")` |
| Операторы для пользовательских типов | Только через явное `extend T with Add` и другие стандартные интерфейсы; переопределение существующих реализаций запрещено |
| Эффекты в сигнатуре | В 0.1 нет: полномочия на уровне пакета, эффекты функций выводятся компилятором и показываются в `unio symbol`. `uses` зарезервировано для 0.3 |
| `==` для `Float` | IEEE 754; `Float` без `Hash`, не ключ и не образец `match`; `total_order()` и `is_nan()` |
| `==` для ресурсов | Ошибка компиляции; тождественность через `is_same(a, b)` |
| Изменение значения, найденного в коллекции | Значения, а не общие ссылки: изменять через коллекцию, `tasks[index].done = true`; имена из образцов и циклов неизменяемы |
| Вариант с именем типа | Краткая форма только при однозначном имени; иначе `Enum.Variant` |
| Слова вроде `error` и `test` как имена | Контекстные ключевые слова: особые только там, где начинается объявление |
| Ветка, которая ничего не делает | `pass`; пустой блок остаётся ошибкой |
| Язык реализации компилятора | Rust с генерацией кода через Cranelift в 0.1; самостоятельная реализация на Unio к 1.0, когда язык стабилен |

## 11. Обоснование последних решений

Решения по вопросам, открытым в версии 0.1 концепции, выведены из принципа «понятный код, явное поведение, контролируемые ресурсы». Пункты 6–14 добавлены в версии 0.4 после рецензии и после написания стандартной библиотеки на Unio.

1. **`Decimal` вне ядра.** Малый словарь конструкций важнее удобства одной предметной области. Привычная запись арифметики сохраняется, потому что операторы привязаны к интерфейсам, а не к встроенным типам. Явное `Decimal("19.99")` исключает скрытое округление при смешении с `Float`.
2. **Эффекты без синтаксиса.** Полномочия пакета уже отвечают на вопрос «что программа может сделать». Эффекты функций полезны читателю и ИИ, но их можно вычислить, а не требовать записывать; так сигнатуры остаются короткими, а информация не теряется. Когда эффект начнёт влиять на выполнение (GPU), он станет частью сигнатуры через `uses`.
3. **`Float` по IEEE 754.** Отклонение от стандарта сделало бы численный код неожиданным для всех, кто знает другие языки. Опасные места закрыты запретом `Hash` и образцов `match`, а не изменением семантики оператора.
4. **Ресурсы без `==`.** У сравнения дескрипторов нет очевидного смысла для читателя: это содержимое или тождество? Ошибка компиляции с подсказкой `is_same` делает выбор явным.
5. **Rust и Cranelift.** Безопасное подмножество Unio опирается на безопасный компилятор: Rust даёт это без ручной проверки памяти. Cranelift обеспечивает быструю и детерминированную сборку, что важнее пиковой оптимизации для утилит CLI и для цикла «сгенерировал — проверил». LLVM может стать вторым backend для `--release`, если бенчмарки выпуска 0.2 этого потребуют. Самостоятельная реализация переносится на 1.0: писать компилятор на языке, который ещё меняется, значит переписывать его дважды.
6. **Песочница как требование, а не опция.** Полномочия в манифесте проверяет компилятор, но проверка компилятора защищает только от того, что он понимает. Код, написанный ИИ, запускают часто и проверяют бегло, поэтому последствия ошибки должна ограничивать операционная система. Закрытие при отказе не даёт отсутствующей функции ядра незаметно отключить песочницу.
7. **Честные гарантии при завершении.** Для `release` нужны память и работающая среда выполнения — именно их и нет после исчерпания памяти или сигнала уничтожения. Большие обещания нельзя было бы проверить; атомарная замена файлов даёт гарантию, которая не зависит от того, как завершилась программа.
8. **Значения вместо общих ссылок.** Если бы имя из `case some(task)` могло изменить элемент списка, читателю пришлось бы отслеживать все псевдонимы, чтобы понять, что меняет строка. Со значениями изменение видно только через место, где оно записано, — это то свойство, которое больше всего нужно проверяющему сгенерированный код. Разделение до изменения удерживает стоимость низкой.
9. **Полные имена вариантов при совпадении.** `return List` читается как тип, а не как команда. Краткая форма сохраняется там, где она однозначна, потому что делает `match` читаемым; где нет — компилятор добавляет имя перечисления.
10. **Контекстные ключевые слова.** Читатель никогда не видит `error` или `test` там, где подходят оба смысла: как ключевые слова они начинают объявление верхнего уровня, где выражение стоять не может. Контекстность сохраняет естественные имена для полей и переменных, что важнее единообразного правила для лексера.
11. **`pass` вместо пустых блоков.** Пустой блок выглядит как недописанный код; `pass` говорит, что бездействие задумано. Слово знакомо по Python и не добавляет новой идеи.
12. **Общее состояние через методы `var self`.** Значения делают каждое изменение видимым там, где оно записано. Цена — изменяемое состояние надо называть в каждом вызове; структура с методами `var self` сохраняет явность без повторения параметров.
13. **Язык на самом языке.** Решения, проверенные только на примерах, упускают то, что нужно большой программе; библиотека и инструменты на Unio — именно такие программы, и они всё равно нужны. Когда они сначала пишутся на Unio, каждое неудобное место становится конкретной находкой, а цена временной второй реализации ограничена сроком до появления интерпретатора.
14. **Слои и профили сейчас, системные возможности позже.** Разделить библиотеку и среду выполнения дёшево, пока они маленькие, и дорого, когда от них зависят приложения; проверка слоёв с самого начала не даёт `core` обрасти скрытыми зависимостями от аллокатора, GC и операционной системы. Сами системные возможности требуют тщательного проектирования и не помогают первому выпуску, поэтому ждут своего выпуска, а эти две границы сохраняют путь открытым — в том числе для встраиваемых устройств и высокопроизводительных вычислений.

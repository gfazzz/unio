# Static semantics of Unio 0.1

Version 0.1-draft. Changes in this draft: decisions recorded while implementing S3 (1.3, 1.4, 2.5, 2.7, 2.8, 4.1) and S4 (6.5, 6.6, 7.2, 8.2, 8.3), the conservative derivation of effects through interfaces, function values and allocating expressions (8.4), and the cases of the RFC 0001 codes E0045 to E0048 with the new E0086 (1.9, 2.9, 3.3, 3.8, 4.2, 4.9, 8.5), and the effects of function values carried by calls with the new E0087 (8.4, RFC 0005, proposed), and the cases that the R-10 control set found unchecked or reported twice (1.2, 1.3, 2.1, 3.6, 6.3, 7.2), and the check of the manifest by `unio check` with the new E0088 (8.6), which the R-10 model trial found missing, and E0085 for a package without `[permissions]` or without a manifest (8.3) and the comparison of `unsafe_modules` with the marked modules with the new E0089 (8.6), both found by the status audit of `9ba5d43`. Russian localization: [ru/semantics.md](ru/semantics.md). Basis: concept sections 2–6, requirements L-1 to L-33, [language-contracts.md](language-contracts.md), RFC 0001 and RFC 0002. This document is the reference that `unio check` implements in sprints S3 and S4 of the plan; where it and the requirements disagree, the requirements win and this document is corrected.

`unio check` runs every check on a whole package and reports every error it finds, not only the first (C-2). Each rule below names its diagnostic. Codes E0051 to E0089 are allocated here; the column "Sprint" says when the compiler starts to report them. Name and type checks run only when every module of the program parses: syntax errors are reported first.

## 1. Packages, modules and names

1. A package is the directory with `unio.toml`; without a manifest, the directory of the file being checked is the package root. A module is a file; its name is its path from the package root with `/` replaced by `.` and without `.unio`. Names that start with `std.` are modules of the standard library (L-22).
2. A module declares names in one namespace: functions, constants, structs, enums, errors, and interfaces. Two declarations with one name in a module are E0051. Methods live in the namespace of their type; two methods with one name for one type are E0051. The second declaration is still checked, with its own parameters, so that the duplicate is its one message.
3. `import a.b` binds `b`, and `import a.b as c` binds `c`, to the module; `from a.b import x, y` binds `x` and `y`. A bound name that collides with a declaration or another import of the module is E0052. A module that cannot be found is E0053, and so is a module whose file, with links resolved, lies outside the package or the standard library it was found in: an import cannot lead out of them through a symbolic link; an imported name the module does not declare, or does not make public, is E0054. Importing a module also makes its public `error` types visible by their short names, because handlers name errors: `on IoError` after `import std.files`. Such a name that collides with another visible name is E0052. A name that an import fails to bind (E0048, E0053, E0054) is known but has no meaning: its uses, as a value, a module or a type, give no further diagnostic (2.8).
4. The prelude of every available layer (S-11) is visible in every module. A declaration of the module hides a prelude name of the same spelling; `some`, `none`, `ok` and `error` cannot be declared (L-6a). A variant declared or imported in the module also hides a prelude name, so the variant `Add` of a command enum can be written without its enum name although the prelude has the interface `Add`. Built-in types (L-4) cannot be hidden: a variant named like one is written in full (L-6a).
5. Local names are introduced by parameters, `let`, `var`, `for`, `using`, `on E as e`, patterns of `case`, lambda parameters, and `is` (L-33). A local name is visible from its introduction to the end of the block that introduces it; `is` bindings follow L-33. A local name may not repeat a local name that is visible at that point (E0055): a reader never has to work out which of two equal names is meant.
6. A name that resolves to nothing is E0056; the fix suggests the closest visible name.
7. Visibility follows L-23 to L-23d: a private declaration, field, or method used from another module is E0057.
8. An import cycle is E0058 and names the modules of the cycle (L-24).
9. A module path that starts with `deps.` names a manifest dependency by its alias (T-14); `deps` is never a directory of the package. `deps.<alias>.<module>` is the module `<module>` of the package that the alias names in the lock of the root package (`unio.lock`, T-7), read from its entry in the package cache ([packages.md](packages.md)); a module of a dependency resolves its own `deps.` imports through its own aliases in the same lock, and its other imports in its own package. The module and its types belong to the identity of that package: the same file under two identities is two modules. The compiler reads only the lock and the cache. An alias that `[dependencies]` does not declare, that the lock does not lock, whose entry is not installed, a package without the named module, an import that names no module, and an unreadable lock are E0048, and the message says which.

## 2. Types

1. The built-in types are those of L-4. A type name with the wrong number of type arguments is E0059, and the type is then unknown, so that comparing it gives no E0061 (2.8). Type names resolve like other names (E0056).
2. The type of a local `let` or `var` is the type of its initializer (L-8). An initializer that does not determine a type, such as `[]`, `{}` or `none` alone, needs an annotation (E0060).
3. Types are compared by name and arguments; there are no implicit conversions (L-5). An expression whose type is not the expected one is E0061; the message names both types, and for `Text + Int` the fix suggests interpolation. Integer literals have type `Int`, other number literals `Float`.
4. `Never` is the type of `fail`, `return`, `break`, `continue`, and calls of functions that return `Never`; it is accepted wherever any type is expected.
5. A value of type `T` is accepted where an interface type `I` is expected when `T` implements `I` and `I` can be used as a type (L-6b); otherwise E0061, and for an interface that cannot be used as a type E0071 names the method that prevents it. Type arguments of a generic interface are compared: a value that implements `Iterator[Int]` is not accepted as `Iterator[Text]`; the same holds for constraints (3.3) and implementation checks (3.6).
6. `some(v)` and `none` have type `Option[T]`, `ok(v)` and `error(e)` have type `Result[T, E]`; the missing type argument comes from the expected type, and without one it is E0060.
7. Every `error` declaration implements `Error`, with a generated `to_text` that names the type and its fields, and therefore `Display`: an error can be interpolated into text.
8. An expression whose type cannot be determined because of an earlier error produces no further diagnostics: one mistake gives one message.
9. The key of a `Map` and the element of a `Set` implement `Hash` and `Equal` (L-9). A key type that is `Float` or is built from it through type arguments, such as `Tuple[Float, Int]` or `Option[Float]`, is E0045, whether it is written (`Map[Float, Int]`, `Set[Float]`) or inferred from a map literal (`{1.5: 2}`); the fix is the key `OrderedFloat` from `value.total_order()` (L-32). The key is then taken as unknown, so that the mistake is reported once.

## 3. Declarations, calls and generics

1. A struct value is built with named arguments for every field without a default; a missing or unknown field is E0063. Fields that are private to another module make the struct impossible to build there (E0057). The default of a field is checked like any expression of its module: its names resolve (E0056) and its type is the type of the field (E0061); it sees the type parameters of the struct or error and no field.
2. A call matches positional arguments to the leading parameters and named arguments by name. Too many or too few arguments, an unknown name, or a name given twice is E0064. Named-only parameters and function shapes follow RFC 0001 (E0040, E0041). A default value is evaluated at each call that omits the argument. It is checked like any expression where it is written: its names resolve (E0056), including the type parameters of the function and the parameters before it, as at run time ([runtime.md](runtime.md) 1.3), and its type is the type of its parameter (E0061); a later parameter is not visible to it, and the default of an external function, evaluated alone, sees no parameter.
3. Generic arguments of a function are inferred from its arguments and from the expected result; when they cannot be, the call must write them (E0060). A type argument that does not meet a constraint `[T with I]` is E0062, except that a type argument built from `Float` (2.9) for a constraint `Order` or `Hash` is E0045 (L-32). A method declared only for bounded type arguments, such as `sorted` of `List[T with Order]`, called on a receiver whose type argument is built from `Float` is E0045 as well, not E0056.
4. A method call `x.m(...)` finds `m` in the `extend` blocks of the type of `x` that are visible, then in the interfaces the type implements, including their default methods (L-6c). A function of a type is called as `T.f(...)` (L-23d).
5. A lambda takes the types of its parameters and result from the expected function type; where there is none, they must be written (E0049, L-8a).
6. `extend T with I` must define every method of `I` that has no default, with the signature of `I` (with `Self` replaced by `T`), including `self` or `var self` and the `var` and `named` parameters; a missing method or a different signature is E0069. A second implementation of `I` for `T`, or one in a module that owns neither `T` nor `I`, is E0044.
7. An enum variant whose short form collides with a visible name must be written with its enum name (L-6a): E0072.
8. The conversions of `std.json` (`encode`, `encode_checked`, `decode`, and `to_value` and `from_value` that the compiler generates) never read or set a private field, even in the module that declares it (S-5, S-17). Their type parameter needs a convertible type, and so does every type parameter of a function that passes its own parameter to one that needs it. A call where such a parameter gets a type that reaches a struct or an error with a field that is not `public`, through `List`, `Set`, `Map`, `Option`, tuples, fields and variants, is E0046 at the call. The fix decodes a public transport struct and then calls the validating constructor of the domain type. At run time decoding such a struct fails with `DecodeError` and sets no field.

## 4. Operators and expressions

1. `+`, `-`, `*`, `/`, `%`, `**` need the operand type to implement `Add`, `Subtract`, `Multiply`, `Divide` (L-9a); `%` and `**` are defined for `Int` and `Float`. Both operands have one type; otherwise E0065. Lists have no `+`: `append_all` joins them, so that copying a list is always visible.
2. `==` and `!=` need `Equal`, `<` `<=` `>` `>=` need `Order`; `Float` follows L-32: its own comparisons are the partial IEEE ones, and a type built from it (2.9) has no `Order`, so `<` on it is E0045. `==` on a resource is E0066 with the fix `is_same(a, b)`.
3. `and`, `or`, `not` take `Bool`, except `or` with an `Option[T]` left operand, which gives `T` with a `T` right operand or `Option[T]` with an `Option[T]` one. Conditions of `if`, `while`, `assert` and guards are `Bool` (E0061).
4. `x in c` calls `c.contains(x)`; `c` must have such a method (E0061).
5. `a?.f` needs `a` of type `Option[T]` and gives `Option[U]` for a field `f` of type `U`.
6. `items[i]` is defined for `List[T]` with an `Int` index and for `Map[K, V]` with a `K` key; it is a fault when the element is missing, and `get` is its safe form (L-18).
7. Every interpolated expression must implement `Display` (E0067).
8. `x is p` is `Bool`; its bindings follow L-33 (E0050).
9. `range(start, end)` is a `Range`, not a `List` (S-15). A `Range` where a `List` is expected, indexed, or given a method that only `List` has is E0047, with the fix `.to_list()` after the range.

## 5. Errors

1. A call of a function with `fails with` outside `try` is E0073, in every position (L-14).
2. Every error a `try` propagates must be listed in the `fails with` of the current function, or handled by an `on` of an enclosing `try:` (L-15); otherwise E0074 names the error and the fix adds it to `fails with`.
3. `fail x` needs `x` of an `error` type that the function lists, or that a surrounding `try:` handles (E0074).
4. The block of an inline handler must not complete normally (L-14a): E0075.
5. `try` before an expression that cannot fail is E0076; the fix removes it.

## 6. Values, mutability and control flow

1. Assigning to a name bound by `let`, a parameter, a `for` variable, or a pattern is E0077 (L-10).
2. Changing a value through a place that does not start at a `var` name, a `var` parameter or a `using` name, changing a field not declared `var`, or calling a `var self` method on such a place is E0078 (L-11).
3. A `var` parameter takes a `var` name of the caller (E0079); one name may not reach two `var` parameters of one call (E0042). The receiver of a `var self` method counts as one of them: `a.absorb(a)` and `a.absorb(a.items)` with a `var` parameter are E0042 (L-29).
4. A function with a result whose end can be reached without `return` is E0082. `break` and `continue` outside a loop are E0083.
5. `match` must cover every variant of its subject or have `case _` (E0068), and E0068 names the cases that are missing. A `match` whose list or tuple patterns combine into more cases than the checker enumerates is not taken as covered: it needs `case _`, and E0068 says so. After E0068, a missing `return` in the same function is not reported again (2.8). A `match` on `Float` is E0061 (L-9).
6. A `Result` or a `std.process.Output` must not be discarded, and a local that holds one must be read; `let _ = expression` discards one explicitly (E0043, L-30). Other results may be ignored.

## 7. Resources

1. A value of a type that implements `Resource` is created only as the initializer of `using` or of a field of another resource; anywhere else it is E0080 (L-20).
2. A resource may not leave its `using` block: storing it in a struct, a collection, or a name of an enclosing block, returning it, or capturing it in a lambda is E0081. A parameter of a resource type may be used and passed on to other functions, but storing, returning, or capturing it is E0081 too. A resource may be passed only to a parameter declared with a resource type or with a type parameter bounded by `Resource` (`is_same`); a parameter of any other type parameter may store what it gets, so passing a resource to it is E0081 even where the type parameter stands for the resource type: `kept.append(h)`, `kept.put(key, h)`, `kept[key] = h`, `some(h)`, a variant `Slot.Full(h)`, or a generic function of the program. A `let` that holds a resource gives only E0080; the name is then treated like a `using` name, so that one mistake gives one message.
3. A resource is not a value: it cannot be held as an interface value (L-6b) or compared with `==` (E0066).

## 8. Layers, profiles and effects

1. A module of a library layer may use only its layer and the layers before it (S-11), and a module of the `core` layer may not allocate (item 4); in a package, `unio check --profile=core` applies the same rule to every function the package defines. A violation is E0084 and lists the chain of calls from the function to the first one of a higher layer, or to the allocating expression and its line (C-21).
2. Effects are derived, not declared (L-9b). An external function has the effect of its standard-library module: `std.files` gives `files.read` or `files.write`, as the "Permission" line of the function says, `std.env` gives `env`, `std.process` gives `process`, `std.net` gives `network`, `std.time` gives `clock`, reading the current time (`now`, `monotonic`, `sleep`), and `std.random` gives `random`, obtaining randomness from the operating system (`from_entropy`, `secure_bytes`, `secure_int`) ([RFC 0009](rfcs/0009-clock-and-randomness-as-derived-effects.md)); operations on a given duration, timestamp or date, and a `Generator` with an explicit seed, whose state changes as a `var` value, have neither; any function of the `alloc` layer gives `allocates`. A function has the union of the effects of the functions it calls. `unio symbol` shows them (C-11).
3. A package that uses a function whose effect its manifest does not permit is E0085, with the chain of calls, which names the argument or the estimate a call through a function value goes through (concept section 6, T-6). `files.read` and `files.write` are checked against the scopes of the same names in the manifest. A package without a manifest, or whose manifest has no `[permissions]` table, has declared no permission and permits none of these effects, so each of them is E0085 there, as the sandbox denies it at run time (SB-2, SB-7, [runtime.md](runtime.md) 9.1). `allocates`, `clock` and `random` need no permission and are never compared with the manifest: they show what a function depends on, not what it may reach (RFC 0009). Their absence does not prove that a function is deterministic: its input, external state and, later, concurrency matter as well; a future strict policy may restrict or virtualize `clock` and `random`, through an RFC of its own.
4. The derivation is conservative: whatever a run can do is among the effects and the layer derived for the functions it runs through (L-9b, C-21). Three rules carry item 2 past direct calls:
   - *Interfaces.* A call of an interface method has the effects and the layer of every implementation of that method in the program and of the interface's default method; when the type of the value is known, only that type's method counts. The language calls interface methods itself, and these calls count the same way: `==` and `!=` call `Equal.equals`; `<`, `<=`, `>` and `>=` call `Order.compare`; `+`, `-`, `*` and `/` call the methods of `Add`, `Subtract`, `Multiply` and `Divide`; interpolation calls `Display.to_text`; `for` calls `iterator` and `Iterator.next`; the end of `using` calls `Resource.release`; `in` calls `contains`. On `Int`, `Float`, `Bool`, `Text`, `Bytes` and `Path` they call no Unio code. A type implements an interface only in its own module or in the interface's (3.6), and `unio check` checks a program together with every module it imports, so the set of implementations is closed for the program checked.
   - *Function values* (RFC 0005). The effects of a function value count where the value is called, not where it is made. Naming a function as a value has none of its effects, and the body of a lambda is a holder of its own; making a lambda has only the effects of evaluating what it captures, and `allocates` when it captures (below). A call through a value has the effects of every value the callee expression can be, as a flow analysis of the program finds them: a named function or a lambda is itself; a local name has what is assigned to it; a constant has its initializer; a field `x.f` of a struct or error has every value stored in that field anywhere in the program, by construction, field default or assignment; a call of a named function that returns a function has what its `return` statements give; `a if c else b` has both. A call through a parameter is a latent effect of its function, and of the function around a lambda that makes it: at each call of the function it is replaced by the effects of the values the argument can be, in the caller, or of the parameter's default when the argument is left out, so `List.map` and a function `apply(f, p)` have no effect of `f` and their callers have the effects of what they pass. `unio symbol` shows such parameters as `argument effects`. Every other value, and a parameter called outside its function after the function kept it, is an estimate: a parameter that escaped has every argument passed for it at any call, its default, and any value of its type if the function is itself used as a value; an element of a collection, a binding of a pattern, a parameter of a lambda and the result of a call through a value have every function value of the program whose parameters may have the types of the place. Under `--profile=core` and in a module of the `core` layer, a call through an estimate one of whose values needs a layer above `core` is E0087 at the call, since it cannot be shown to stay in core; E0087 replaces E0084 for a function whose chain passes through it, and is reported at the call of that function that leads to the estimate, so each function has the error at a place of its own. The estimate can reject a call no run makes: a field filled with an allocating function in one place makes every call through that field allocate, and a list of functions has every function value of its element type. External functions of the library have the latent effects of their parameters of function type, because the runtime calls them. A value is made by naming a function or evaluating a lambda, both recorded, and moves only by binding, assignment, argument, `return`, field store, or a collection or pattern, each followed or estimated by type, so the value a run calls is in the set the check uses. This completeness holds only for the closed set of functions, lambdas and interface implementations of the program checked: the sources `unio check` reads and the standard library. A function value from a source outside that set is never treated as having no effects; the rule stays when packages arrive (S7), so code that `unio check` does not read must bring its function values into the set or be estimated by type like any unknown value. The tests in this set are those that run with the program (RFC 0005, "Tests in the analysis"): none for `unio check` and `unio run`, so a function value that arises only inside `test` blocks is not a possible target of the ordinary program; for `unio test`, the tests of the given modules that its filter selects, each a holder whose values, calls and stores count, while the tests of imported modules and of the standard library count only when their modules are given. Test blocks are checked for names and types in every case. The initializer of a constant counts for every function that uses the constant, the default of a parameter for its function, and the defaults of the fields of a struct or error for every function that builds a value of it, where they are evaluated ([runtime.md](runtime.md) 1.3, 6.3).
   - *Allocation.* An expression that makes a value of the `alloc` layer allocates by itself: a list literal, a map literal, a list comprehension, a text with interpolation, `+` on texts, and a lambda that captures a local name or `self`. It gives the function, constant or field default that contains it `allocates` and the layer `alloc`, so under `--profile=core` it is E0084 with the chain ending at the expression; in a module of the `core` layer it is E0084 at the expression (item 1). A text without interpolation and a lambda that captures nothing do not allocate. The grammar has no set literal: a set is made by a function of the `alloc` layer, which item 2 covers.

   `unio symbol` shows the effects derived this way, and E0085 is reported at the first call, call through a function value, use of a constant or field default, or implicit call of each module that needs an effect its manifest does not permit.
5. An `external function` is a primitive of the runtime: in release 0.1 it is declared only in an `unsafe module` of the standard library (S-7, S-10), and every one declared there has an implementation in the runtime. An `external function` anywhere else, including an `unsafe module` of a package, is E0086 at its name, so that no program reaches a call the runtime cannot make. The list of `unsafe module` files in the manifest (T-6) and the confirmation when a dependency is installed (T-9) concern packages, which declare no external functions in 0.1.
6. The manifest `unio.toml` of every package that `unio check` reports is checked as a whole, as `unio run` and `unio test` read it (T-6, RFC 0008): `[package]` with `name` (lowercase letters, digits, `-` and `_`, starting with a letter), `version` (a semantic version), `unsafe_modules` (a list of module names), `unio_version` (a version requirement on the toolchain) and `targets` (a list of the target triples of `unio build`), the requirements of T-14 that installation checks ([packages.md](packages.md) section 1); `[permissions]` with `files.read` and `files.write` as lists of paths, whose placeholders are `$HOME`, `$CWD` and `$TEMP` and whose only `*` is the suffix `/**`, `env` as a list of variable names, `process` as a list of programs, and `network = false`; each entry of `[dependencies]` a table with exactly one source (`path`, `registry` with `package` and `version`, or `archive` with `sha384`); and no other table or key. Each mistake is E0088 at its line of the manifest, once (2.8); a manifest that the reader of its format cannot read has only that mistake. A package whose manifest has a mistake gets no E0085, since its permissions are not known, and an import of a dependency whose entry has a mistake gets no E0048. `unsafe_modules` names exactly the modules of the package that carry `unsafe module` (T-6, RFC 0004): every `.unio` file of the package directory is parsed for the marker, except below a name that starts with a dot, below `target/` at the top, and in a directory with a `unio.toml` of its own, which is another package. A marked module that the list does not name, and a name of the list that is no marked module, are each E0089 at the line of `unsafe_modules`, or of `[package]` when the key is missing; a list that is not a list is E0088 alone, and a package without a manifest has no list to compare. A standard library or a dependency is not checked here: its manifest was checked when it was installed.

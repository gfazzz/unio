# Implementation status of release 0.1

Russian localization: [ru/status.md](ru/status.md). Basis: [requirements.md](requirements.md) (specification 0.16), [plan.md](plan.md) section 12.

**This table is updated with each change.** A change that implements, checks, narrows, or breaks a requirement updates its row in the same commit, in both languages. A row says what the code in the repository does and which automated check confirms it, not what a sprint intended. Parsing a program or passing `unio check` is static validation; only `unio test`, `unio run`, and the executables of `unio build` execute Unio code. When this document and another one disagree about what is done, the code decides, and both documents are corrected.

State of the checkout this table describes: commit `b18ce5e` (the rows were read again against the code and the commits since `85aa017` on 2026-11-12); facts were established by reading the code, the tests, and the CI workflow, and by probes with `unio check` and `unio run` named in the rows; no benchmark was rerun.

## Legend

Status:

- **implemented and checked**: the behavior the requirement states exists, and an automated check in CI fails if it breaks, on the platforms the requirement covers or, for a platform-independent rule, on at least one.
- **implemented, partly checked**: the behavior exists, but the check covers only part of it, only some of the required platforms, or only a review.
- **partial**: part of the behavior is missing or differs from the requirement; the row names what.
- **not started**: no implementation beyond the specification and, where noted, policy text.

Checks: `tests/X.rs` is `compiler/unio/tests/X.rs`; `runtime tests/X.rs` is `compiler/unio-runtime/tests/X.rs`; "spec corpus" is `spec/tests/valid` and `spec/tests/invalid`; "semantic corpus" is `spec/tests/semantic`; "test blocks" are the `test` blocks of `stdlib/`, `examples/`, `docs/examples/`, `docs/ru/examples/`, and `tools/`, run by `unio test` in the CI job `spec` and by `tests/interpreter.rs`. CI is [.github/workflows/ci.yml](../.github/workflows/ci.yml).

Platforms where the check runs: **Lx64** Linux x86-64 (`ubuntu-latest`), **mac** macOS arm64 (`macos-latest`), **Win** Windows x86-64 (`windows-latest`). **La64** Linux arm64 (`ubuntu-24.04-arm`), the fourth platform of R-8, runs only the job `native-linux-arm` (the code generation test and `tests/native.rs`). The jobs `compiler` (`cargo test` of both crates, and the release step of `tests/native.rs`) and `spec` (the Unio tools and test blocks) run on all three; the benchmarks, the Python parity job, and the editor tests run on Lx64 only. A platform marked "CI only" has its check in CI but has not been seen passing when the row was written. On Win, `unio run` and `unio test` run with `--allow-weaker-sandbox`, and the executables of `tests/native.rs` under the same weaker sandbox the operator allows, because there is no operating-system sandbox there (gap 7).

Native targets: a target counts as done only after its test executables have run on it and the runtime guarantees have been checked there (faults, traces and exit codes, the stack limit, the reserve for `release` of C-17, the operating-system sandbox of the platform, the refusal of an incompatible image with code 104), not after successful linking or a verified object file ([plan.md](plan.md) section 12, step 6). By this criterion the native targets La64 and mac are done: their test executables ran in CI and the runtime guarantees, the operating-system sandbox of the platform included, were checked there. Win is not done: the native suite and the runtime guarantees were checked there, but under the weaker sandbox (a Job Object without AppContainer), so the operating-system sandbox of the platform is missing until AppContainer exists (gaps 7 and 11).

## Known gaps

These were found by an audit of the sprints S1 to S6 and are stated here precisely, so that "done" in the plan can be read against them. "Being fixed" means work in progress at the time of writing; the row changes when the fix lands with its check.

Three items have closure conditions in [plan.md](plan.md) section 12. The memory reserve for `release` (C-17, condition 1) is implemented with the tests the condition names and its measured peaks are recorded in [runtime.md](runtime.md) 3.7; its native tests passed in CI on every platform as well (Lx64, La64, mac, and Win, the last under the weaker sandbox; run `42630176676` on `bd8678a`). Commit `c51d269` added three tests of a `release` that exhausts the reserve and frees the block before the next check (`a_release_that_exhausts_the_reserve_and_frees_it_ends_with_102`, `the_executable_ends_with_102_when_a_release_exhausts_the_reserve_and_frees_it`, `a_block_over_the_reserve_freed_before_the_check_is_exhaustion`); in run `43164795419` on `b18ce5e` the runtime and the interpreter test passed in the job `compiler` on Lx64, mac, and Win, and the native test there and in the job `native-linux-arm` on La64 (Win under the weaker sandbox), which is what the condition asked of each kind of test then (row C-17). Each of them set a heap limit, and a program without `limits.heap_bytes` did not end with 102 when a `release` overflowed the reserve (audit item A6). The condition now states that the reserve bounds the path of a fault whatever the heap; the fix and its tests of a program without a heap limit passed locally on Lx64 and have not run in CI, so the condition is met again once they pass on mac and Win (the native test also on La64). The R-10 control set with its model trial (condition 2) is future implementation, not done work. The decision on C-13 (condition 3) is open: either the requirement is met as written or an RFC that keeps reference counting is accepted after measurements (gap 9). A green CI run means that the checks that exist pass; it does not mean that future checks or trials passed. Plan section 12 also lists five release conditions for 0.1 (installation without a source checkout, an independent reproducible build, exact toolchain pinning, licence files, and the check-to-use races of file access closed or the scopes enforced by the operating system); none holds yet, and they are recorded under gaps 6, 10, and 19 and rows C-4, C-5, R-6, and T-6a. Packages and dependency management (T-7, T-14), signatures and the cryptography policy (T-8, T-8a, R-6 to R-6c), the language server (T-10, SB-13), and the R-10 control set are requirements only: nothing of them is implemented.

1. **Runtime type identity** (fixed in `fcb06d3`). Values of declared types carry the identity of their declaration; methods, handlers, patterns and type functions use it in the interpreter and in native code. Checked by `tests/interpreter.rs` and `tests/native.rs` with the fixture `tests/programs/same_names/`.
2. **Indirect effects and allocation by literals** (fixed in `fcb06d3`; function values per RFC 0005, accepted; docs/semantics.md 8.4). Interface calls take the union of the implementations; making a function value has only the effects of making it, and a call carries the effects of every value the callee can be, found by a flow analysis, with calls through parameters latent and resolved at each call site; estimated calls (fields, collections, generic positions) take a conservative set, and under `--profile=core` such a call needing a higher layer is E0087. Allocating expressions give `allocates` (E0084). Remaining: the analysis is not context-sensitive; estimates match parameter types only; the interface union is program-wide; the false rejections listed in RFC 0005. RFC 0005 is accepted: acceptance fixes the semantics, and the correctness of the implementation is confirmed separately by tests on passing, returning, storing and calling function values, including recursive chains, added in `6c3c804` (`tests/effects.rs`). The completeness of the analysis holds only for the closed set of functions and implementations of the current program; a function value from an unknown source is never treated as having no effects, and this rule must be kept when packages arrive (S7). The tests in that set are the tests that run (RFC 0005, "Tests in the analysis"): none for `unio check` and `unio run`, the selected tests of the given modules for `unio test`; the tests of imported modules and of the standard library count only when their modules are given, so a library test helper such as `positive` is not a target of a user's estimated call; ordinary library functions still are, so the library keeps code used only by its tests inside the test blocks. Checked by `tests/symbol.rs`, `tests/catalog.rs`, `tests/effects.rs`.
3. **Children of `process.run`** (fixed in `fcb06d3` and the commit of the children's rules, docs/runtime.md 9.5). Children get only granted variables and `PATH`, run in their own process group (on Windows a Job Object without breakaway, which the child joins while still suspended; a job that cannot be set up fails the call), and the whole tree is killed at the deadline, which also bounds pipe draining; each stream is capped at 16 MiB and counted in the heap, and the output on its way from the pipes passes a bounded queue whose bound (384 KiB) counts in the heap too. On Linux every child installs a seccomp filter that denies `setsid` and `setpgid` to it and its descendants, so no process leaves the group; on macOS descendants that left the group are found through their parents and, under the program's Seatbelt profile, by a marker of the profile that every descendant inherits, and killed. Every worker of the tools runs in the same kind of tree (`sandbox/tree.rs`) and the whole tree ends when the worker ends, at a limit or not, so the link step of `unio build` ends with its whole tree at its time limit; SIGINT, SIGTERM, SIGHUP, and SIGQUIT of the tool first stop the process groups of its workers; on Windows a worker joins its Job Object while still suspended. Remaining: on Linux a program that needs `setsid` or `setpgid` fails in a child; without seccomp (weaker sandbox) a process can leave the group; on macOS an orphan that left the group (double fork) is found only by the marker of the program's profile, so not without a sandbox, and the marker relies on `sandbox_check`, which has no public header; Ctrl-C does not reach the child group of a program; the macOS marker passed in CI on `macos-latest` (run `43164795419` on `b18ce5e`, `a_double_fork_into_a_new_session_is_stopped_with_the_tree`), the Windows suspended start passed in CI on `windows-latest` (the same run, `a_process_the_child_starts_at_once_is_stopped_with_its_job`) and its fail-closed path has no test, and `process.run` counts calls, not the processes of the tree (SB-3). Checked by `unio-runtime/tests/process.rs` (`a_descendant_that_calls_setsid_is_stopped_at_the_timeout`, `a_double_fork_into_a_new_session_does_not_escape_the_tree`, `a_child_that_writes_far_more_than_the_limit_is_stopped_at_it`), `unio-runtime/tests/process_windows.rs`, `sandbox::tree::tests` (the marker on macOS), `tests/sandbox.rs` (`a_descendant_that_leaves_the_process_group_is_stopped_at_the_timeout`, `a_double_fork_into_a_new_session_is_stopped_with_the_tree` on Linux and macOS), `unio-runtime/tests/process.rs` (`the_output_on_its_way_counts_against_the_heap_limit`), `unio-runtime/tests/process_windows.rs` (`a_process_the_child_starts_at_once_is_stopped_with_its_job`), and `tests/workers.rs` (`the_link_step_over_the_time_limit_ends_with_its_process_tree`).
4. **Imports through symbolic links** (fixed in `fcb06d3`). A module whose resolved path leaves the package or the standard library is E0053. Checked by `tests/semantic.rs` (Unix).
5. **Heap accounting** (partly fixed in `fcb06d3`, docs/runtime.md 3.4–3.7). Allocations driven by program input (reading files and chunks, process output, `Text.repeat`) are checked against the limit before they happen and use fallible allocation, so they end with 102. The reserve for `release` (C-17, closure condition 1 of [plan.md](plan.md) section 12) exists: 1 MiB set aside before `main`, before each test, and in executables, its pages written and counted within a heap limit of at least 2 MiB (a lower limit is code 103); it opens when a fault is created, before its message and trace are allocated, and the allocations of the fault's path come from its pages through the runtime's allocator; the reserve, not the heap limit, bounds the fault's path: a `release` that goes beyond it ends with 102 and skips the rest, with a heap limit and a full heap, with a limit and room on the heap, and without a heap limit in the policy, also when it frees the block before the next check, since the reserve stays marked as overflowed until it closes (`reserve::room`; the block freed before the check fixed in `c51d269`, the heap limit and the room on the heap made irrelevant in the fix of audit item A6); the temporary memory of file operations (write copies, growing read buffers, listings, long path copies) counts against the limit too; measured peaks of 15–29% of the reserve are recorded in docs/runtime.md 3.7. Checked by the runtime unit tests `the_release_reserve_is_set_aside_before_main`, `the_reserve_opens_only_for_unwinding`, `the_reserve_opens_before_the_fault_is_built`, `the_unwinding_path_allocates_from_the_reserved_pages`, `the_reserve_peak_is_measured` (in `unio/src/interp.rs`), `a_block_over_the_reserve_freed_before_the_check_is_exhaustion` (`unio-runtime/src/runtime.rs`; also without a heap limit and with room on the heap), `unio-runtime/tests/files.rs` (`the_temporary_memory_of_file_operations_counts_against_the_heap_limit`, `reading_a_file_of_unknown_size_counts_the_buffer_it_grows`), `tests/interpreter.rs`, `tests/sandbox.rs` and `tests/native.rs` (row C-17; in run `43164795419` on `b18ce5e` the runtime and interpreter tests of `c51d269` passed on Lx64, mac, and Win, and its native test on Lx64, La64, mac, and Win). The tests of a program without a heap limit (`a_release_beyond_the_reserve_ends_with_102_without_a_heap_limit`, `a_release_within_the_reserve_ends_with_101_without_a_heap_limit`, `unio_test_ends_a_release_beyond_the_reserve_with_exhaustion` in `tests/interpreter.rs`, `the_executable_ends_a_release_beyond_the_reserve_with_102_without_a_heap_limit` in `tests/native.rs`) passed locally on Lx64 and are pending in CI (audit item A6). Remaining: counts are estimates; other growth (for example comprehensions) is checked after each step, also when it overflows the reserve; outside the path of a fault a small allocation failing inside the Rust standard library still aborts; the OOM killer of the system can end the process without 102.
6. **Operating-system rules are wider than the manifest for reading library directories and metadata, and for what a child can run.** Writes are closed: a separate writer process performs every write of `std.files` and checks the write scopes itself, so the program and its children have no write rights at the operating-system level on Linux and macOS (audit item 3, first part). Starting programs is closed too (audit item 3, second part, [runtime.md](runtime.md) 9.5–9.6): the system lets children start with `execve` only the listed programs, the interpreters of listed scripts and, on Linux, the dynamic loader of listed ELF programs, and read only the read scopes, the libraries the listed programs need, and the library directories; checked by `tests/sandbox.rs` (`a_child_runs_and_reads_only_what_the_manifest_lists`). What a child can run is wider than the list, and the list must be read that way: on Linux the loader runs any ELF program the child can read (in the library directories, the added libraries, or the read scopes) without `execve` of it; the libraries it loads run as code in its processes; and a listed interpreter (`sh`, `python3`) runs any script it can read and any code in its arguments, so listing an interpreter grants every readable script. What stays closed is a program a child can neither start nor read, and no child can write a file to make one; running an anonymous file (`memfd_create`) is not covered by a test. Paths are resolved component by component in the order of the system (on Linux and macOS a link before the `..` after it, on Windows `..` first), and the operation opens the path that was checked (fixed in `c51d269`, `unio-runtime/tests/files.rs`, `a_link_followed_by_dot_dot_does_not_lead_a_file_operation_out_of_its_scope`); a read in a Linux sandbox and every write through the writer do not follow a link put on the path after the check. Remaining: the library directories are readable as a whole; where the operating system does not enforce the scopes (reads on macOS and Windows, the weaker sandbox, and `exists`, `is_directory`, `list_directory`, and `resolve` everywhere) a link that another process puts on a checked path between the check and the use is still followed ([runtime.md](runtime.md) 9.2), and closing this race, or the operating system enforcing the scopes, is release condition 5 of [plan.md](plan.md) section 12; `stat` is not restricted; a read root that does not exist at start grants nothing; a write scope whose directory does not exist at start cannot be written. Children are restricted only by the operating-system rules, not by the runtime. macOS behaviour of the writer and of the rules for children is checked in CI only. Rows SB-2, SB-4, SB-8; [runtime.md](runtime.md) section 9.
7. **Windows has no operating-system sandbox.** AppContainer and the restrictions of Job Objects are not implemented (a Job Object only holds the process tree of a child and the memory and process limits of a tool worker); programs start only with `--allow-weaker-sandbox`, and then only the runtime layer and the limits apply. Rows SB-1, SB-4, SB-5, SB-8, R-7a.
8. **Tool isolation** (partly fixed; [runtime.md](runtime.md) 9.7). `unio check`, `fmt`, `build`, `outline`, `symbol`, `parse`, and the compile steps of `unio test` and `unio run` run their work in a worker process: on Linux Landlock and seccomp let it read only the packages of the given files and the standard library, write only its own temporary directory, open no socket, and start no process; it gets only the language variables of the environment; memory (`RLIMIT_AS`) and time (stopped by the tool) come from the `[compile]` table of the policy or the defaults of 2 GiB and 10 minutes, and a worker over a limit ends with its whole process tree, a diagnostic, and code 102. The limits of the workers are the `[compile]` table of the policy, apart from the limits of the program (RFC 0006, replacing the floor of 256 MiB of `c51d269`): they hold alike for `check`, `build` with its link step, `run`, `test`, and the other tools, `[limits]` does not reach a worker, and a `compile.memory_bytes` below the measured minimum of 192 MiB is refused with 103 before compiling instead of being raised (`a_worker_over_the_compile_time_limit_is_stopped_alike_in_every_command`, `a_worker_over_the_compile_memory_limit_is_stopped_alike_in_every_command`, `a_worker_over_the_compile_cpu_limit_is_stopped_alike_in_every_command`, `the_program_limits_do_not_change_the_compile_limits`, `a_compile_memory_below_the_minimum_is_refused_before_compiling`). `unio fmt` writes only the given files, through the writer process; `unio build` links in a second sandboxed step that may execute only the C compiler and the programs it runs, and the tool copies the executable to the path the operator chose. `unio test` and `unio run` load the program again from the sources the worker returned, inside the program's sandbox. Checked by `tests/workers.rs` (SB-15: links and the home directory, writes, `fmt`, network, processes, environment and `/proc/<pid>/environ`, time, memory, pathological sources, `build`). Remaining: on Windows the worker has only a Job Object (memory, one process) and no restriction of files and the network (no AppContainer), so the tools refuse there with 103 unless the operator allows the weaker sandbox by the flag or the external policy, as programs do (checked by `the_tools_refuse_a_weaker_sandbox_on_windows_unless_the_operator_allows_it`); CI on Windows runs its functional checks in the weaker mode, which does not count as passing the full sandbox checks; macOS (Seatbelt, the footprint watched by the tool) and Windows are checked in CI only; `stat` is not restricted, so a worker learns whether a path exists anywhere; the tool still reads the manifest and the policy itself to set up the sandboxes of `run` and `test`; no `target/` is written yet; package operations (SB-12), the language server (SB-13), and `unio doc` do not exist, and SB-12 and SB-13 ship together with the features they protect, not after them ([plan.md](plan.md) section 12, steps 7 and 8); SB-15 has no archives, since nothing unpacks one yet.
9. **C-13 and reference counting.** C-13 asks for a precise, tracing, non-moving GC; the runtime uses reference counting with copy-on-write and no tracing. This is a deviation from the requirement: keeping it needs an RFC after measurements, including the latency of freeing a large structure at once (the counterpart of a GC pause) and the GC-pause row of 7.1. It is decided before 0.1 by closure condition 3 of [plan.md](plan.md) section 12: either C-13 is met as written (a precise, tracing, non-moving GC) or an RFC that keeps reference counting is accepted on these measurements; it closes when row C-13 says "implemented and checked" under either. Rows C-13, L-19.
10. **Reproducibility.** C-4 is tested as two builds of one source in one directory and as one project copied into two directories and built there with another home and temporary directory (`tests/native.rs`, `two_builds_are_byte_for_byte_the_same`, `builds_in_two_directories_are_byte_for_byte_the_same`); the program image holds no path of the machine that built it (docs/runtime.md 8.4). Each build records the identity of its linker and SDK (names and versions) in the image, and `unio build --print-toolchain` prints it (`the_toolchain_is_recorded_in_the_executable`); the extraction for macOS and Windows is unit-tested on sample paths and environments (`native::toolchain::tests`) on any machine, and on a real Xcode and Visual Studio installation it ran in CI: `the_toolchain_is_recorded_in_the_executable` passed on macOS arm64 and Windows x86-64 (run `42630176676` on `bd8678a`). Builds on two machines are not compared: their C compiler, linker, and C library may differ, and the lock file that C-4 names does not exist yet (T-14). The release conditions 2 and 3 of [plan.md](plan.md) section 12 ask for an independent build on a second machine or runner with the same bytes and for exact pinning of the toolchain: the Rust toolchain (`compiler/rust-toolchain.toml`, 1.97.0) and the crates (`Cargo.lock`, exact versions) are pinned, the linker and SDK are recorded but not pinned on the CI runners, and no comparison across machines exists. Rows C-4, R-6.
11. **Native targets.** `unio build` makes executables for Linux x86-64 and arm64, macOS arm64, and Windows x86-64 (docs/runtime.md 8.4). A target counts as done only after its test executables have run on it and the runtime guarantees have been checked there: faults, traces and exit codes, the stack limit, the reserve for `release` (C-17), the operating-system sandbox of the platform, and the refusal of an incompatible image with code 104; successful linking or a verified object file does not count ([plan.md](plan.md) section 12, step 6). Code generation for all four is checked on every machine (`native::tests`); by this criterion that alone does not make a target done. The native suite passed on Linux x86-64; on Linux arm64 in CI on the real runner `ubuntu-24.04-arm` with the operating-system sandbox (commits `bd3ca8b` and `a930da1`, job "native executables on Linux AArch64"; before that it had run only under qemu-user, without the sandbox, since qemu passes neither Landlock nor seccomp); on macOS arm64 (`macos-latest`), 14 of the 14 tests of `tests/native.rs` in debug and in release with Seatbelt (runs `42625607113` on `485de62` and `42627912988` on `a930da1`; every test reported `ok`, none skipped); and on Windows x86-64 (`windows-latest`), 14 of 14 in debug and in release on `a930da1`, after `473f952` moved the search for `link.exe` out of the runtime library. In run `42630176676` on `bd8678a` every job passed on all four platforms. So La64 and mac are done. Win is not: its native suite and runtime guarantees were checked, but under the weaker sandbox the operator allows (a Job Object without AppContainer, so the file and network restrictions of the operating system are missing), and the criterion requires the operating-system sandbox of the platform; Win is done when AppContainer exists (gap 7). An executable is made only for the machine of the compiler; there is no cross-compilation. Rows C-5, R-8.
12. **Signing and trust.** Post-quantum signing, trust anchors, rotation, revocation, and rollback protection exist only as policy ([cryptography.md](cryptography.md)); nothing is implemented. Packages, the registry, and installation (T-7, T-14), the language server (T-10), and licence files with third-party notices (release condition 4 of [plan.md](plan.md) section 12; the root has no `LICENSE-MIT` or `LICENSE-APACHE`, although both crates declare `MIT OR Apache-2.0`) do not exist either. Rows T-7, T-8, T-8a, T-10, T-14, R-6 to R-6c.
13. **File guarantees after power loss.** The fault-injection hook fails `fsync`, `close`, `rename`, and the directory sync one by one, and the tests check the recorded state. The crash trials of `tests/power_loss.rs` (docs/runtime.md 10) record the file operations of a real run, from the program and the writer process, replay them at every crash point on a model file system with ordered and with weak persistence, and check guarantees 1–3 in every state; the harness is first shown to catch broken protocols (no data sync, rename before the data sync, no directory sync, plain `fsync` on macOS, an unsynced parent of a new directory). Programs, and on Linux the writer process alone, are killed at random points during writes. The trials found two faults, both fixed: a new directory was not synced into its parent, and on macOS a failed `F_FULLFSYNC` of a directory fell back to a plain `fsync` silently. Not done: a real power cut, dm-log-writes replay, and powering off virtual machines (S-9b), which need root or virtual machines; real traces come from Linux and macOS, and Windows is checked on its code path under stated assumptions. S-9b stays partial: the crash model and the trials with `kill -9` are useful but do not confirm survival after a power loss. Rows S-9b, R-2, C-19.
14. **Fuzzing.** `tests/fuzz.rs` runs 2,000 deterministic mutations by default (`UNIO_FUZZ_ITERATIONS` raises it), plus random renaming in `tests/semantic.rs`; the plan asks for long coverage-guided runs, 24 hours before release (R-1).

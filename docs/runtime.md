# Dynamic semantics and the runtime of Unio 0.1

Version 0.1-draft. Russian localization: [ru/runtime.md](ru/runtime.md). Basis: concept sections 2–4, requirements L-10 to L-21, C-13 to C-20, S-9 to S-12, SB-1, T-4, T-5a; [semantics.md](semantics.md) for what is checked before a program runs. This document is the reference for the interpreter of sprint S5 and for the native runtime of sprint S6.

A program that reaches the runtime has passed `unio check`: names resolve, types agree, errors are handled, resources stay in their blocks. The runtime therefore checks only what cannot be known before execution: faults, exhaustion, and the outside world.

## 1. Evaluation

1. Evaluation is strict and goes from left to right: the operands of an operator, the arguments of a call, the fields of a struct construction, the items of a list or map literal, and the parts of a text with interpolations are evaluated in the order they are written.
2. `and` and `or` evaluate their right operand only when it decides the result; `a or b` on an `Option` evaluates `b` only for `none`. `x if c else y` evaluates `c` and then one branch.
3. A default value of a parameter is evaluated at each call that omits the argument, after the arguments that precede it, and can use the parameters before it.
4. A `for` loop evaluates its collection once, before the first iteration; changing the source variable inside the loop does not change the iteration, because the loop holds the value it started with.
5. A comprehension `[e for x in c if g]` evaluates `c` once, then `g` and `e` for each item in order.

## 2. Values

1. `Int` is a 64-bit two's-complement integer; overflow of `+`, `-`, `*`, `**`, division by zero, and `%` by zero are faults (L-17). `/` truncates toward zero, and `%` has the sign of the left operand.
2. `Float` is IEEE 754 binary64 with round-to-nearest-even; no operation on `Float` faults.
3. `Text` is an immutable sequence of Unicode scalar values stored as UTF-8 with an index of character positions, so that `length`, `slice`, and `char_at` take constant time.
4. Structs, enums, tuples, lists, maps, sets, `Bytes`, and texts are values (L-11a). A value is shared between names until it is changed; changing a shared value first copies the level that changes, and changing an unshared value happens in place (L-11b). Map and set iterate in the order keys were first inserted, and hashing does not depend on the run, so the output of a program is the same on every run.
5. Function values capture the values of the names they use when they are created (L-11a).
6. A resource is not a value: it has identity, is never copied, and its `release` runs exactly once (section 5).

## 3. Memory

1. Because values never share mutable state and closures capture copies, a value can never reach itself: there are no reference cycles. The interpreter of S5 and the executables of S6 therefore manage memory by reference counting, which frees each value when its last name goes away and also tells the copy-on-write rule when a value is unshared.
2. Requirement C-13 is reference counting (RFC 0007, accepted on 2026-11-12, in place of a precise, tracing, non-moving collector). Reference counting is precise and non-moving, never scans the memory that stays live, and needs no tracing because cycles cannot occur. Its pause is freeing what the program drops, proportional to it: about 0.4 to 0.6 ms per MB on Linux x86-64 (`bench/free/`, `bench/README.md`), bounded at 1 ms per MB by 7.1. With glibc the runtime fixes the allocator's mmap threshold at its default of 128 KiB when a program starts (`fix_mmap_threshold` in `compiler/unio-runtime/src/heap.rs`): glibc otherwise raises it to the size of each mapped block that is freed, so after the front end of `unio run` freed a buffer of about 1 MB, the large buffers of the program came from the allocator's heap, and freeing one of them in a drop consolidated every small block freed before it, which doubled the pause of `bench/free/` in the interpreter (1.2 ms per MB on CI). The trim threshold is fixed with it at 64 MiB, the most glibc's own adjustment reaches, so that a free does not give the top of a thread's heap back to the system, which reads `/proc/sys/vm/overcommit_memory` first (a system call the filter of section 11 forbids). Freeing does not recurse with the depth of a structure: every object that holds values hands its contents to `release` (`compiler/unio-runtime/src/value.rs`): lists, tuples, maps, sets (keys included), structs, enums, the captures of a closure of the interpreter and of native code (`Captures`), and the value of a resource, which frees them by recursion up to 128 levels of nesting and below that through a list that a loop of the frame at the 128th level drains, so the native stack is bounded whatever the depth (before, a chain of nested lists aborted the process with a stack overflow at 120,000 to 160,000 levels on an 8 MiB stack). Freeing stays immediate: the loop ends before the outermost drop returns and the heap count is exact. Before, a closure freed its captures by recursion: a chain of closures each capturing the one before overflowed the 1 GiB stack of `unio run` and of an executable between 8 and 10 million closures (about 128 bytes of stack a closure), which ended `unio run` with "fatal runtime error: stack overflow" and code 134 and an executable with the signal SIGSEGV; `a_deep_chain_of_closures_is_freed_without_recursion` (`compiler/unio/tests/interpreter.rs`), `the_executable_frees_a_deep_chain_of_closures_without_recursion` (`compiler/unio/tests/native.rs`), and `closures_and_resources_are_freed_without_recursion` (`value.rs`) free such chains and mixed ones. The other operations that walk a value do not recurse with its depth either (item 8).
3. **The heap and its limit (RFC 0010).** The heap of a program is every byte its threads request from the allocator while it runs and still hold: the blocks of values and of their wrappers (the reference-counted block of each struct, enum, closure, and resource, with its fields, captures, and names), vectors and maps, the structures the interpreter makes while the program runs, the temporary buffers of the runtime, and the reserve for `release` (item 6). The global allocator of the runtime (`compiler/unio-runtime/src/reserve.rs`) counts each allocation, reallocation, and free when it happens (`compiler/unio-runtime/src/heap.rs`). A block counts as requested, its size rounded up to its alignment (`Layout::pad_to_align`); a reallocation counts its new size in place of the old one. The count belongs to the program: the thread that runs it counts without atomic read-modify-write operations, and the threads the runtime starts for it (the two readers of `process.run`) count into the same total, so a block allocated on one thread and freed on the other leaves the count exact; values hold `Rc` and never reach another thread. `limits.heap_bytes` (SB-3a) is a hard limit: an allocation that would take the count over it is refused before the system is asked, and a refused allocation is exhaustion (C-18). A fallible reservation of the runtime (item 4) receives the refusal and unwinds with code 102; any other ends the program at once with code 102 and the prepared diagnostic, as a refusal of the system does. No user code runs after it, `release` included. Recursion deeper than the stack limit also ends with code 102.
   - **Not counted.** What the allocator adds to a block (its header, the rounding to a size class, freed pages it keeps), measured by `the_overhead_of_the_allocator_is_measured` (`heap.rs`, glibc on Linux x86-64, 100,000 values of each kind): +54% for one-byte `Bytes`, +29% for short texts, +19% for structs of two `Int` fields, +20% for enums of one field, +23% for lists of one `Int`, +10% for texts of 100 characters, 0% for blocks of 64 KiB; fragmentation after frees is bounded only by the backstop of item 5. Memory not requested from the Rust allocator: thread stacks, the code, the mappings of the system and its libraries. Memory that is not the program's: the captured output of a test in `unio test` and the report of its result. A block made before the program starts and freed while it runs lowers the count; the runtime frees nothing of the loaded program while it runs.
   - **Counted as it happens.** The count follows what a run does: the index of character positions of a text with non-ASCII characters counts once it is built, and freeing a structure deeper than 128 levels (item 2) holds a list of pending values, up to 72 bytes a level, until the free ends. The test hook of item 6 adds a ballast that holds no memory.
   - **The moment of the check.** Every allocation is checked when it is made. The harness of `unio test` defers a refusal instead, so that one test cannot end the run: the allocation is granted, the test is marked exhausted and ends with exhaustion at its next call or check of the heap, and the other tests run. A deferred refusal grants at most 1 MiB above the limit (`OVERDRAFT`); beyond it the process ends with code 102 as a program does. A test without `limits.heap_bytes` in the policy has the default heap of 1 GiB, and a deferred refusal of it grants up to that limit again (`Meter::set_overdraft`), so that a list or a text that doubles past it ends the test, not the run (T-12, [tools.md](tools.md) section 4); time limits of a test are kept in the same way.
4. **Budget before allocation.** Where the program decides the size of an allocation, the runtime checks the heap limit before it allocates and reserves the memory with fallible allocation (`try_reserve`), so that the call unwinds with exhaustion (code 102) instead of reaching a refusal of the allocator, and an allocation the system refuses is the same exhaustion, not an abort: the buffer of `FileReader.read_bytes` (`max_bytes`), `read_text` and `read_bytes` (the size of the file), the output that `process.run` captures, and `Text.repeat`. The temporary memory of the file operations of `std.files` is checked the same way before it is allocated: the copies an operation makes of a long path (the native path, its resolution, the text of the system call, the request to the writer; those of a path of ordinary length, up to 32 KiB in all, are a fixed cost like the chunk buffer of a read), the names `list_directory` holds before it makes its list, and, for a file whose size the system does not report (a pipe), the growth of the buffer as it is read; `AtomicFile.write_bytes` writes the bytes the program holds without copying them. Every other allocation is checked by the allocator when it is made (item 3). Any other allocation the system refuses, outside these fallible reservations and on or off the path of a fault, ends the program with code 102 as well: the global allocator of the runtime (`reserve.rs`) writes the prepared message and exits instead of letting Rust abort (C-18). The message of code 102 is prepared in advance and written without allocating.
5. **The backstop of the operating system.** With `limits.heap_bytes`, the sandbox of the program also limits its memory through the system, for what the count of item 3 does not see. On Linux the soft `RLIMIT_AS` of the process becomes the address space it maps when the sandbox applies (the code, the stacks of its threads, among them the stack of 1 GiB that the interpreter and an executable reserve before, and the loaded program), plus twice the heap limit, once for the heap and once for what the allocator adds, plus an allowance of 512 MiB for the mappings made later, such as the stacks and allocator arenas of the threads of `process.run` (`backstop_bytes` and `BACKSTOP_ALLOWANCE` in `compiler/unio-runtime/src/sandbox/mod.rs`). On Windows the process joins a Job Object whose limit of committed memory per process is what the process has committed when the sandbox applies plus the same amount. Memory beyond the backstop is refused by the system, and the allocator turns the refusal into code 102 and the prepared diagnostic like any refusal of the system (`the_heap_limit_is_backed_by_the_address_space` in the same file, Linux). Only the soft limit is lowered: a child of `process.run` and the writer process get their address space back before they run, since their memory is not the program's heap; on Windows a child stays in the job of the program and has the same limit of its own. On macOS no system limit bounds the memory the allocator maps (`RLIMIT_AS` and `RLIMIT_DATA` do not apply to `mmap` there), so the count of item 3 is the only bound.
   - **What cannot be guaranteed.** The allowance is address space, not memory; a program whose count stays under the limit can still reach the backstop through what the count does not see, such as fragmentation beyond the limit again, and then ends with code 102 as well. The runtime cannot see memory the system promised but cannot deliver: with overcommit (the default on Linux) an allocation can succeed and the process can then be ended by the system's out-of-memory killer, without code 102 and its diagnostic; an allocation that fails, small or large, inside the Rust standard library or the runtime, does not abort: every allocation goes through the global allocator of the runtime, which turns a refusal into code 102 and the prepared diagnostic (item 4; `checked` and `refused` in `reserve.rs`), and only a reservation inside `fallible` receives the refusal and unwinds with 102 itself. The process aborts only if the exit after a refusal itself fails to allocate, and the exit writes the prepared message without allocating. A heap limit in the policy is therefore the reliable way to get code 102; a limit of the operating system (`ulimit -v`, a cgroup) stops the process from outside.
6. **The reserve for `release` (C-17).** Before `main`, before each test of `unio test`, and in an executable of `unio build`, the runtime sets aside a reserve of 1 MiB (1,048,576 bytes): it is allocated, every page is written so that the system has delivered it, and it is counted in the heap. The reserve lies within `limits.heap_bytes`, not on top of it: the program may use the limit minus the reserve. A policy whose `limits.heap_bytes` is below 2 MiB (2,097,152 bytes) is refused before `main` with code 103, with a diagnostic that names the limit, the minimum, and the reserve.
   - The reserve opens only on a fault (code 101), when the fault is created and before its message and trace are allocated, so that a full heap cannot end the program with code 102 before it reaches the release path. From then on every allocation of the thread of the program comes from the reserved pages: the runtime's global allocator (`compiler/unio-runtime/src/reserve.rs`) hands out blocks of the reserve instead of asking the system. From then on the reserve, not the heap limit, bounds the path: it goes on while the reserve has room, on a full heap as well, and ends with code 102 when it needs more, whether or not the policy sets a heap limit and whether or not the heap has room. The reserve serves the message and the trace (16 bytes per frame), the unwinding, and the `release` calls of the open `using` blocks (section 5). The diagnostic is written to standard error line by line, so its text needs no memory however long the trace.
   - An allocation of the path that does not fit in the reserve is exhaustion. The allocator cannot unwind, so the block is taken from the system, counted in the heap (item 3; over the heap limit it is refused, which ends the program with code 102 at once), and the reserve counts as overflowed until it closes; the next check of the heap, at the latest the end of the `release` that overflowed, ends the program with code 102 and the preallocated diagnostic, and a buffer whose size the program decides (item 4) is refused before it is allocated when it does not fit. This does not depend on the heap: with a heap limit and a full heap, with a limit and room on the heap, and without a heap limit in the policy, where the system would grant the memory, the result is the same. The mark stays when the block is freed before any check, so a `release` that builds a large text and drops it at once, or many small blocks that add up to more than the reserve, ends with code 102 as one that keeps them does. The remaining releases are skipped: a file of `open_atomic` keeps its temporary file and its target is unchanged (S-9). A program whose `release` needs more than the reserve on the path of a fault must therefore release less there; the budget of the path is the reserve, not the heap.
   - Exhaustion (code 102) never opens the reserve, and no user code runs after it (C-18). `expect_fault` closes the reserve again once it has received its fault, and the test goes on with the budget it had. Memory that is not the program's is taken outside the reserve, as it is not counted in the heap either: the captured output of a test in `unio test` and the report of its result.
   - A test hook fills the heap exactly: with a heap limit, the environment variable `UNIO_TEST_HEAP_FREE=N` counts the heap as full but for `N` bytes before `main` (`fill_to` in `compiler/unio-runtime/src/heap.rs`, like `fail_point` of S-9b). It holds no memory and can only shrink the budget of the program. Since every block counts (item 3), a program needs some room to reach a fault: the tests of the reserve leave 64 KiB, far less than their releases take from the reserve.
7. **The parameters of the reserve and their measurements.** The reserve of 1 MiB and the minimum heap limit of 2 MiB are the initial parameters of 0.1, an engineering budget (plan section 12, closure condition 1). The test `the_reserve_peak_is_measured` (`compiler/unio/src/interp.rs`) runs the measured cases on a heap that the test hook filled to the limit, so that the whole path comes from the reserve, and reports the highest point the path reached in the reserve, of 1,048,320 usable bytes (the reserve less 256 bytes of its bookkeeping). Measured on Linux x86-64:

   | Case | Peak, bytes | Share | Margin, bytes |
   |---|---:|---:|---:|
   | Deep unwinding: a `using` block in each of 9,000 nested calls, each `release` building 20 texts and handling an error | 156,336 | 14.9% | 891,984 |
   | Repeated faults: the same stack, the innermost ten `release` calls fault in turn after handling an error, each with a trace of about 9,000 frames | 300,448 | 28.7% | 747,872 |
   | A diagnostic with a long trace: a fault 9,990 calls deep, under a long function name and file path (2 MB of diagnostic text) | 159,952 | 15.3% | 888,368 |

   Every peak fits; the largest leaves 730 KiB. The traces dominate: the stack limit is 10,000 frames, so one trace takes at most 160 KB, and the case with repeated faults holds two at once, the fault of the program and the fault of a `release`. The text of the diagnostic does not count, because it is written line by line. The parameters therefore stay as they are; the test fails if a later change makes a peak exceed the reserve.

8. **Walking a value (L-17a, C-18).** `==` and `!=`, the hash and the equality of a key of a map or a set, and the text of a value by its structure (`Debug`, which the runtime uses where it shows a value that has no `to_text`, as in the report of a counterexample of `check_property`) walk the value in a loop over a list of the parts still to visit, not by recursion, so the native stack they use does not depend on the depth of the value (`compiler/unio-runtime/src/value.rs`, "walking values"); so does that text of a struct or an enum in the interpreter and in native code (`display` in `compiler/unio/src/interp.rs`). Interpolation in a checked program needs `Display` (E0067), so it calls the `to_text` of the program. The list holds one entry for each part still to visit: one for a chain, the siblings along one path for a tree; it is counted in the heap like any allocation. The order of the visits is that of the recursion it replaced, so hashes and texts are unchanged. Before, `==` of two chains of 10 million enum values overflowed the 1 GiB stack and aborted `unio run` with code 134; `deep_values_are_compared_and_hashed_without_recursion` (`compiler/unio/tests/interpreter.rs`), `the_executable_compares_and_hashes_deep_values_without_recursion` (`tests/native.rs`), and `deep_values_are_compared_hashed_and_formatted_without_recursion` (`value.rs`, a million levels on a stack of 2 MiB) check it. Three walks are bounded instead, with exhaustion of the stack as their defined outcome (code 102 and the prepared diagnostic, L-17a):
   - The JSON conversions `std.json.to_value` and `std.json.from_value`, which `json.encode` and `json.decode` call, enter one call for each level of the value, so a value nested deeper than the stack limit of 10,000 calls, counted with the calls that lead to it, ends the program with 102 (`json_conversions_of_deep_values_end_with_102`, and in an executable `the_executable_ends_json_conversions_of_deep_values_with_102`); before, they recursed on the native stack without a bound. `json.parse` refuses text nested deeper than `max_depth` (128 by default) with `ParseError`, and the writer of `json.encode` is Unio code, whose recursion counts as calls.
   - A `to_text`, `equals`, or `compare` of the program, which interpolation, `==`, and ordering call, is a call of the program and counts against the stack limit like any other.
   - Comparing two maps or two sets looks each key up in the other, and when the keys are maps or sets themselves, the lookup compares them in turn. That nesting is bounded at 10,000 levels (`NESTED_LOOKUPS`); past it the process ends with code 102 and the diagnostic of the stack, in `unio test` too, where it ends the run.

   No operation copies a value deeply: a change copies the level that changes (section 2, item 4).

## 4. Errors and faults

1. A function with `fails with` ends either with its result or with one of its errors. `try` passes an error on unchanged; `on E as e` receives it; `fail e` ends the function with `e`. An error is a value and never unwinds past a function that does not list it, which the checker guarantees.
2. A fault (L-17) stops the program at its point. The runtime opens the reserve for `release` (section 3.6), records a trace of function names, files, and lines (C-14), unwinds the stack, calls `release` of every open `using` block in reverse order (C-17), writes the diagnostic and the trace to standard error, and ends with code 101. A fault inside `release` during this unwinding is reported and the remaining resources are still released; a `release` that exhausts the reserve ends the program with code 102 instead, with or without a heap limit, and the remaining releases are skipped (C-18).
3. A fault cannot be received by `on`. `expect_fault(action)` in a `test` block runs `action` and succeeds only if it ends with a fault; the resources opened inside `action` are released before `expect_fault` returns.
4. `assert c` and `assert_fail(m)` are faults with the text of the condition or the message.

## 5. Resources

1. `using r = e:` evaluates `e`, binds `r`, and runs the block. When the block ends, normally, through `return`, `break`, `continue`, an error, or a fault, `release` of `r` runs; several `using` blocks release in reverse order of opening.
2. `release` cannot fail: its signature has no `fails with`, and an error that happens inside it is the resource's own business (for example, `AtomicFile` ignores errors of removing a temporary file).
3. On emergency termination (code 102) and abnormal termination, `release` does not run (C-18, C-19). On a fault, `release` runs from the reserve set aside before `main` (section 3.6).
4. **What holds at each kind of termination (C-20).** `print` and `print_error` write their line to the system before they return: the runtime keeps no buffer of standard output or standard error beyond the line it writes, so at every kind of termination the lines printed before it are with the system (a pipe, a file, a terminal), unless their reader has gone; `unio test` captures the output of each test instead. Every write of `std.files` is atomic (S-9): `write_text`, `write_bytes`, `copy_file`, and `open_atomic` write a temporary file next to the target, without a buffer in the program, and rename it over the target only on commit, so the target holds its old or its new complete content whatever ends the program. The library of 0.1 has no other handle that writes a file: a write through an open handle without `open_atomic` would not be safe, since after emergency or abnormal termination its content may be cut off at any point, and that is what a temporary file left behind may be. Descriptors are closed by the operating system at every end of the process. Checked by `compiler/unio/tests/termination.rs`, one test per kind, and for code 104 by `an_incompatible_image_is_refused` (`tests/native.rs`).

   | Kind of termination | Exit code | `release` of the open `using` blocks | Standard output and error | Files |
   |---|---|---|---|---|
   | Normal end: `main` returns (C-16) | 0, or the value of `main` | already ran as each block ended | every line printed | a committed target holds its new content; an atomic file without a commit removed its temporary file in `release`, and its target is unchanged |
   | Fault (C-17) | 101 | runs for each open block in reverse order, from the reserve (section 3.6); a `release` that exhausts the reserve ends the program with 102 and skips the others | every line printed, then the diagnostic and the trace on standard error, then what the releases print | as at a normal end: no temporary file is left, a target not committed is unchanged |
   | Exhaustion (C-18): heap, stack, the heap limit, the wall or CPU time of the policy | 102 | does not run; no user code runs | every line printed before, then the prepared diagnostic on standard error; at a time limit the watchdog first stops the child processes of the program | a target holds its old or its new complete content; the temporary file of an atomic file not committed stays next to it (S-9 allows it) |
   | The sandbox or the policy cannot be applied (C-15, SB-3) | 103 | nothing of the program has run | nothing on standard output; the reason on standard error | untouched |
   | The image of an executable cannot be run (section 8.4) | 104 | nothing of the program has run | nothing on standard output; the reason on standard error | untouched |
   | A signal or a kill (SIGKILL, or SIGTERM and SIGINT, for which the runtime installs no handler; `TerminateProcess` on Windows), a crash of external code, a failure of the system, power loss (C-19) | the signal, or what the system reports | does not run | the lines whose `print` returned; a line being written when the process ended may be cut | the guarantees of S-9 only: a target holds its old or its new complete content, and after power loss guarantees 2 and 3 hold on the file systems of S-9a; temporary files stay |

## 6. Programs and tests

1. A program starts at `public function main()` of the module given to `unio run`. Without a result, the exit code is 0; with an `Int` result, it is that value, which must be 0–100, otherwise it is a fault (C-15). `main` takes no parameters and has no `fails with`; `unio check` refuses any other signature with E0090 ([semantics.md](semantics.md) 3.9), so a program never starts with arguments it cannot receive.
2. `unio test` runs every `test` block of the given modules, each in a fresh state; the order of the blocks does not matter, because there is no global mutable state. The result of each test is passed, failed with the fault that ended it, or failed with the diagnostics that keep it from compiling (T-5a), in text or JSON with name, status, time, and output (T-4). The effects analysis of `unio test` counts the tests it runs, and only those (RFC 0005, "Tests in the analysis"): the `test` blocks of the given modules that the filter selects join the program, so the function values they pass or store are possible targets of the program's calls and their effects are checked against the manifest (E0085 fails the file, and none of its tests runs). Tests of imported modules and of the standard library are not included, unless their modules are themselves given (`unio test stdlib/alloc/builtin/list.unio` runs and analyses the library's tests). `unio check` and `unio run` include no test. Including tests never widens the manifest or the external policy: a test body runs in the sandbox, which still denies what they do not permit.
3. Top-level constants are evaluated once, in dependency order, before `main` or before the first test that needs them; a constant whose evaluation faults ends the program with that fault.

## 7. External functions

1. The standard library declares 118 external functions, all in `unsafe module` files (S-7, S-10). Each is bound by its full name, such as `std.files.system_rename` or the method `Text.slice`, to a function of the runtime. The documentation comment of the declaration is its specification.
2. A test of the runtime checks that every external declaration has a binding and every binding has a declaration, so that the library and the runtime cannot drift apart.
3. The groups and the layer each needs:

| Clocks, sleeping and entropy | `std.time.monotonic_nanoseconds`, `wall_nanoseconds`, `sleep_nanoseconds`, `std.random.entropy`, `secure_bytes`, `secure_int` (derived effects `clock` and `random`, [semantics.md](semantics.md) 8.2) | std |

4. `unio run` and `unio test` start every program inside the sandbox of requirements section 4.6: the permissions of the nearest `unio.toml`, narrowed by the policy, are applied before `main` or before the first test. Section 9 says how this works and where its limits are.
5. Behavior fixed while implementing the externals, where the declarations were silent:
   - `Float.to_text` writes decimal notation for exponents from −6 to 20 and scientific notation otherwise (`1e+300`), always with a fraction for whole numbers (`2.0`), and `nan`, `inf`, `-inf` for non-finite values; `Text.to_float` does not read the last three back.
   - `Text.index_of` with a `start` outside `0..length()` is a fault, like `slice`. `Int ** n` with a negative `n` is a fault.
   - `Float.to_int` gives the Int only for a whole number in `MINIMUM_INT..MAXIMUM_INT`; `std.math.round` rounds a half away from zero; the transcendental functions of `std.math` are those of the platform's `libm` and may differ in the last bit between platforms. `std.random.entropy` reads `getentropy` on Linux and macOS and `BCryptGenRandom` with the preferred system generator on Windows, and ends the program with a fault if the system gives no entropy; the monotonic clock counts from the first reading of the process; the tables of `std.text` normalization and graphemes are generated by `.github/scripts/unicode_tables.py`, whose version and licence `THIRD-PARTY-NOTICES` records.
   - `std.files.rename` never replaces a target, and the check is part of the rename itself: `renameat2` with `RENAME_NOREPLACE` on Linux, `renamex_np` with `RENAME_EXCL` on macOS, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows. Where the system or the file system lacks this, a file is linked under the new name (which fails if the name exists) and then unlinked, and a directory fails with kind `Unsupported` instead of racing with another process.
   - `std.files.list_tree` does not follow a symbolic link to a directory: the link is listed as an entry, so a cycle of links ends and a link cannot lead the listing out of the tree. A link is recognized because `resolve` of it is not its own place in the resolved tree.
   - `std.env.home_dir` asks the operating system for the profile directory of the user; on Windows that directory is what the system reports through the user profile, not a variable the program set.
   - `std.process.run` gives a child an empty standard input; a child ended by a signal has status 128 plus the signal number; a timeout of zero or less is a `ProcessError` of kind `Other`. The child gets an environment built for it (9.5), runs in a process tree of its own, and has each output captured up to 16 MiB; section 9.5 gives the rules.

## 8. The interpreter of sprint S5 and native code of sprint S6

1. The interpreter of S5 walked the checked syntax tree with the tables of the checker. Sprint S6 lowers that tree first (`compiler/unio/src/lower.rs`): names are resolved to slots of local values and indexes of constants, field positions and enum variants are found once at each place, literal lists and tuples are built once, and calls share one value stack. Several prelude functions (`is_empty`, `first`, `last`, `enumerate`, `contains`, `keys`, `values`, `append_all`, `range`, `Text.to_int`) run as intrinsics of the runtime with the results of their Unio definitions. The same lowered form is the input of native code (item 4). Measurements are in [bench/README.md](../bench/README.md).
2. The interpreter is the reference for the meaning of programs: native code must give the same output, exit code, and diagnostics for every test of the repository (item 5).
3. Exit criterion of S5: every `test` block of `stdlib/`, `examples/`, `docs/examples/`, and `tools/` runs and passes; the tools in `tools/` run in the interpreter and give the same results as the Python checkers, which stay in the repository as the reference for parity and for comparisons of performance.
4. **Native code (S6).** `unio build [--release] FILE [-o OUT]` makes one executable (C-5) for the machine the compiler runs on: Linux on x86-64 or AArch64, macOS on AArch64, or Windows on x86-64 (MSVC); on any other machine it stops with a message that names these four. The build checks the program as `unio run` does, lowers every body as the interpreter does, and translates each lowered body (functions, lambdas, constants, defaults of fields and of parameters of externals) with Cranelift into one object file (ELF, Mach-O, or COFF, with the calling convention of the system: System V, Apple's AArch64, or Windows x64), which the system linker links with the runtime built from the compiler's crate (`libunio.a`, on Windows `unio.lib`) and the system libraries that the runtime needs: on Linux the C compiler (`cc`, or `CC`); on macOS `clang` of the selected developer tools with their SDK, both found by `xcrun` before the link step (or `CC`), for macOS 11 or later and without a debug map; on Windows `link.exe` of the newest Visual Studio C++ build tools, found as rustc finds it (or from a developer command prompt), with `/Brepro`, so that the executable carries no time stamp. Without `-o` the executable is named after FILE, with `.exe` on Windows. The runtime library is `UNIO_RUNTIME_LIB`, the file next to the compiler (as `cargo build` leaves it), or `lib/unio/` beside the `bin/` directory of an installed compiler: the installed layout is `PREFIX/bin/unio`, `PREFIX/lib/unio/libunio.a` (`unio.lib`), and `PREFIX/share/doc/unio/` with the licence files, made by `.github/scripts/release_build.sh` (plan section 12, release condition 1). The standard library is embedded in the compiler, so an installed compiler needs no file of it (RFC 0004; `trusted_stdlib` in `compiler/unio/src/program.rs`). `--release` optimises the generated code (Cranelift's level `speed`, with every function starting at a 64-byte boundary so that its speed does not depend on the code placed before it); without it Cranelift does not optimise. The design (`compiler/unio/src/native/`):
   - Values have the layout of the runtime: `Value` is `repr(u8)`, its first byte is the tag, the payload of `Int` and `Float` is at offset 8 and that of `Bool` at offset 1. A local whose type is `Int`, `Float`, or `Bool` by its signature or by its binding is kept unboxed in a register. Operators on such values are machine instructions with the checks of section 2: an addition is one add and a branch on overflow, a division tests zero and `MINIMUM_INT / -1`. Values of these types never touch a reference count. `for i in range(a, b)` is a counted loop that tests its bound once before the first iteration and then at the end of each. An operation is compiled without its overflow check only where bounds known to the code prove the result in range: the variable of a counted loop with literal bounds, and a parameter of type `Int` after a test of it against a literal that is known to have held or failed (`if n < 2: return n` gives `n >= 2` below it); neither can be assigned (L-10). An addition or subtraction of an operand whose sign is known is checked by one comparison of the result with the other operand. `x % c` and `x / c` for a literal `c > 1` and an `x` known not to be negative are a multiplication by a reciprocal without the corrections for the sign; for other operands Cranelift's division by a constant keeps the rule of 2.1 (`/` truncates toward zero, `%` has the sign of the left operand). Every operation whose range is not proven keeps its check, so each fault of the interpreter happens natively at the same place. Where the type is not known statically, integers are recognised by their tags and still computed inline; comparisons of texts, integers, and booleans are made where the values are, without copying them.
   - A call of a function with a body and without type arguments is a direct call: scalar parameters and results travel in registers, other values by address and are taken by the callee, `var` parameters come back through their addresses, and the depth of the runtime's call stack with the callee's frame is one more argument in a register. The callee pushes its frame with one comparison against the stack limit and one store of its site with the line of its declaration; popping it costs nothing. Memory holds the depth and the line of the current statement only where the runtime can read them: before a call of the runtime that receives the context (one that can fault or run code) the code stores both, before a direct call only the line, and a statement without such a call stores nothing. The line is a variable of the generated code that each statement sets, so after a loop, a branch, or a handler the stored line is that of the statement that started last, as in the interpreter; traces and the stack limit (C-14, C-18) are those of the interpreter. A function whose body starts with clauses `if c: return v` that read only scalar parameters and cannot fault has them decided at each direct call: when the stack has room for the callee's frame and a condition holds, the result is `v` and no call is made; at the stack limit the call is made and ends with code 102 as it would.
   - Operations on values that own memory call the runtime: dispatch of a method by the type of its receiver with a cache at each call site (an external or a compiled method is then called without a frame of the interpreter), fields (read in place when the frame holds the value, changed in place when assigned), indexing, construction with defaults, interpolation, patterns, iteration, places with indexes, and the externals.
   - Errors, faults, and exhaustion unwind by status: an operation that fails returns status 1, and the code releases the temporaries it holds and continues at the innermost handler of `try` or `on`, at the release of an open `using` block (C-17), or returns status 1 to its caller. `break`, `continue`, and `return` release open `using` blocks on the way, as in the interpreter.
   - **The program image.** The executable holds a program image prepared by the build, not the sources (`compiler/unio/src/native/image.rs`): the declarations the run needs (modules, types with their fields and variants, functions with their parameters, constants, implementations), every lowered body that the native code refers to, and the permissions the manifest declares; apart from them, as diagnostic metadata, the file of each module and the line of each function for traces. Declarations are numbered in the order of the build and named by module and name, from which the run derives the identity of each type as `unio run` does; externals are bound by name at start. The image is versioned: it starts with a mark, the format version (2), the identity of the compiler (its version and a hash of the sources of the compiler and of the runtime), and the identity of the toolchain that linked the executable (below). An executable whose image is of another format, was made by another compiler than the runtime linked into it, or is damaged stops before `main` with a message saying which and code 104 (one of the codes C-15 reserves for the runtime).
   - **The start.** Before `main` the executable reads the image, builds the interpreter's tables from its declarations, installs the lowered bodies and the native code of every unit, fills each body's table of references (the caches of its call sites and its literals), applies the sandbox of the manifest narrowed by the policy of `UNIO_POLICY` (SB-1; the arguments belong to the program, so there is no `--policy`), and runs `main` on a thread with the stack of `unio run`. It neither parses, checks, nor lowers anything, and the parser, the checker, and the lowering are not linked into it. An empty program starts in about 2.6 ms (7.1: at most 5 ms; [bench/README.md](../bench/README.md)).
   - **Paths.** The image holds no path of the machine that built it. A trace names the file of a module relative to the root of its package (the directory of its `unio.toml`, or of the file without one), and a module of the standard library as `std:` with its path below the library (`std:core/prelude.unio`); `unio run` and `unio test` name files in the same way, so traces are the same natively and in the interpreter, wherever the program was built or runs.
   - **Permissions of an executable.** The executable keeps the entries of `[permissions]` as the manifest writes them and expands them when it starts: `$CWD` is the working directory of the run, `$HOME` and `$TEMP` are those of the run, and absolute paths stay as written; the policy of `UNIO_POLICY` narrows them as for `unio run`. A relative entry of `files.read` or `files.write` is relative to the directory of the manifest (T-6a), which an installed or moved executable does not have, and binding it to the working directory or to the directory of the executable would change what it grants; `unio build` therefore refuses such a manifest, names the entry, and suggests `$CWD/...` or an absolute path. An executable moved to another directory, with its project gone, runs with the same permissions.
   - A construct that the generator cannot compile yet stops `unio build` with "not yet compiled natively" and its file and line; nothing falls back to the interpreter. Refused so far, and used by no program of the repository: an argument of a method call that changes the name of the receiver through `var`, an indexed place as a `var` argument of a method whose name has a `var` parameter, and `var self` on an indexed place whose index has effects.
   - Builds are deterministic: the same sources give the same bytes, also when the project is copied into another directory and built there with another home and temporary directory (C-4).
   - **The toolchain.** Pinning the code that finds the linker does not pin the linker it finds, so a build records the linker and the SDK it links with. Before the compile step the `unio` tool computes the identity of its toolchain (`compiler/unio/src/native/toolchain.rs`): the target triple, then on Linux the C compiler and the first line of its `--version` (`x86_64-unknown-linux-gnu; cc: cc (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0`); on macOS the compiler, the first line of its `--version`, and the version of the SDK (`xcrun --show-sdk-version`, else the name of the SDK); on Windows the version of the MSVC toolset of `link.exe` (from its directory `VC\Tools\MSVC\<version>`, else from its banner) and that of the Windows SDK (from the directory `Windows Kits\10\lib\<version>\um` in `LIB`): `x86_64-pc-windows-msvc; link.exe: MSVC 14.51.36231; sdk: Windows 10.0.26100.0`. It holds tool names and versions, never a path of the machine, so it is the same wherever the same toolchain is installed. The tool runs these queries itself, as it runs `xcrun` on macOS, not in the sandbox of the link step. The worker writes the identity into the image after the identity of the compiler; the run does not check it. `unio build --print-toolchain` prints the identity a build would record and builds nothing; `native::image::made_by_executable` reads the identity back from an executable (the image holds it as a plain UTF-8 text). Two builds are the same bytes only on the same toolchain, which the record names. When the linker is missing (`cc` or `CC` on Linux, the developer tools on macOS, `link.exe` on Windows), `unio build` stops before compiling with a message that names it and says what to install; it installs nothing.
   - **Targets.** The four targets differ only in the instruction set, the calling convention, the object format, and the linker. Values have the layout of the runtime on each (64-bit, little-endian); the depth of the call stack is the runtime's counter, not the machine stack, so traces and the stack limit (C-14, C-18) are the same on every target; the thread of `main` has the stack of `unio run`, and frames probe the machine stack page by page (Cranelift's inline probes), so no frame skips a guard page. The division by a constant above is generated as Cranelift's `umulhi`, exact on both instruction sets. The executable applies the sandbox of its system as `unio run` does there (Landlock and seccomp, Seatbelt, the AppContainers of 9.4 on Windows) and reads its arguments, on Windows, from the UTF-16 command line as `unio run` does. A test of the code generator builds object files of reference programs for all four targets on any machine, verified by Cranelift and the same in two builds (`native::tests`); linking and running happen only on each target.
5. **Equivalence.** `compiler/unio/tests/native.rs` builds every reference program that the tests of the interpreter run (the utilities with their inputs, the task list, programs that end with every kind of fault and with exit codes, the benchmarks, and the four tools of `tools/` over the repository), runs each natively and with `unio run`, and compares standard output, standard error, and the exit code. It also checks that two builds are identical, also of one project copied into two directories, that a program with errors is not built, that the executable applies the manifest of its package and, moved to another directory without its project, the same permissions, that traces name files relative to their package, that the fast paths of the generator (lines stored before calls, bounds that remove overflow checks, division by constants, leading clauses decided at the call) keep each fault, trace, and exit code, that the identity of the toolchain that `unio build --print-toolchain` prints is the one the executable carries and contains no path of the machine, that a missing linker (a `CC` that does not exist, on Linux and macOS) stops the build with a message and no executable, and that an image of another format, of another compiler, or damaged is refused with code 104 (on macOS the changed executable is signed again with an ad-hoc signature, since the system runs only signed code). CI runs it in the `compiler` job on Linux x86-64, macOS on AArch64, and Windows x86-64, and in the job `native-linux-arm` on Linux AArch64; on any other machine it is skipped with a note.
6. **Not done yet**, in the order that matters for speed: types of the checker in the lowered form, for static dispatch of methods and for monomorphised generics (kinds are now inferred locally from signatures and bindings); elision of reference counts and reuse in place in the style of Perceus (dup and drop by last use, borrowed parameters, reuse of a released cell by a construction of the same size); unboxed lists of scalars; an optimising release back end.

## 9. The sandbox in practice

This section is the documentation of the limits of the sandbox that SB-9 requires.

1. **Where permissions come from.** `unio run` and `unio test` read `[permissions]` from the nearest `unio.toml` above the program (T-6) and narrow it by the policy (SB-3a). Without a manifest, a program can read its arguments and standard input and write to standard output and standard error, nothing else (SB-2). Tests get the same permissions as the program; a test that needs files declares them, for example `files.write = ["$TEMP/**"]`.
2. **Paths and writes.** Relative entries are relative to the directory of the manifest or the policy. Links and `..` are resolved before a path is compared, in the order the system takes them, and the operation then uses the path that was checked, so that what is authorized and what is opened agree (`resolve` and `walk_path` in `compiler/unio-runtime/src/sandbox/mod.rs`). On Linux and macOS the system follows a link before the `..` after it, so `open/link/..` is the directory above the link's target, not `open`: the path is resolved one component at a time from the root, each link is replaced by its target before the next component is taken, and below the first missing component the rest is taken by its text. On Windows the system removes `..` from the text first, and so does the check. A read-class operation (`read_text`, `read_bytes`, opening a file to read it in chunks, `exists`, `is_directory`, `list_directory` and so `list_tree`, and `resolve`) uses the resolved path. In a sandbox on Linux and macOS, the full one or the weaker one, it reaches that path from the directory of the scope that covers it without following a link in any component (`compiler/unio-runtime/src/sandbox/beneath.rs` and `fdio.rs`): the anchor is the root of a subtree scope, or the directory that holds a scope of one file. On Linux the anchor is opened one component at a time from `/` (`O_PATH`, `O_NOFOLLOW`), and the rest relative to it with `openat2` and `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS`, or, where the kernel has no `openat2` (before 5.6), one component at a time with `openat` and `O_NOFOLLOW`; `exists` and `is_directory` open the object with `O_PATH` and ask `fstat`, and `list_directory` reads the names from the opened descriptor (`fdopendir`). On macOS 11 and later the checked path, which has no `.`, `..`, or link, is opened with `O_NOFOLLOW_ANY` and examined with `fstatat` and `AT_SYMLINK_NOFOLLOW_ANY`, which fail on a link in any component, the last one included; `O_NOFOLLOW_ANY` is passed without `O_NOFOLLOW`, because the kernel refuses the two together (`EINVAL` on macOS 26, CI run `43302933957`); on an older macOS a read in a sandbox fails. A link that another process puts on the path after the check therefore makes the operation fail (`exists` and `is_directory` report `false`) instead of leading it out of the scope: it is refused, not followed and checked again. `resolve` reports the resolution that was checked, once the object is confirmed to exist in this way, never a second resolution by name. A write-class operation names an entry: its directory is resolved and its last name kept as given, so a link as the last name is the entry itself. Writing one file also permits the temporary files of its atomic commit next to it and syncing its directory. A program name without a path matches only a call by that name, never a path that ends in it.
   - **The writer process.** On Linux and macOS a program has no right to write files at the level of the operating system, and neither have the children it starts. Every write-class operation of `std.files` is a request to a writer process: the steps of `AtomicFile` (and so `write_text`, `write_bytes`, and `copy_file`), `create_directory`, and `rename`. The writer is started from the same executable before the sandbox of the program applies, with an empty environment, closed standard input and output, and one end of a socket pair. It receives the effective write scopes (the manifest narrowed by the policy, SB-3a) once, before any code of the program runs, and accepts no other configuration. Then it applies its own sandbox: on Linux `no_new_privs`, Landlock with write access to the write scopes only (a scope of one file on its directory, a right only the writer holds), no reading of other files and no TCP, and seccomp without exec, new processes or threads, and sockets; on macOS a Seatbelt profile with the write scopes, the temporary files of each scope of one file, and reading of the directories on the way to them. The writer ends with the program: the socket closes, and on Linux a parent-death signal kills it.
   - **What the writer checks.** The runtime checks each operation first, as everywhere (item 3); the writer checks it again against its own scopes and does not trust the program. It opens the directory of a path one component at a time from `/` with `O_NOFOLLOW` (on Linux also `O_PATH`), refuses a link on the way, and does every later step relative to that descriptor. A temporary file is created with `O_CREAT | O_EXCL | O_NOFOLLOW` under the name `.<name>.unio-tmp-<writer pid>-<operation id>`; the commit renames it over the target in the same directory with `renameat`; `durable = true` syncs that directory; `rename` uses `renameat2` with `RENAME_NOREPLACE` (`renameatx_np` with `RENAME_EXCL` on macOS); `create_directory` uses `mkdirat` and then syncs the directory that holds the new one (10.4). A directory replaced by a link between two requests therefore cannot lead a commit elsewhere, and a new request through the link is refused. A link as the last name of a target is replaced as an entry and never followed. Operation ids are unpredictable 64-bit numbers issued by the writer: only the operation that created a temporary file can commit or remove it, and a commit must name the target of its operation. The program receives a descriptor of its temporary file (passed with SCM_RIGHTS and closed on exec) and writes the data itself, so the data does not pass through the writer and the file-size limit of the program applies to it. The writer also answers whether a target supports `durable = true` (S-9a), from the mount table it read before its sandbox applied.
   - **The protocol** is versioned and length-prefixed: a frame is a 32-bit little-endian length, then a version byte, an operation byte (configuration, durability query, open, commit, abort, sync by operation, sync of a directory, create a directory, rename), and its fields: 64-bit numbers and byte strings with a 32-bit length. A reply carries a status: done, refused, an error of the system with its number, or malformed. A request that cannot be decoded, of another version, or a second configuration is refused as malformed; a frame over 1 MiB ends the connection. At most 256 atomic files are open at once in one program.
   - **Windows** has no writer process; the writer is a second AppContainer of the program (item 4). The thread of the program takes the token of that container only for a write-class operation of the runtime, after the checks of the runtime, on the paths those checks resolved, and returns to the token of the program right after it (`Program::as_writer` in `compiler/unio-runtime/src/sandbox/windows.rs`). The writer's container holds the write grants: a tree of a write scope with everything in it, and for a scope of one file the right to create, replace, and remove entries of its directory without listing or reading it, the directory-level right the writer process holds on Linux, with an entry that what it creates there inherits, so that it can write its temporary file; that entry is removed from the directory and from the files in it when the program ends. Neither the token of the program nor its children have any write grant. The design differs from Unix in one point: the writer runs on the thread of the program, so it checks nothing the runtime has not checked; what it adds is that the operating system confines each write to the write scopes, so a defect of the checks cannot write elsewhere.
   - **What the checks alone cannot exclude.** Where the operating system does not enforce the scopes (Linux and macOS with a weaker sandbox, SB-5, and the checks-only mode of the tests on Windows), the runtime checks are the only barrier. On every system they hold against a link that another process puts on a checked path between the check and the use: every read-class operation reaches the checked path without following a link (above), and every write goes through the writer. The test `a_link_swapped_in_after_the_check_reveals_nothing_outside_the_scope` (`compiler/unio-runtime/tests/files.rs`) swaps a directory and a file of the scope for links out of it in a tight loop, under the runtime checks alone, while the program reads, lists, asks about, and resolves paths through them, and finds nothing from outside. On Windows the same walk opens the anchor by its path as itself (`FILE_FLAG_OPEN_REPARSE_POINT`) and confirms by its final name that it is the checked directory (a directory above it replaced by a junction would give another name), then each name relative to the handle of the one before (`NtCreateFile` with `RootDirectory` and `FILE_OPEN_REPARSE_POINT`) and refuses any handle whose attributes name a reparse point (`ERROR_STOPPED_ON_SYMLINK`), for reads, `exists`, `is_directory`, `list_directory` (listed from the handle), and `resolve` (`sandbox/windows.rs`, `Steps`). Since Windows has no writer process, its writes open the same way: the directory of the entry from the directory of its write scope, then the temporary file created in it, the commit a rename relative to that handle, written through (`FILE_WRITE_THROUGH`, as `MOVEFILE_WRITE_THROUGH`), `rename` relative to the directory of the target without replacing, `create_directory` and the removal of a temporary file in the same way. The reader of a program may enter, not list, the directory above each read scope, since a scope's own root and a scope of one file are opened from there. The race test runs on Windows with symbolic links (junctions where the account may not make them) and races the writes too; with the walk disabled it finds the leaks (CI runs `43290120156` and the negative control `43290978690`). A Unio program cannot make links itself, but a child it may run can. The directory sync of a durable write (`system_sync_directory`) still opens its directory by name on every platform; it reads no content and reveals nothing but whether the sync succeeded.
3. **Blocked operations** are the errors the functions declare, of kind `PermissionDenied`, naming the missing permission; `exists` and `is_directory` report `false`, and `env.get` reports `none` (SB-6).
4. **Platforms.**
   - Linux: the runtime checks every operation, and the operating system enforces the read scopes with `no_new_privs`, Landlock (files, TCP, signals), and seccomp (sockets, `ptrace`, mounts, namespaces, `io_uring`, `bpf`, and other dangerous calls); core dumps are disabled. The program and its children may write no file; the writer process writes for the program (item 2). Children may start with `execve` only the listed programs, the interpreters of listed scripts, and the dynamic loader of listed ELF programs, and read only the read scopes and what those programs need to start; through the loader and a listed interpreter they can run more than the list (item 5). Without Landlock ABI 3 or seccomp the start fails with code 103 unless the operator allows a weaker sandbox.
   - macOS: a deny-by-default Seatbelt profile built from the read scopes; the program and its children may write no file, and the writer process writes for the program (item 2); children may start only the listed programs and the interpreters of listed scripts, and a listed interpreter runs any script it can read (item 5). Seatbelt restricts the whole process once, so the writers of all programs of one `unio test` start before the first profile applies. The profiles are checked in CI on macOS.
   - Windows: each run of a program gets two AppContainers of its own, created as profiles with fresh names (`unio.<process>.<random>`, so a SID is never reused) and without capabilities, so they reach no network, not even the loopback; both profiles are deleted when the program ends (`compiler/unio-runtime/src/sandbox/windows.rs`). The reader holds grants on exactly the read scopes, the files of the listed programs (read and execute), and the working directory (entering it, not listing it, since a process whose working directory it cannot enter starts no process); the writer holds the write grants (item 2). A grant is an entry for the SID of the container in the DACL of the root of a scope; for a tree it is written on everything below the root as well, whatever the DACL of each entry inherits, and new files get it by inheritance. The walk does not follow reparse points, so a link or junction in a scope carries no grant to its target. The entries are removed when the program ends; changes of DACLs are serialised between the processes of the user by a named mutex, since runs share directories. Directories may be entered and listed, files read; a file of a read scope is not executable. The thread of the program impersonates a token of the reader (a lowbox token made from the token of the process), checked to be at the level that opens files and inside the AppContainer, so its own opens are checked by the system, and every child is created in the reader with `CreateProcessW` and the security capabilities of the container, which children of children inherit. Writes go through the writer's token (item 2). The operating system then denies a child, and the thread itself, every file outside the grants except what every application package may read (the system directories, `Program Files`), every write outside the write scopes, and every connection. Inside a container the system does not give the drive letter of a path, since it cannot reach the mount manager, and normalizing a name in that form would need the directories above it, which it may not open; so the runtime and the compiler resolve a path to its normalized name with the NT name of its volume and turn the volume into its drive letter by a table read before the container applies (a worker gets the table from the tool), which keeps the resolution of links of item 2 (`windows::canonicalize`).
5. **Limits.** Wall and CPU time are enforced by a watchdog that ends the program with code 102; the CPU limit also applies to children. The process limit `limits.processes = N` counts every process the program starts: each call of `process.run`, and each process that a child or one of its descendants creates. A call past N fails with `PermissionDenied` before the child starts. In the trees of the children:
   - **Linux:** with a limit, the thread of the program installs one more seccomp filter, with a listener (`SECCOMP_FILTER_FLAG_NEW_LISTENER`), that makes `fork`, `vfork`, and `clone` without `CLONE_THREAD` wait for the runtime (`clone3` already fails with `ENOSYS`, and the C library then uses `clone`). A thread of `unio`, started with the program, answers: a creation by the thread of the program is a call of `process.run`, counted already; every other one counts one more, and once N are counted it fails with `EAGAIN`, so a shell reports that it cannot fork. The filter cannot be removed and every descendant inherits it, so the count is exact and nothing is created past it. It needs Linux 5.5 (user notification with `SECCOMP_USER_NOTIF_FLAG_CONTINUE`); without it a program with a limit does not start (code 103), and without seccomp at all (a weaker sandbox) the limit counts the calls only. It needs neither root nor a delegated cgroup; `RLIMIT_NPROC` was not used because it counts every process of the user (and none of root), and a user namespace to separate the count is closed by the sandbox itself (`unshare` and the namespace flags of `clone` are denied).
   - **Windows:** the Job Object of a child allows at most the processes the limit leaves at once (`JOB_OBJECT_LIMIT_ACTIVE_PROCESS`), so the system refuses a creation past it, and a thread counts every new process from the messages of the job (`JOB_OBJECT_MSG_NEW_PROCESS`). When the count reaches N the job allows no further process; a tree that created more in the moment before (between two creations, a new process can start before the message of the previous one is handled) is terminated, and the call fails with `PermissionDenied`. So a tree never runs more processes at once than the limit leaves, and one that started more in all is stopped.
   - **macOS:** the system cannot count the creations of a tree without root (`RLIMIT_NPROC` counts every process of the user, and `NOTE_TRACK` of kqueue no longer exists), so with a limit the children of the program may create no process at all (RFC 0011). After the runtime forks a child and before the child runs its program, the child sets its soft and hard `RLIMIT_NPROC` to 0 (`deny_process_creation` in `compiler/unio-runtime/src/sandbox/mod.rs`); `fork1` of XNU, which serves `fork`, `vfork`, and `posix_spawn`, then fails every creation of the child with `EAGAIN`, a process that is not root cannot raise the hard limit again, and the limit is inherited across `exec`. A child may still `exec` a listed program, which creates no process. A shell reports that it cannot fork; the `bash` that is `sh` on macOS first retries for about 15 seconds. A limit that cannot be set fails the spawn before the child runs. The program itself still starts its children through `process.run`, each counted before it starts, so the program causes at most N processes in all. Seatbelt cannot carry this rule: the children run under the profile of the program, which must allow `process-fork` for `process.run`, and a process under a profile cannot apply another one. The kernel does not apply `RLIMIT_NPROC` to a real user of 0, so both ways to it are closed. A program whose real or effective user is 0 does not start with a limit: code 103 before `main`, with a reason that names both users (`root_refusal`; the test hook `UNIO_TEST_AS_ROOT=1` simulates root and can only refuse). And before each call starts its child, the runtime checks every file the profile lets a child execute (`process-exec`: the listed programs and the interpreters of listed scripts, resolved once with links resolved; in `unio test` those of all its programs): each is opened without following a last link and checked with `fstat`, and a set-user-ID or set-group-ID file, a path that is a link now, or a file that is not regular fails the call with `PermissionDenied` (`verify_executables`). The program is then executed by the checked path, with its name as written as `argv[0]`, and the child checks the same files again right before it executes, each still the same device and inode without either bit, or the start fails with `EPERM` (`recheck_executables`). macOS has no `fexecve`, so a listed file replaced after that check, or given a bit, while a child runs is not seen; doing that needs root or write access to the listed path, which neither the program nor its children have (item 2). The search of the tree every 5 ms that the limit used before is removed; the search of the descendants that stops a tree stays.

   The file-size limit is checked by the runtime and, on Linux and macOS, by the operating system. Child processes of `process.run`:
   - **What a child may run and read.** A child inherits the rules of the program, and a `process` permission adds to them only what the listed programs need to start. Each listed name is resolved as the runtime resolves it (a bare name through every directory of `PATH`, a path as written, links resolved). Exactly the resulting files may be started with `execve`, with what the next sentences add. A file that starts with `#!` adds its interpreter, and when the interpreter is `env`, the program `env` is to run, found through `PATH`; a listed script therefore runs its interpreter and nothing more. On Linux an ELF file adds its dynamic loader (`PT_INTERP`), which the kernel executes, and the shared libraries of its `DT_NEEDED` entries, found through its `DT_RUNPATH` or `DT_RPATH` (with `$ORIGIN`), `/etc/ld.so.cache`, and the library directories, and followed in turn; a library outside the library directories may be read as a single file. The library directories `/lib`, `/lib32`, `/lib64`, `/libx32`, `/usr/lib`, `/usr/lib32`, `/usr/lib64`, `/usr/libx32`, and `/usr/local/lib` may be read but not executed, since programs load libraries and modules from them at run time (the NSS and `gconv` modules of the C library, the library of an interpreter such as Python); so may the files `/etc/ld.so.cache` and `/etc/localtime`, and `/dev/null` may also be written. On macOS the listed files and the interpreters of listed scripts may be executed, `/bin/sh` adds the shell that `/private/var/select/sh` names, and the system libraries may be read and mapped: `/usr/lib`, `/System`, `/Library/Apple`, `/private/var/db/dyld`, and `/private/preboot/Cryptexes` (the dyld shared cache), with `/private/etc/localtime` and the names in `/`. Nothing else may be started with `execve` or read beyond the read scopes: a child that may run `sh` cannot start `/bin/cat` or `/usr/bin/env`, by path or by name, and cannot read `/etc/passwd` or a file outside the scopes. A program that reads its own data outside these places (for example under `/usr/share` or `/opt`) needs a read scope for it in the manifest, which the program then may read too.
   - **What a child can run in effect.** The list names what the kernel may start, not everything a child can run, so the capability is wider than the list:
     - On Linux the dynamic loader of a listed ELF program may be executed, and the loader is itself a program that loads and runs any ELF file it can read (`ld-linux-x86-64.so.2 FILE`) without `execve` of that file. Every ELF program a child may read, in the library directories, among the libraries added outside them, and in the read scopes of the manifest, can therefore be run, listed or not. A statically linked program brings no loader, but a listed dynamically linked one is enough.
     - Shared libraries are mapped as executable code: on Linux those of `DT_NEEDED` and every file of the library directories, on macOS the system libraries listed above, to which the profile grants `file-map-executable` (the read scopes may be read but not mapped as code there). Landlock and Seatbelt restrict starting a program, not mapping a readable library, so the code of these files runs inside the processes that load them.
     - A listed interpreter, and the interpreter a listed script brings (`sh`, `python3`, `perl`), runs any script it can read and any code given in its arguments (`sh -c`, `python3 -c`); a listed program that executes its input (a shell, `awk`, `make`) does what that input says.
     - Listing a program therefore grants running everything that program can be made to run with the rights of the child: listing an interpreter grants running any script the child can read, and on Linux listing a dynamically linked program grants running any ELF program the child can read. What stays closed is a program the child can neither start nor read: on Linux `/usr/bin`, `/bin`, `/sbin`, and the other directories of programs outside the read scopes; on macOS every program that is not listed, since a child cannot start the system loader there. No child can write a file (item 2), so it cannot make a program to run, and every process it starts keeps the same rules. Running an anonymous file (`memfd_create` with `execveat`) is not covered by a test. A manifest should list an interpreter or a shell only when the program needs one, and read such an entry as granting every script the child can read.
   - **Environment.** A child receives only the variables the effective permissions grant under `env`, and `PATH` (on Windows also `SystemRoot`), with the values of the running program; nothing else is inherited. On Windows the system adds `LOCALAPPDATA`, `TEMP`, and `TMP` in the AppContainer, naming the folders of its own profile (a process of an AppContainer does not start without `LOCALAPPDATA`), so they tell the child nothing of the user's. `PATH` is passed because the runtime finds a program by its bare name through it and the child may run further programs in the same way; `SystemRoot` because system libraries on Windows do not load without it. Locale, time zone, home, and temporary-directory variables are not passed unless granted, and a child without them uses the defaults of its system (for example the C locale). Without a sandbox, as in the tests of the runtime, a child inherits the whole environment, matching `env.get`, which then permits every variable.
   - **Process tree.** On Unix the child leads a new process group, and every process it starts belongs to it. On Linux no descendant can leave the group: after making its group and before running the program, the child installs a seccomp filter that fails `setsid` and `setpgid` with `EPERM` for it and every process it starts (also without a sandbox, with `no_new_privs` set in the child). On macOS a descendant can leave the group, and stopping the tree freezes the group with SIGSTOP, finds the descendants of the child through their parents (`proc_listpids`) and, under the Seatbelt profile of the program, through the marker of that profile, and freezes each until two rounds find nothing new, then sends SIGKILL to them and to the group. The marker is a pair of rules at the end of the profile, named after a random token of the process: reading one preference domain is allowed (`user-preference-read`), reading another is denied. It names preference domains rather than paths because `sandbox_check` reports a path that does not exist as denied for every process, with or without a profile; the allowed domain grants nothing, since reading a preference needs `cfprefsd`, which the profile does not let a process reach. `sandbox_check` reports exactly this pair only for processes under that profile, which no process can leave or change and which every process it starts inherits, so a descendant whose parent has already ended is found too. On Windows the child is created suspended (`CREATE_SUSPENDED`) by the runtime's own `CreateProcessW` (in the AppContainer of the program, with exactly its three standard handles inherited), put in a Job Object with kill-on-close and without breakaway (neither `JOB_OBJECT_LIMIT_BREAKAWAY_OK` nor `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` is set), and only then resumed, so its first instruction already runs in the job and a process in the job cannot start a child outside it. When the job cannot be created, configured, or assigned, the suspended child is terminated before it ran and the call fails with a `ProcessError` of kind `Other`. When the child ends, the processes still running in its tree are stopped (SIGKILL to the group, which happens before the child is reaped, so the number of the group cannot be reused in between; on Windows the job is terminated). On a timeout, on output over the limit, and on exhaustion the whole tree is stopped. When the watchdog ends the program with code 102, it stops the trees of the children that still run. The trees are implemented in `compiler/unio-runtime/src/sandbox/tree.rs`.
   - **Deadline and output.** `timeout_seconds` covers the whole call, including reading the outputs. If the child has ended but a pipe stays open, the call waits for it only until the deadline and then fails with `TimedOut`; waiting on pipes is always bounded. Each of standard output and standard error is captured up to 16 MiB (16,777,216 bytes); more fails with kind `OutputTooLarge`. The captured bytes count against the heap limit as they arrive, and exceeding it ends the program with code 102. Between the pipes and the call the output passes through a bounded queue: a reader stops reading while its chunks are not taken, so at most 384 KiB are on the way (`IN_FLIGHT`: two chunks of 64 KiB in the queue and, for each stream, the chunk that waits for the queue and the buffer being read into). That bound counts against the heap limit for the whole call, before the child starts. Output over the limit ends the call at once and stops the tree, so a child that writes far more than 16 MiB costs the call no more memory than the limit and the bound.
   - **Limits of the tree.** On Linux a program that needs `setsid` or `setpgid` in the child or a descendant fails there: a daemon that detaches, the `setsid` utility, job control of an interactive shell, and `start_new_session` or `process_group` of Python's `subprocess`; denying them is the price of a tree that cannot be left without a cgroup, which the runtime cannot rely on being delegated to it. Without seccomp (a weaker sandbox, SB-5) the filter is missing and a process that leaves the group outlives the call. On macOS a descendant that leaves the group and whose parent has already ended (a double fork into a new session) belongs to launchd and is found only by the marker of the profile. A program runs under its profile whenever its sandbox applies; without a sandbox (the tests of the runtime, which call it directly) such a descendant is not found and can outlive the call. The marker relies on `sandbox_check` of libsystem_sandbox, which has no public header; a test checks its answers on macOS (`tree.rs`), and a check that fails finds nothing, so the stop falls back to the group and the parents; a process that ends and is reaped between the search and the signal could in principle have its number reused. A process that outlives the call keeps a reader thread blocked on a pipe it holds until it closes it, but the call itself returns at the deadline. On Unix, an interrupt from the terminal (Ctrl-C) reaches only `unio`, not a child of a program in its own group: that child runs on until it ends by itself (the workers of the tools are stopped, 9.7). Seccomp, Landlock, and Seatbelt still restrict a process that escaped the tree.
6. **What the sandbox does not do** (SB-9).
   - It does not protect against vulnerabilities of the kernel, against side channels, or against misuse of what was granted: a program allowed to write `$HOME/**` can destroy those files.
   - Writing is exact at the level of the operating system: neither a program nor its children can write any file there, and the writer process, which holds the directory-level right that a scope of one file needs, permits only that file and the temporary files of its own operations. A child cannot write even the files the program may write; it returns data to the program, which writes them. A write scope whose directory does not exist when the program starts cannot be written at all, since the rule of the writer's sandbox needs the directory. On Windows a process of an AppContainer can always write the folder of its own profile (`%LOCALAPPDATA%\Packages\<name>\AC`, where its temporary directory points), so a child can write files there; the folder is private to the run and deleted with the profile when the program ends. Reading on Windows is wider than the scopes by what every application package may read: the system directories and `Program Files`, and a child can run every program there.
   - On Windows the grants are entries in the DACLs of the user's files while a program runs. A run that is ended from outside (killed, or ended by a limit, code 102) leaves its entries and its profile behind; they name a SID that no token has again, so they grant nothing, but they stay in the DACLs until removed. A file whose DACL the user may not change (one owned by another user) cannot be granted: the program starts, warns, and is denied that file. Granting a large tree writes the DACL of every entry in it, twice per run, which takes time in proportion to its size.
   - On Windows the thread of the program can return to the token of the process with `RevertToSelf`, which no Unio program can call: only a defect that runs foreign native code on that thread could, as such a defect could on Linux use the unrestricted main thread of `unio run` (below). The children and the workers are processes of their AppContainers, which nothing in them can leave.
   - Starting programs is exact at the level of the operating system: a child may start with `execve` only the listed programs, the interpreters of listed scripts, and on Linux the dynamic loader (item 5). What it can run is wider, as item 5 states: on Linux any ELF program it can read, through the loader, and everywhere any script it can read, through a listed interpreter. Reading is still coarser than the checks of the runtime in these ways. A read scope whose root does not exist at start grants nothing there. Metadata (`stat`) is not restricted. With any `process` permission the library directories are readable, by the program too; they hold some programs and scripts besides libraries (for example under `/usr/lib`), and on Linux a child can run such a program, or a listed one, through the dynamic loader (`ld-linux.so /usr/lib/.../program`), which loads it without `execve`; it cannot run a program it cannot read, so `/usr/bin` and the other directories of programs stay closed. A listed interpreter (`sh`, `python3`) runs any script it can read, as a listed program does with its input. A script whose `env` line finds its interpreter in another way (an option of `env` that takes a value, such as `-u NAME` or `-C DIR`, before the name, or an assignment to `PATH`) and on macOS a program that starts another one by itself (as `/usr/bin/python3` does with the developer tools) needs the other program listed too.
   - The writer trusts the scopes it receives from the runtime of the same executable before the program runs; it does not read the manifest or the policy again. It does not stop another process of the same user that can write the directories of the scopes: such a process can replace a temporary file or a target between two requests, which never leads a write outside the scopes but can change what a target holds.
   - On Linux the rules apply to the threads that run the program and to its children; the idle main thread of `unio run` is not restricted.
   - For code written by AI, use a minimal manifest, a policy with limits, and a separate user, container, or virtual machine for untrusted code.
7. **Workers of the tools** (SB-10, SB-11, SB-12, SB-14, SB-15). The tools read projects that may be hostile, so their work runs in a worker process, and the tool itself only handles its arguments, starts the worker, and shows what it returns.
   - **Which commands.** `unio check`, `fmt`, `build`, `outline`, `symbol`, `parse --ast`, the compile steps of `unio test` and `unio run`, every analysis of the language server `unio lsp` (below), and the download and unpack steps of the package commands `unio add`, `remove`, `update`, and `install` (below). `unio explain` reads no source and runs in the tool.
   - **Start.** The worker is the same executable, started with a hidden first argument, an empty environment except the variables that select the language of messages (`UNIO_LANG`, `LANG`, `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`; on Windows also `SystemRoot`, without which system libraries do not load, and `LOCALAPPDATA`, `TEMP`, and `TMP`, which the system sets to the folders of the worker's own AppContainer profile), and its configuration on standard input: its scopes, its limits, the directory of the standard library the tool found (so `UNIO_STDLIB` need not reach it), and its temporary directory. Its standard output and error are pipes that the tool relays. On Linux it ends with the tool (a parent-death signal).
   - **Scopes.** It may read the package of every given file and the standard library. The package is the nearest directory above the file, by its written path, that holds `unio.toml`; a link at the end of the path is not followed, so a source that is a link to a file elsewhere stays in the package it is listed in, and reading it is refused by the system. Without a manifest the directory of the file is its package, as in the compiler; `unio symbol` reads the package around the working directory. It may also read the cache entries of the dependencies that the `unio.lock` of each such package locks (T-14, [packages.md](packages.md)), each as a tree, and no other part of the cache; the tool gives the worker the directory of the cache, since the worker has no environment to find it in. It may read and write only its own temporary directory (mode 0700 below the temporary directory of the system, removed afterwards). No tool writes `target/` yet: a later build cache there becomes a write scope only after the tool checks that it is a directory and not a link.
   - **Rules.** Linux: `no_new_privs`; Landlock with reading of the scopes, reading and writing of the temporary directory, no execution, no TCP, and signals only inside the sandbox (ABI 6); seccomp without sockets, `execve`, `fork` and `vfork`, with `clone` only for threads (`CLONE_THREAD`), and without the calls of item 4; no core files. The rules apply on the main thread before anything of the project is read, so they hold for every thread. macOS: a deny-by-default Seatbelt profile with reading of the scopes, reading and writing of the temporary directory, listing of the working directory (which `getcwd` needs), no process and no network. Windows: the tool creates the worker in an AppContainer of its own (item 4) with grants on exactly its scopes: reading the packages and the standard library, reading and writing its temporary directory and, for the unpack worker, the staging directory of its cache entry, writing in place the files `unio fmt` was given, executing `unio` itself, and entering the working directory; it has no capability, so no network. The worker checks that it runs in an AppContainer and fails closed (code 103) when it does not, and joins a Job Object with the memory and CPU limits and one active process, so it cannot start another. The grants are removed when the worker ends.
   - **Limits.** Memory and time come from the `[compile]` table of the policy (`--policy` or `UNIO_POLICY`, SB-3a, RFC 0006): `compile.memory_bytes`, `compile.wall_seconds`, and `compile.cpu_seconds`, or are 2 GiB, 10 minutes, and no CPU limit of their own. They are not the limits of the program: `[limits]` never reaches a worker, and `[compile]` never reaches a program. They hold alike for every worker: `unio check`, `fmt`, `outline`, `symbol`, `parse --ast`, the compile steps of `unio run` and `unio test`, and both steps of `unio build`, the compile step and the link step, each worker separately (each of the two workers of `build` has the whole `compile.wall_seconds`). The memory limit is the address space on Linux (`RLIMIT_AS`, also the file-size limit of the worker), the footprint the tool reads every few milliseconds on macOS, and the memory limit of the Job Object on Windows; the tool keeps the wall time. A worker over a limit is stopped, and the tool prints `unio: error: the worker of the tool was stopped: ...` and ends with code 102; it never hangs. A worker runs in a process tree of its own, as a child of a program does (9.5): a process group that no descendant can leave on Linux; on macOS the group, the descendants found through their parents, and, for the link step, every process whose Seatbelt profile carries the marker the tool gave it; on Windows a Job Object the worker joins while it is still suspended. When the worker ends, at a limit or not, what is left of its tree is stopped, so a linker and the processes it started do not outlive `unio build`; a tree that cannot be set up stops the tool with code 103. SIGINT, SIGTERM, SIGHUP, and SIGQUIT of the tool, while they have their default action, first send SIGKILL to the process groups of its workers. The CPU limit is `RLIMIT_CPU` on Linux and macOS (user and system time) and the user time of the Job Object on Windows. The tool reports the end at that limit as a limit too, with code 102, by the processor time the system accounted to the worker when the tool reaped it (`wait4` on Linux and macOS, `GetProcessTimes` on Windows), never by wall time, since a worker spends processor time on several threads: the worker ended with SIGKILL (Linux) or SIGXCPU (macOS), or with a failure on Windows, and its processor time reached the limit. Any other end, such as SIGKILL from another process before the limit, is an abnormal end with code 101, and the message names the signal or status and the processor time used. `unio.toml` never sets these limits.
   - **The least memory.** The tool never raises a limit of the operator. A `compile.memory_bytes` below 192 MiB (201,326,592 bytes, `MINIMUM_COMPILE_MEMORY` in `compiler/unio/src/worker.rs`) cannot be honoured, since a worker needs about that much to start and compile an empty program, so the tool refuses it with code 103 and `unio: error: compile.memory_bytes = N of the policy is below the minimum of 201326592 bytes (192 MiB) ...` before it starts a worker or compiles anything. The minimum comes from measurements on Linux x86-64 (kernel 6.18, GNU ld 2.42, GCC 13.3): the smallest address space with which the worker of each command finished, found by bisection to 1 MiB and varying by a few MiB between runs, which includes the 64 MiB stack of the thread of the front end. For an empty program a release build of the tool needed 109 MiB for `check`, `run`, `test`, and `symbol`, 78 MiB for `fmt`, `outline`, and `parse --ast`, and 127 MiB for `build` with its link step; a debug build needed 121 MiB, 90 MiB, and 139 MiB for the compile step of `build`. For the largest source of the repository, `tools/grammar.unio` (38 KB), a release build needed 153 MiB for `check`, 154 MiB for `test`, 123 MiB for `fmt`, 115 MiB for `outline` and `parse --ast`, about 165 MiB for `build`, and 175 MiB for `build --release`; a debug build needed 164 MiB for `check` and `test` and 173 MiB for the compile step of `build`. 192 MiB leaves about half again over the release numbers of an empty program; 256 MiB is the recommended value, which also holds the largest source with a margin. The numbers of macOS (the footprint, which does not count the reserved stack) and Windows (the memory of the Job Object) are pending: `a_compile_memory_below_the_minimum_is_refused_before_compiling` in `compiler/unio/tests/workers.rs` compiles and runs the empty program at the minimum on every system in CI. The link step runs the system linker, whose need depends on the toolchain and the size of `libunio.a`: about 130 MiB with the library of a release build and about 530 MiB with the 290 MB library of a debug build, which carries debug information; a linker over the limit ends the build with 102, or with code 1 and the message of the linker when that message does not show the exhaustion.
   - **Failing closed.** Without Landlock ABI 3 or seccomp, or when the rules cannot be applied, the worker stops with code 103 unless the operator passes `--allow-weaker-sandbox` (every command that reads sources takes it) or sets `allow_weaker = true` (SB-5). On Windows nothing is missing; a worker that is not in an AppContainer stops with 103 whatever the operator allows, and an AppContainer that cannot be set up stops the tool with 103. SB-14 keeps the tools from executing code of the package, but they still process untrusted data (sources, imports, paths, deeply nested constructs), and a defect of the compiler could lead outside the project, hang, or exhaust memory; that boundary is what SB-10 protects. Only the operator can allow the weaker sandbox, by the flag or by the external policy (a policy for trusted working directories saves passing the flag each time); a project cannot allow it through `unio.toml`. In the weaker mode the restrictions that exist still apply. CI runs every system with its full sandbox.
   - **`unio fmt`** writes through the writer process of item 2, which the worker starts before its own rules apply and which may write exactly the given files, each as an entry of its directory: a given file that is a link is replaced by the formatted file and never followed, and its target outside the package cannot even be read. The worker itself has no right to write any source.
   - **`unio build`** has three steps. The worker checks the program and writes the object file into its temporary directory. The link step is a second worker that applies its own rules and runs the C compiler (`cc`, or `CC` of the tool): it may execute exactly the compiler and the programs it names for `collect2` and `ld`, resolved as for the children of a program (item 5, with interpreters and the dynamic loader), read the library directories, `/etc/ld.so.cache`, `/etc/localtime`, the directory of the compiler's own programs (for plugins such as `liblto_plugin.so`, read only), `libunio.a`, and the temporary directory, write only that directory, and open no socket; its environment is `PATH` and `TMPDIR`. On macOS the tool runs `clang` and its linker directly, not the `xcrun` shims of `/usr/bin`, and the link step's Seatbelt profile lets it start processes that execute exactly those programs, read and map the tree of the developer tools (`Xcode.app/Contents/Developer` or the command line tools) and the system libraries, and read the SDK; on Windows it runs `link.exe` in its AppContainer, which `link.exe` inherits, with the variables that locate the libraries of Visual Studio and the Windows SDK (`LIB`, `LIBPATH`, `PATH`); `link.exe` and those libraries are under `Program Files`, which every application package may read, and it may read the object and `unio.lib` and write only the temporary directory (a toolchain installed elsewhere would need a grant that the link step does not give). The tool then copies the executable to OUT, by a temporary file and a rename: OUT is chosen by the operator, never by the project, so it needs no write scope. The worker that reads the project starts no process, as SB-11 asks; the linker is a program of the system that reads only the object made by the compiler and the runtime, and it is confined the same way. What remains: a defect of the linker that a crafted object could reach runs with those rules.
   - **`unio test` and `unio run`.** The worker loads and checks the program and returns its diagnostics and every file it was loaded from (its modules, the modules of the standard library, and the manifests of its packages). The tool keeps them in memory; the thread of each program applies the sandbox of SB-1 first and then loads the program again from memory and runs it. The project is therefore never parsed outside a sandbox. The tool still reads the manifests and the policy itself, as before, to set up the sandboxes of the programs.
   - **The language server (SB-13).** `unio lsp` speaks LSP on its standard streams and holds the open documents; it reads no source itself. Each analysis (the diagnostics of a document when it is opened, changed, or saved; hover, go to definition, completion, type hints, formatting, and rename) runs in a worker of its own with the scopes and the `[compile]` limits above, for the package of the document: the worker may read that package and the standard library, writes only its temporary directory, and has no network and no processes. The request and the unsaved texts of the open documents of that package reach the worker on its standard input, after its configuration (whose line `input N` announces N bytes); inside, those texts take the place of their files for the loader (`unio::vfs::overlay`), so an unsaved buffer needs no file and no wider read scope, and the buffers of other packages are not sent. The worker writes the result of LSP as JSON on its standard output, and the server parses it before passing it on. A worker over a limit is stopped as for every tool; the server then publishes a diagnostic at the start of the document in place of the analysis, or answers a request with an error. Each analysis waits for its worker on a thread of its own, so the server answers other messages meanwhile; the diagnostics of one document run one at a time, and once more for the last change when a run ends. The policy and `--allow-weaker-sandbox` are those given to `unio lsp`, and a policy that cannot be honoured stops the server at its start with code 103. `unio/explain`, the text behind the link of a diagnostic code, is answered by the server itself, like `unio explain`, since it reads no source. Checked by `compiler/unio/tests/lsp.rs`: in the worker of an analysis the probes past the compiler are denied (a file outside the package, a source that is a link out of it, the home directory, writes, processes, the network), nothing of the secret reaches the editor, and an analysis over the time or the memory limit gives a diagnostic while the server keeps answering.
   - **Package operations (SB-12).** The package commands split their work between two kinds of worker, started like the others, with the `[compile]` limits of the policy, and failing closed in the same way; the tool reads only the manifest and the lock of the root package and the packages configuration of the operator, and writes `unio.toml`, `unio.lock`, and the finished cache entries ([packages.md](packages.md)).
     - The *download worker* fetches one file of a configured registry. The tool checks that the host of the URL is the host of a registry in the configuration, resolves it, and opens the TCP connection itself; the worker inherits that connection and may open none: on Linux its seccomp filter denies `socket` and `connect` and Landlock denies TCP connections, on macOS its Seatbelt profile denies the network, on Windows its AppContainer has no capability and gets the socket as an inherited handle, so it cannot reach any other host or port, even on the same machine. It reads nothing, writes only its temporary directory (the download area), speaks HTTP/1.1 with `Connection: close`, follows no redirect, and limits the response (the archive limit, 8 MiB for an index, 1 MiB for a signature, 4 MiB for the endorsements and 1 MiB for the revocation list of a registry). The trust files and signature envelopes it downloads are passed on as bytes. For a registry index it receives on its standard input the trust bundle of the registry (the operator's anchor and the registry's trust files as downloaded, with the floor of the revocation list), the envelope of the index, and the floor of its sequence; it verifies the trust files, the ML-DSA-65 signature of the index, and its sequence *before* it parses the index (T-8a; [packages.md](packages.md) 7.3), and gives the tool its normalized lines, the signer, and the sequences, so the tool never parses data from the network.
     - The *unpack worker* has no network and starts no process. For an archive it may read only that file (the signature and the trust files come on its standard input) and write only the staging directory of the one cache entry being made (`<cache>/staging/...`, renamed into `packages/<content hash>` by the tool once everything is checked and confirmed). It checks the SHA-384 of the archive against the manifest, the index, or the lock before it reads the archive; for a registry package it then verifies, with the trust bundle and the envelope it receives on its standard input, the trust files and the ML-DSA-65 signature of the archive for exactly that package and version, and refuses the package on any failure, with no exception (T-8, T-8a; [packages.md](packages.md) 7.3); only then does it read the entries, refusing absolute paths, `..`, links, devices, FIFOs, extended headers, duplicate and case-colliding names, non-portable names, and every limit of size, count, and depth before anything is written. For a path dependency it may read only that directory and copies it by the same rules; for `unio install` it reads an existing cache entry, writes nothing, and checks its content hash. It parses the modules of the package to find the `unsafe module` marker, which runs none of them (SB-14), and reports the manifest, the marked modules, and the content hash as data.
     - SB-14: nothing of a package is executed during installation or a build: there are no build scripts, and the only processes are the workers, which start none.
     - Checked by `compiler/unio/tests/packages.rs`: every hostile archive case of SB-15 is refused by the unpack worker with nothing written to the cache; in the unpack worker the probes of a write into the cache outside its staging directory and into the project, of reads outside the package, and of exec are denied; a hash mismatch is refused before unpacking; the probe of another port on 127.0.0.1 is denied in the download worker while the download from the configured registry succeeds, and an archive URL on an unconfigured host is refused before any connection; nothing of a package runs during `add`, `install`, `check`, or `test`; tampered, untrusted, revoked, rolled back, or unsigned registry files are refused before anything of an archive is unpacked (`tampered_and_untrusted_registry_files_are_refused_before_unpacking` and the other tests of signed registries).
   - **Probes.** With `UNIO_WORKER_PROBE` the worker tries operations after its rules apply, with plain system calls past the compiler, and reports each on standard error as `unio worker probe: OPERATION: allowed` or `denied (ERROR)`: `read=`, `list=`, `write=`, `mkdir=`, `remove=`, `write-temp`, `exec=`, `fork`, `connect=HOST:PORT`, `udp`, `env`, `pid`, `sleep=`, `spin`, `alloc=BYTES`. The SB-15 suite (`compiler/unio/tests/workers.rs`) uses them to show that the system, not the compiler, denies each attempt. The variable is read by the tool, not by the project.
   - **Limits of the workers.** Metadata is not restricted on Linux and macOS, so a worker can learn whether a path exists and its size anywhere; on macOS it can list the working directory. On Windows a worker can read what every application package may read, and write the folder of its own profile, which is deleted with it. `unio doc` reads and checks the package in such a worker with the scopes of `unio check` and returns the pages, which the tool writes ([tools.md](tools.md) section 9). On macOS the use of the inherited connection under the Seatbelt profile is checked in CI only.

## 10. Trials of the file guarantees

This section says how the guarantees of S-9 are trialled against crashes (S-9b) and what is not trialled. The trials are `compiler/unio/tests/power_loss.rs`, part of `cargo test` on Linux, macOS, and Windows.

1. **The trace.** With the environment variable `UNIO_TEST_FILE_TRACE=1`, the runtime writes one line to standard error for each operation that decides what storage may keep after power loss, once it has succeeded: the creation of a temporary file, each write into it, each sync of a file or directory with the call that did it (`fsync`, `fullfsync` for `fcntl(F_FULLFSYNC)`, `flush` for `FlushFileBuffers`), each rename, removal, and new directory (`compiler/unio-runtime/src/file_trace.rs`). The program records what it does itself; the writer process (9.2) records what it does for the program, on the standard error it inherits, before it replies, so the lines of both processes are in the order of the operations. The program passes the variable to the writer only when it is set. Like `UNIO_TEST_HEAP_FREE`, the hook only observes: it opens nothing, grants nothing, and changes no operation. A second hook, `UNIO_TEST_FAIL_PARENT_SYNC`, makes the sync of the parent after `create_directory` fail: with `once` only that sync, with `always` also each later attempt (`parent_sync_fails` in `compiler/unio-runtime/src/externs/durability.rs`); it is passed to the writer in the same way and can only make an operation fail.
2. **Simulated power loss.** A test program replaces a file several times with and without `durable`, writes it in parts through `open_atomic`, releases one atomic file without a commit, creates a new file, and writes into a directory it has just created. Its trace is replayed on a model file system at every crash point, after every prefix of the operations, and every state the model allows storage to keep is checked, in the manner of ALICE and CrashMonkey.
   - The model keeps the data of a file only up to its last sync by a call that reaches storage on the platform: `fsync` on Linux, `fcntl(F_FULLFSYNC)` on macOS (a plain `fsync` does not count there), `FlushFileBuffers` on Windows. Data written after that may be lost from any write on; the weak model may also keep the new length with zeros.
   - A directory entry (a new file, a rename, a removal, a new directory) is kept for certain once its directory has been synced after it by such a call, or on Windows once a rename with `MOVEFILE_WRITE_THROUGH` at or after it has returned. Entries that are not certain are kept in two models: *ordered*, a prefix in the order of the operations, as the journals of ext4, XFS, Btrfs, APFS, and NTFS keep metadata; and *weak*, any subset, which is all POSIX promises. A rename is atomic in both.
   - Checked in every state: the target holds its old content or the complete content of one commit that reached its rename (guarantees 1 and 2); once a commit with `durable = true` has returned, the target holds that content or a later one (guarantee 3); the directory holds no name but the targets, the files that were there, the new directories, and the temporary files `.<name>.unio-tmp-*` that S-9 allows after a crash; the files that were there keep their content.
   - The trace replayed without a crash must give the file system the run left, so that an operation that changes it cannot go unrecorded, and each commit in the trace must carry the data the program wrote.
   - The harness is first shown to catch broken protocols in the same trace: without the data sync, with the rename before the data sync, without the directory sync of a durable commit, with a plain `fsync` on macOS, without the sync of a new directory's parent (caught by the weak model), and on the Windows code path without `FlushFileBuffers` or without `MOVEFILE_WRITE_THROUGH`; a hand-written write in place is caught as well.
   - The trace is that of a real run on Linux or macOS. Windows has no writer process yet, and its code path in `externs/files.rs` is checked on the trace changed into the calls that path makes, under two stated assumptions: `FlushFileBuffers` reaches storage, and NTFS keeps its log in order, so that a write-through rename returns once it and every entry before it are on storage.
3. **Killed processes.** A program replaces a file in a loop with contents of up to 300 KB that can be told apart and checked for completeness, with and without `durable`. It is killed with SIGKILL (on Windows `TerminateProcess`) at random points after its first commit; on Linux the writer process alone is also killed, after which the next write fails with an error. Each time the target holds one complete content, and nothing but temporary files of it is beside it. The seed is printed, and `UNIO_TRIAL_SEED` repeats a run.
4. **What the trials found and what changed.**
   - A new directory was not synced into its parent: a durable write into a directory just made by `create_directory` could be lost together with that directory after power loss on a file system that does not keep metadata in order (the weak model), although `write_text` had returned. `create_directory` now syncs the directory that holds the new one, in the writer and without it; Windows has no sync of a directory, and NTFS journals the entry.
   - When that sync failed, it was ignored, so a later durable write into the new directory returned although the directory itself might not survive power loss (found by an audit; the trial with `UNIO_TEST_FAIL_PARENT_SYNC=once` failed in the weak model). `create_directory` still succeeds, since the directory exists, but the writer, and the runtime where it creates directories itself, remembers each new directory whose parent was not synced. A durable sync of a directory, the last step of a durable commit, first syncs again the parent of every such directory on its path, up to the directories that existed before the run, deepest first; if one still fails, the sync fails and `commit` reports kind `DurabilityUnconfirmed` (S-9c), with the target already replaced. A durable commit therefore confirms the whole chain of new directories it depends on. Past 1,024 such directories in one run no durable commit is confirmed. The trial runs with the hook: with `once` every crash state of both models keeps the guarantees, and with `always` the commit reports `DurabilityUnconfirmed`. A directory renamed with `rename` is not synced, as `rename` makes no durability promise.
   - On macOS, when `fcntl(F_FULLFSYNC)` of a directory failed, the directory was synced with a plain `fsync` and the commit counted as durable, although a plain `fsync` does not reach storage there. The plain `fsync` is still done, since it orders the rename, but the error is now reported, so `commit` fails with kind `DurabilityUnconfirmed` (S-9c).
   - The data sync was checked in the standard library of the pinned toolchain: on Apple platforms `File::sync_all` is `fcntl(F_FULLFSYNC)` with no fallback to `fsync`; on Windows it is `FlushFileBuffers`.
5. **Recorded block writes (a real power cut).** `compiler/unio/tests/power_cut.rs` records the blocks that the kernel's ext4 and XFS write while a Unio program, run with `unio run` and so with the writer process, replaces files with `write_text` and `open_atomic`, with and without `durable`, in parts, leaves an atomic file without a commit, and writes into a directory it has just created. A file system with the old contents is made on an image and put behind a recorder: the device-mapper target `log-writes` (`UNIO_POWER_CUT=dm-log-writes`, as xfstests uses it), or, where the kernel has no device mapper, a loop device over a file served by a FUSE server in the test (`UNIO_POWER_CUT=fuse`), which records each write and each fsync the loop device passes on (a flush; a FUA write arrives as a write and a flush) before it answers. Both write the on-disk log format of `drivers/md/dm-log-writes.c`, and the harness adds a mark each time the program reports that a durable commit has returned. The replay program is the reader of the test, which follows `src/log-writes/log-writes.c` of xfstests (the `replay-log` tool is not used): the log is applied to a copy of the base image one entry at a time, and after every entry, so at every flush and FUA and at every point between them, a copy is mounted, which runs the journal recovery, and checked: each target holds its old content or the complete content of one commit, never a torn or empty one; after the mark of a durable commit, that content or a later one; only the targets, the files that were there (unchanged), the new directory, and temporary files `.<name>.unio-tmp-*` are in the directory. The whole log replayed must give the device the run left, so no write is unrecorded. As a negative control the harness then writes one file in place, in two synced parts, and some replayed state must show it torn. The trial needs root and is `#[ignore]`d; the CI job `power-cut` (Linux x86-64, ubuntu-24.04) installs `linux-modules-extra`, loads `dm-log-writes`, and runs it with both recorders on ext4 and XFS. What it proves: on those file systems and that kernel, every state that a prefix of the recorded writes leaves keeps guarantees 1–3 of S-9. What it does not: a prefix is one ordering; storage may also keep any subset of the writes after the last flush, which the model of item 2 covers for metadata but this trial does not, and storage that acknowledges writes it has not stored is beyond any software check (S-9a). Powering off virtual machines (S-9b) is not done: hosted runners give no nested virtualization for a guest that could be cut off, on any of the four platforms.
6. **What is not trialled.** The model states the guarantees of the file systems as their documentation gives them; it is not a power cut. Powering off virtual machines and a power cut of macOS and Windows are not run (item 5); a cut of real hardware is not run either; the trace records system calls, not the blocks a file system writes, so a file system that breaks its own promises is not found. The rules for macOS and Windows are assumptions, and real traces come from Linux and macOS only. A temporary file that a crash leaves is not removed later; S-9 allows it. Storage that acknowledges writes it has not stored is beyond any software check (S-9a).

## 11. Layers of the runtime (S-12)

1. **The layers.** The runtime is divided as the library is (S-11, S-12; `compiler/unio-runtime/src/layers.rs`):
   - **core**: the entry of a program and its exit code (6.1, C-15), faults and their traces (section 4), checked arithmetic (2.1), and the externals of `stdlib/core` (`fault.rs`, `externs/core.rs`, `externs/math.rs`). It makes no call to the operating system.
   - **alloc**: the heap with its limit and reference counting, and the reserve for `release` (section 3; `heap.rs`, `reserve.rs`, `value.rs`), and the externals of `stdlib/alloc` (`externs/alloc.rs`, `unicode.rs`, `float_text.rs`).
   - **std**: standard output and error, files, processes, clocks, entropy, the sandbox and the watcher of the time limits (`externs/system.rs`, `files.rs`, `durability.rs`, `process.rs`, `clock.rs`, `sandbox/`, `deadline.rs`, `file_trace.rs`).
2. **The hooks.** The core runtime reaches the other layers only through `Hooks`, a set of plain functions that a profile installs before the first program (`layers::install`): from alloc, opening the reserve for `release` when a fault starts, asking whether it is open, and closing it when `expect_fault` receives the fault (C-17); from std, writing standard output, writing standard error (the diagnostics of faults and of exhaustion), and ending the process (C-18). Each hook is a function pointer, so a call allocates nothing, also on the path of exhaustion. In 0.1 the application profile is the only one; its hooks (`layers::application`) are those of the runtime and are in place when no profile installed others. A system profile (concept section 8.1) provides its own.
3. **The check.** Two tests prove that the core runtime makes no system call:
   - At run time, on Linux on x86-64 and AArch64 (`compiler/unio/tests/layers.rs`): programs that pass `unio check --profile=core` are built with `unio build` and run with the test hook `UNIO_TEST_CORE_SECCOMP=1`, with which the executable installs on all its threads, after its start and right before `main`, a seccomp filter that ends the process with SIGSYS at any system call except `write` and `writev` to descriptors 1 and 2, the memory calls of the allocator (`brk`, `mmap`, `munmap`, `mremap`, `madvise`, `mprotect`), `futex` (the thread of the start waits for `main`), `rt_sigprocmask` and `sigaltstack` (the end of a thread), and `exit` and `exit_group`. A core program runs to its exit code, and a faulting one writes its fault and trace and ends with 101; a program that asks the file system is ended by the filter, which shows that the filter is in force. Like the other test hooks, this one only takes authority away.
   - In the sources, on every platform (`the_core_layer_reaches_the_system_only_through_hooks` in `compiler/unio-runtime/tests/bindings.rs`): every external of `stdlib/core` is bound in `externs/core.rs` or `externs/math.rs` and only they are, and these files and `fault.rs` name no interface of the system (`std::fs`, `std::process`, `std::env`, standard streams, `extern "C"`, ...) and no module of another layer.
   The run-time test is the proof: it observes the property itself, including what the Rust standard library and the C library do underneath, which a reading of the sources cannot see; the source check keeps the layering on the systems where seccomp does not exist. The interpreter of `unio run` and the start of an executable (the sandbox, the image, the heap limit) belong to the std layer and make system calls before `main`.

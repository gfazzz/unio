# Dynamic semantics and the runtime of Unio 0.1

Version 0.1-draft. Russian localization: [ru/runtime.md](ru/runtime.md). Basis: concept sections 2–4, requirements L-10 to L-21, C-13 to C-20, S-9 to S-12, SB-1, T-4, T-5a; [semantics.md](semantics.md) for what is checked before a program runs. This document is the reference for the interpreter of sprint S5 and for the native runtime of sprint S6.

A program that reaches the runtime has passed `unio check`: names resolve, types agree, errors are handled, resources stay in their blocks. The runtime therefore checks only what cannot be known before execution: faults, exhaustion, and the outside world.

## 1. Evaluation

1. Evaluation is strict and goes from left to right: the operands of an operator, the arguments of a call, the fields of a struct construction, the items of a list or map literal, and the parts of a text with interpolations are evaluated in the order they are written.
2. `and` and `or` evaluate their right operand only when it decides the result; `a or b` on an `Option` evaluates `b` only for `none`. `x if c else y` evaluates `c` and then one branch.
3. A default value of a parameter is evaluated at each call that omits the argument, after the arguments that precede it, and can use the parameters before it.
4. A `for` loop evaluates its collection once, before the first iteration; changing the source variable inside the loop does not change the iteration, because the loop holds the value it started with.
5. A comprehension `[e for x in c if g]` evaluates `c` once, then `g` and `e` for each item in order.

## 2. Values

1. `Int` is a 64-bit two's-complement integer; overflow of `+`, `-`, `*`, `**`, division by zero, and `%` by zero are faults (L-17). `/` truncates toward zero, and `%` has the sign of the left operand.
2. `Float` is IEEE 754 binary64 with round-to-nearest-even; no operation on `Float` faults.
3. `Text` is an immutable sequence of Unicode scalar values stored as UTF-8 with an index of character positions, so that `length`, `slice`, and `char_at` take constant time.
4. Structs, enums, tuples, lists, maps, sets, `Bytes`, and texts are values (L-11a). A value is shared between names until it is changed; changing a shared value first copies the level that changes, and changing an unshared value happens in place (L-11b). Map and set iterate in the order keys were first inserted, and hashing does not depend on the run, so the output of a program is the same on every run.
5. Function values capture the values of the names they use when they are created (L-11a).
6. A resource is not a value: it has identity, is never copied, and its `release` runs exactly once (section 5).

## 3. Memory

1. Because values never share mutable state and closures capture copies, a value can never reach itself: there are no reference cycles. The interpreter of S5 therefore manages memory by reference counting, which frees each value when its last name goes away and also tells the copy-on-write rule when a value is unshared.
2. Requirement C-13 asks for a precise, tracing, non-moving collector. Reference counting is precise and non-moving, has no collection pauses at all, and needs no tracing because cycles cannot occur. Whether the native runtime of S6 keeps reference counting or adds tracing is decided by the measurements of section 7.1 of the requirements; replacing C-13 needs an RFC.
3. The runtime counts the memory it holds. When it exceeds the heap limit of the policy (`limits.heap_bytes`, SB-3a) or the memory the system grants, the program ends with code 102 (C-18). Recursion deeper than the stack limit also ends with code 102.
4. **Budget before allocation.** Where the program decides the size of an allocation, the runtime checks the heap limit before it allocates and reserves the memory with fallible allocation (`try_reserve`), so that an allocation the system refuses is the same exhaustion with code 102, not an abort: the buffer of `FileReader.read_bytes` (`max_bytes`), `read_text` and `read_bytes` (the size of the file), the output that `process.run` captures, and `Text.repeat`. Other values grow step by step and are checked after each step. The message of code 102 is prepared in advance and written without allocating.
5. **What cannot be guaranteed.** The runtime sees the allocations it makes and the refusals of the allocator. It cannot see memory the system promised but cannot deliver: with overcommit (the default on Linux) an allocation can succeed and the process can then be ended by the system's out-of-memory killer, without code 102 and its diagnostic; a small allocation that fails inside the Rust standard library still aborts the process. The counted sizes are estimates of capacity (`compiler/unio-runtime/src/heap.rs`), not exact figures of the allocator. A heap limit in the policy is therefore the reliable way to get code 102; a limit of the operating system (`ulimit -v`, a cgroup) stops the process from outside.

## 4. Errors and faults

1. A function with `fails with` ends either with its result or with one of its errors. `try` passes an error on unchanged; `on E as e` receives it; `fail e` ends the function with `e`. An error is a value and never unwinds past a function that does not list it, which the checker guarantees.
2. A fault (L-17) stops the program at its point. The runtime records a trace of function names, files, and lines (C-14), unwinds the stack, calls `release` of every open `using` block in reverse order (C-17), writes the diagnostic and the trace to standard error, and ends with code 101. A fault inside `release` during this unwinding is reported and the remaining resources are still released.
3. A fault cannot be received by `on`. `expect_fault(action)` in a `test` block runs `action` and succeeds only if it ends with a fault; the resources opened inside `action` are released before `expect_fault` returns.
4. `assert c` and `assert_fail(m)` are faults with the text of the condition or the message.

## 5. Resources

1. `using r = e:` evaluates `e`, binds `r`, and runs the block. When the block ends, normally, through `return`, `break`, `continue`, an error, or a fault, `release` of `r` runs; several `using` blocks release in reverse order of opening.
2. `release` cannot fail: its signature has no `fails with`, and an error that happens inside it is the resource's own business (for example, `AtomicFile` ignores errors of removing a temporary file).
3. On emergency termination (code 102) and abnormal termination, `release` does not run (C-18, C-19).

## 6. Programs and tests

1. A program starts at `public function main()` of the module given to `unio run`. Without a result, the exit code is 0; with an `Int` result, it is that value, which must be 0–100, otherwise it is a fault (C-15).
2. `unio test` runs every `test` block of the given modules, each in a fresh state; the order of the blocks does not matter, because there is no global mutable state. The result of each test is passed, failed with the fault that ended it, or failed with the diagnostics that keep it from compiling (T-5a), in text or JSON with name, status, time, and output (T-4).
3. Top-level constants are evaluated once, in dependency order, before `main` or before the first test that needs them; a constant whose evaluation faults ends the program with that fault.

## 7. External functions

1. The standard library declares 83 external functions, all in `unsafe module` files (S-7, S-10). Each is bound by its full name, such as `std.files.system_rename` or the method `Text.slice`, to a function of the runtime. The documentation comment of the declaration is its specification.
2. A test of the runtime checks that every external declaration has a binding and every binding has a declaration, so that the library and the runtime cannot drift apart.
3. The groups and the layer each needs:

| Group | Externals | Layer |
|---|---|---|
| Faults, identity, checked arithmetic, `Float` classification and total order | `assert_fail`, `expect_fault`, `is_same`, `Int.checked_*`, `Int.to_float`, `Float.is_nan`, `Float.is_finite`, `total_order_key` | core |
| Text, bytes, lists, maps, sets, numbers as text, code points | 40 methods and constructors in `alloc/builtin/*`, and 3 functions of `std.text`, among them `from_code_point` | alloc |
| JSON conversions generated for each type | `std.json.to_value`, `std.json.from_value` (implemented by the compiler, not by hand) | alloc |
| Standard output, arguments, environment, paths | `write_output`, `write_error`, `std.args.list`, `std.env.*`, `Path`, `Path.to_text`, `separator` | std |
| Files and the atomic commit protocol | 19 functions of `std.files` | std |
| Processes | `std.process.run` | std |

4. `unio run` and `unio test` start every program inside the sandbox of requirements section 4.6: the permissions of the nearest `unio.toml`, narrowed by the policy, are applied before `main` or before the first test. Section 9 says how this works and where its limits are.
5. Behavior fixed while implementing the externals, where the declarations were silent:
   - `Float.to_text` writes decimal notation for exponents from −6 to 20 and scientific notation otherwise (`1e+300`), always with a fraction for whole numbers (`2.0`), and `nan`, `inf`, `-inf` for non-finite values; `Text.to_float` does not read the last three back.
   - `Text.index_of` with a `start` outside `0..length()` is a fault, like `slice`. `Int ** n` with a negative `n` is a fault.
   - `std.files.rename` never replaces a target, and the check is part of the rename itself: `renameat2` with `RENAME_NOREPLACE` on Linux, `renamex_np` with `RENAME_EXCL` on macOS, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows. Where the system or the file system lacks this, a file is linked under the new name (which fails if the name exists) and then unlinked, and a directory fails with kind `Unsupported` instead of racing with another process.
   - `std.files.list_tree` does not follow a symbolic link to a directory: the link is listed as an entry, so a cycle of links ends and a link cannot lead the listing out of the tree. A link is recognized because `resolve` of it is not its own place in the resolved tree.
   - `std.env.home_dir` asks the operating system for the profile directory of the user; on Windows that directory is what the system reports through the user profile, not a variable the program set.
   - `std.process.run` gives a child an empty standard input; a child ended by a signal has status 128 plus the signal number; a timeout of zero or less is a `ProcessError` of kind `Other`. The child gets an environment built for it (9.5), runs in a process tree of its own, and has each output captured up to 16 MiB; section 9.5 gives the rules.

## 8. The interpreter of sprint S5 and native code of sprint S6

1. The interpreter of S5 walked the checked syntax tree with the tables of the checker. Sprint S6 lowers that tree first (`compiler/unio/src/lower.rs`): names are resolved to slots of local values and indexes of constants, field positions and enum variants are found once at each place, literal lists and tuples are built once, and calls share one value stack. Several prelude functions (`is_empty`, `first`, `last`, `enumerate`, `contains`, `keys`, `values`, `append_all`, `range`, `Text.to_int`) run as intrinsics of the runtime with the results of their Unio definitions. The same lowered form is the input of native code (item 4). Measurements are in [bench/README.md](../bench/README.md).
2. The interpreter is the reference for the meaning of programs: native code must give the same output, exit code, and diagnostics for every test of the repository (item 5).
3. Exit criterion of S5: every `test` block of `stdlib/`, `examples/`, `docs/examples/`, and `tools/` runs and passes; the tools in `tools/` run in the interpreter and give the same results as the Python checkers, which stay in the repository as the reference for parity and for comparisons of performance.
4. **Native code (first part of S6).** `unio build [--release] FILE [-o OUT]` makes one executable (C-5), so far for Linux on x86-64; the other three targets follow. The build checks the program as `unio run` does, lowers every body as the interpreter does, and translates each lowered body (functions, lambdas, constants, defaults of fields and of parameters of externals) with Cranelift into one object file, which the system C compiler (`cc`, or `CC`) links with `libunio.a`, the runtime built from the compiler's crate. `--release` optimises the generated code; without it Cranelift does not optimise. The design (`compiler/unio/src/native/`):
   - Values have the layout of the runtime: `Value` is `repr(u8)`, its first byte is the tag, the payload of `Int` and `Float` is at offset 8 and that of `Bool` at offset 1. A local whose type is `Int`, `Float`, or `Bool` by its signature or by its binding is kept unboxed in a register. Operators on such values are machine instructions with the checks of section 2: an addition is one add and a branch on overflow, a division tests zero and `MINIMUM_INT / -1`. Values of these types never touch a reference count. `for i in range(a, b)` is a counted loop. Where the type is not known statically, integers are recognised by their tags and still computed inline; comparisons of texts, integers, and booleans are made where the values are, without copying them.
   - A call of a function with a body and without type arguments is a direct call: scalar parameters and results travel in registers, other values by address and are taken by the callee, `var` parameters come back through their addresses. The call frame on the runtime's call stack is pushed and popped inline, and every statement stores its line, so traces and the stack limit (C-14, C-18) are those of the interpreter.
   - Operations on values that own memory call the runtime: dispatch of a method by the type of its receiver with a cache at each call site (an external or a compiled method is then called without a frame of the interpreter), fields (read in place when the frame holds the value, changed in place when assigned), indexing, construction with defaults, interpolation, patterns, iteration, places with indexes, and the externals.
   - Errors, faults, and exhaustion unwind by status: an operation that fails returns status 1, and the code releases the temporaries it holds and continues at the innermost handler of `try` or `on`, at the release of an open `using` block (C-17), or returns status 1 to its caller. `break`, `continue`, and `return` release open `using` blocks on the way, as in the interpreter.
   - The executable holds the program's sources and the manifest of its package. Before `main` it rebuilds the declaration tables from the embedded sources without reading a file, lowers the program in the same way, fills each body's table of references (the caches of its call sites and its literals), applies the sandbox of the manifest narrowed by the policy of `UNIO_POLICY` (SB-1; the arguments belong to the program, so there is no `--policy`), and runs `main` on a thread with the stack of `unio run`. This start takes about as long as the start of `unio run`.
   - A construct that the generator cannot compile yet stops `unio build` with "not yet compiled natively" and its file and line; nothing falls back to the interpreter. Refused so far, and used by no program of the repository: an argument of a method call that changes the name of the receiver through `var`, an indexed place as a `var` argument of a method whose name has a `var` parameter, and `var self` on an indexed place whose index has effects.
   - Builds are deterministic: two builds of one source give the same bytes (C-4).
5. **Equivalence.** `compiler/unio/tests/native.rs` builds every reference program that the tests of the interpreter run (the utilities with their inputs, the task list, programs that end with every kind of fault and with exit codes, the benchmarks, and the four tools of `tools/` over the repository), runs each natively and with `unio run`, and compares standard output, standard error, and the exit code. It also checks that two builds are identical, that a program with errors is not built, and that the executable applies the manifest of its package. CI runs it on Linux x86-64; elsewhere it is skipped with a note.
6. **Not done yet**, in the order that matters for speed: types of the checker in the lowered form, for static dispatch of methods and for monomorphised generics (kinds are now inferred locally from signatures and bindings); elision of reference counts and reuse in place in the style of Perceus (dup and drop by last use, borrowed parameters, reuse of a released cell by a construction of the same size); unboxed lists of scalars; declaration tables serialised into the executable instead of the embedded sources; the other targets; an optimising release back end.

## 9. The sandbox in practice

This section is the documentation of the limits of the sandbox that SB-9 requires.

1. **Where permissions come from.** `unio run` and `unio test` read `[permissions]` from the nearest `unio.toml` above the program (T-6) and narrow it by the policy (SB-3a). Without a manifest, a program can read its arguments and standard input and write to standard output and standard error, nothing else (SB-2). Tests get the same permissions as the program; a test that needs files declares them, for example `files.write = ["$TEMP/**"]`.
2. **Paths and writes.** Relative entries are relative to the directory of the manifest or the policy. Links and `..` are resolved before a path is compared. Writing one file also permits the temporary files of its atomic commit next to it and syncing its directory. A program name without a path matches only a call by that name, never a path that ends in it.
   - **The writer process.** On Linux and macOS a program has no right to write files at the level of the operating system, and neither have the children it starts. Every write-class operation of `std.files` is a request to a writer process: the steps of `AtomicFile` (and so `write_text`, `write_bytes`, and `copy_file`), `create_directory`, and `rename`. The writer is started from the same executable before the sandbox of the program applies, with an empty environment, closed standard input and output, and one end of a socket pair. It receives the effective write scopes (the manifest narrowed by the policy, SB-3a) once, before any code of the program runs, and accepts no other configuration. Then it applies its own sandbox: on Linux `no_new_privs`, Landlock with write access to the write scopes only (a scope of one file on its directory, a right only the writer holds), no reading of other files and no TCP, and seccomp without exec, new processes or threads, and sockets; on macOS a Seatbelt profile with the write scopes, the temporary files of each scope of one file, and reading of the directories on the way to them. The writer ends with the program: the socket closes, and on Linux a parent-death signal kills it.
   - **What the writer checks.** The runtime checks each operation first, as everywhere (item 3); the writer checks it again against its own scopes and does not trust the program. It opens the directory of a path one component at a time from `/` with `O_NOFOLLOW` (on Linux also `O_PATH`), refuses a link on the way, and does every later step relative to that descriptor. A temporary file is created with `O_CREAT | O_EXCL | O_NOFOLLOW` under the name `.<name>.unio-tmp-<writer pid>-<operation id>`; the commit renames it over the target in the same directory with `renameat`; `durable = true` syncs that directory; `rename` uses `renameat2` with `RENAME_NOREPLACE` (`renameatx_np` with `RENAME_EXCL` on macOS); `create_directory` uses `mkdirat`. A directory replaced by a link between two requests therefore cannot lead a commit elsewhere, and a new request through the link is refused. A link as the last name of a target is replaced as an entry and never followed. Operation ids are unpredictable 64-bit numbers issued by the writer: only the operation that created a temporary file can commit or remove it, and a commit must name the target of its operation. The program receives a descriptor of its temporary file (passed with SCM_RIGHTS and closed on exec) and writes the data itself, so the data does not pass through the writer and the file-size limit of the program applies to it. The writer also answers whether a target supports `durable = true` (S-9a), from the mount table it read before its sandbox applied.
   - **The protocol** is versioned and length-prefixed: a frame is a 32-bit little-endian length, then a version byte, an operation byte (configuration, durability query, open, commit, abort, sync by operation, sync of a directory, create a directory, rename), and its fields: 64-bit numbers and byte strings with a 32-bit length. A reply carries a status: done, refused, an error of the system with its number, or malformed. A request that cannot be decoded, of another version, or a second configuration is refused as malformed; a frame over 1 MiB ends the connection. At most 256 atomic files are open at once in one program.
   - **Windows** has no writer process yet: the operations run in the process of the program after the checks of the runtime, since the operating system does not restrict that process there (item 4).
3. **Blocked operations** are the errors the functions declare, of kind `PermissionDenied`, naming the missing permission; `exists` and `is_directory` report `false`, and `env.get` reports `none` (SB-6).
4. **Platforms.**
   - Linux: the runtime checks every operation, and the operating system enforces the read scopes with `no_new_privs`, Landlock (files, TCP, signals), and seccomp (sockets, `ptrace`, mounts, namespaces, `io_uring`, `bpf`, and other dangerous calls); core dumps are disabled. The program and its children may write no file; the writer process writes for the program (item 2). Without Landlock ABI 3 or seccomp the start fails with code 103 unless the operator allows a weaker sandbox.
   - macOS: a deny-by-default Seatbelt profile built from the read scopes; the program and its children may write no file, and the writer process writes for the program (item 2). Seatbelt restricts the whole process once, so the writers of all programs of one `unio test` start before the first profile applies. The profiles are checked in CI on macOS.
   - Windows: AppContainer and the restrictions of Job Objects are not implemented yet (`process.run` uses a Job Object only to stop the process tree of a child, 9.5). A program does not start (code 103) unless the operator passes `--allow-weaker-sandbox`; then only the checks of the runtime and the time and heap limits apply. SB-8 is not met on Windows until this is done.
5. **Limits.** Wall and CPU time are enforced by a watchdog that ends the program with code 102; the CPU limit also applies to children. The process limit counts calls of `process.run`. The file-size limit is checked by the runtime and, on Linux and macOS, by the operating system. Child processes of `process.run`:
   - **Environment.** A child receives only the variables the effective permissions grant under `env`, and `PATH` (on Windows also `SystemRoot`), with the values of the running program; nothing else is inherited. `PATH` is passed because the runtime finds a program by its bare name through it and the child may run further programs in the same way; `SystemRoot` because system libraries on Windows do not load without it. Locale, time zone, home, and temporary-directory variables are not passed unless granted, and a child without them uses the defaults of its system (for example the C locale). Without a sandbox, as in the tests of the runtime, a child inherits the whole environment, matching `env.get`, which then permits every variable.
   - **Process tree.** On Unix the child leads a new process group, and every process it starts belongs to it unless it leaves it; on Windows the child is put in a Job Object with kill-on-close. When the child ends, the processes still running in its tree are stopped (SIGKILL to the group, which happens before the child is reaped, so the number of the group cannot be reused in between; on Windows the job is terminated). On a timeout, on output over the limit, and on exhaustion the whole tree is stopped. When the watchdog ends the program with code 102, it stops the process groups of the children that still run.
   - **Deadline and output.** `timeout_seconds` covers the whole call, including reading the outputs. If the child has ended but a pipe stays open, the call waits for it only until the deadline and then fails with `TimedOut`; waiting on pipes is always bounded. Each of standard output and standard error is captured up to 16 MiB (16,777,216 bytes); more fails with kind `OutputTooLarge`. The captured bytes count against the heap limit as they arrive, and exceeding it ends the program with code 102.
   - **Limits of the tree.** A process that leaves the process group (`setsid`, `setpgid`, or a double fork into a new session) is not stopped by the runtime and can outlive the call; a reader thread then stays blocked on a pipe that process holds until it closes it, but the call itself returns at the deadline. On Windows, a process the child starts in the moment between its start and its joining the job is not in the job, and a process that breaks away from the job (if the job permits it) escapes too. On Unix, an interrupt from the terminal (Ctrl-C) reaches only `unio`, not a child in its own group: that child runs on until it ends by itself. Seccomp, Landlock, and Seatbelt still restrict a process that escaped the tree.
6. **What the sandbox does not do** (SB-9).
   - It does not protect against vulnerabilities of the kernel, against side channels, or against misuse of what was granted: a program allowed to write `$HOME/**` can destroy those files.
   - Writing is exact at the level of the operating system: neither a program nor its children can write any file there, and the writer process, which holds the directory-level right that a scope of one file needs, permits only that file and the temporary files of its own operations. A child cannot write even the files the program may write; it returns data to the program, which writes them. A write scope whose directory does not exist when the program starts cannot be written at all, since the rule of the writer's sandbox needs the directory.
   - Reading and running are still coarser at the level of the operating system than the checks of the runtime. A read scope whose root does not exist at start grants nothing there. Any `process` permission lets children read and execute the system directories: on Linux `/usr`, `/bin`, `/sbin`, `/lib`, `/lib32`, `/lib64`, `/libx32`, `/opt`, `/nix/store`, and the directories of `PATH`, the files `/etc/ld.so.cache`, `/etc/ld.so.conf`, `/etc/ld.so.conf.d`, `/etc/localtime`, `/etc/nsswitch.conf`, `/etc/passwd`, `/etc/group`, and `/etc/alternatives`, and writing `/dev/null`; on macOS `/usr/lib`, `/usr/libexec`, `/usr/share`, `/System`, `/Library/Apple`, `/private/var/db/dyld`, `/private/preboot/Cryptexes`, `/private/etc/localtime`, and listing the names in `/`, which the loader reads at start. A child may read and run what those grant, even where the read scopes of the program do not reach.
   - The writer trusts the scopes it receives from the runtime of the same executable before the program runs; it does not read the manifest or the policy again. It does not stop another process of the same user that can write the directories of the scopes: such a process can replace a temporary file or a target between two requests, which never leads a write outside the scopes but can change what a target holds.
   - On Linux the rules apply to the threads that run the program and to its children; the idle main thread of `unio run` is not restricted.
   - For code written by AI, use a minimal manifest, a policy with limits, and a separate user, container, or virtual machine for untrusted code.
